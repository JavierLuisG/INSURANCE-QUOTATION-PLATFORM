## 3. User Story
Como sistema,
Quiero validar que las sumas aseguradas de las coberturas estén dentro de los rangos predefinidos,
Para asegurar que los valores son coherentes con las políticas de suscripción.

## 4. Functional Description
**Description:** Esta historia de usuario describe el proceso automatizado mediante el cual el sistema verificará que la suma asegurada especificada para una cobertura individual cumple con los límites (mínimo y máximo) preestablecidos para dicha cobertura. El propósito principal es aplicar las políticas de suscripción, previniendo la aceptación de valores que no cumplan con los criterios de negocio. Los rangos de validación deben ser configurables y accesibles.
**Flow:** [HU-164 - Parámetros Disponibles para Motores de Cálculo y Validación] → [HU-165 - Validar Rangos de Sumas Aseguradas] → [Continuación del flujo de creación/actualización de pólizas si es válido / Generación de error si es inválido]

## 6. Acceptance Criteria (3-5 criteria)
### AC-001: Validación de suma asegurada dentro de rango
**Description:** Este criterio valida que una suma asegurada se considera válida si se encuentra entre el valor mínimo y máximo permitido para la cobertura.

```gherkin
Scenario: Suma asegurada dentro del rango permitido
  Given que se ha configurado un rango para una cobertura (ej. Mínimo: 1000, Máximo: 10000)
  When el usuario ingresa una suma asegurada de 5000
  Then el sistema valida la suma asegurada sin generar ningún error
```

### AC-002: Generación de error por suma asegurada fuera de rango mínimo
**Description:** Este criterio asegura que el sistema genera un error de validación claro cuando la suma asegurada ingresada es menor que el mínimo permitido.

```gherkin
Scenario: Suma asegurada menor que el rango mínimo
  Given que se ha configurado un rango para una cobertura (ej. Mínimo: 1000, Máximo: 10000)
  When el usuario ingresa una suma asegurada de 500
  Then el sistema genera un error de validación claro indicando que la suma asegurada está por debajo del mínimo
```

### AC-003: Generación de error por suma asegurada fuera de rango máximo
**Description:** Este criterio verifica que el sistema genera un error de validación claro cuando la suma asegurada ingresada es mayor que el máximo permitido.

```gherkin
Scenario: Suma asegurada mayor que el rango máximo
  Given que se ha configurado un rango para una cobertura (ej. Mínimo: 1000, Máximo: 10000)
  When el usuario ingresa una suma asegurada de 12000
  Then el sistema genera un error de validación claro indicando que la suma asegurada excede el máximo
```

## 7. Data and Business Rules


| field | type | required | default | validation | catalog | example |
|---|---|---|---|---|---|---|
| id_cobertura | string | yes | N/A | Identificador único de cobertura | Catálogo de Coberturas | COB001 |
| suma_asegurada | decimal | yes | N/A | Valor numérico positivo, hasta dos decimales | N/A | 7500.50 |
| rango_minimo | decimal | yes | 0.00 | Valor numérico positivo, <= rango_maximo | Parámetros de Configuración | 1000.00 |
| rango_maximo | decimal | yes | 999999999.99 | Valor numérico positivo, >= rango_minimo | Parámetros de Configuración | 100000.00 |


**BR-001:** Validación de Rango de Suma Asegurada por Cobertura
- Description: La suma asegurada para una cobertura específica debe estar contenida dentro de los valores de rango mínimo y rango máximo preestablecidos para esa cobertura.
- Trigger: Esta regla se ejecuta cada vez que se intenta establecer o modificar la suma asegurada de una cobertura.
- Logic: `(suma_asegurada >= rango_minimo_cobertura) AND (suma_asegurada <= rango_maximo_cobertura)`
- Implementation: Módulo de Reglas de Validación (Backend)
- Exception: Si la condición lógica no se cumple, se genera una excepción de validación que resulta en un error para el usuario o sistema llamador.

## 13. Edge Cases and Exceptions
### Case 1: Rangos de cobertura no definidos
```gherkin
Scenario: Rangos de cobertura no encontrados
  Given que la cobertura 'COB002' no tiene rangos mínimo y máximo configurados en el sistema
  When el sistema intenta validar una suma asegurada para 'COB002'
  Then el sistema genera un error indicando que los rangos de la cobertura no están disponibles o configurados
  And la operación de establecer la suma asegurada es rechazada
```

### Case 2: Suma asegurada con valor cero o negativo
```gherkin
Scenario: Suma asegurada con valor no positivo
  Given que se ha configurado un rango para una cobertura (ej. Mínimo: 1000, Máximo: 10000)
  When el usuario ingresa una suma asegurada de 0 o -500
  Then el sistema genera un error de validación indicando que la suma asegurada debe ser un valor positivo
```

## 16. Technical Notes and Risks
**Risks:**
1.  **Consistencia y Disponibilidad de Datos de Rango:**
    *   Descripción: Si los rangos configurados para las coberturas (provenientes de HU-123 y HU-164) son incorrectos, inconsistentes o no están disponibles, la validación fallará o, peor aún, permitirá valores inválidos o rechazará valores válidos.
    *   Impacto: Errores en la emisión de pólizas, incumplimiento de políticas de suscripción, insatisfacción del cliente, posibles riesgos financieros.
    *   Probabilidad: Media.
    *   Mitigación: Implementar robustos controles de calidad en la configuración de parámetros, asegurar alta disponibilidad y resiliencia del servicio de parámetros, monitoreo de la integridad de los datos de configuración.
**Technical Debt:** N/A (Se determinará por el equipo operativo según el alcance y el MVP).

## 17. Criticality
**Criticality Level:** Alta
**Justification:** Esta historia es crítica porque es un punto de control fundamental para asegurar la validez y coherencia de los datos de las pólizas de seguro. Un fallo en esta validación podría llevar a la emisión de pólizas financieramente inviables o no conformes con las políticas de suscripción.
**Feature Impact:** La no implementación o el fallo de esta validación comprometería la integridad de todo el proceso de suscripción y gestión de pólizas, afectando directamente la capacidad del negocio para operar de manera segura y rentable.
**Critical Dependencies:** Las historias US-123 y US-164 son dependencias críticas, ya que sin los parámetros de rango correctos, esta validación no puede funcionar.
**Recommended Priority:** Sprint actual (dada su prioridad "Alta" y su impacto en la integridad del negocio).
