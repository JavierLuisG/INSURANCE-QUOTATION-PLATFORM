## 2. Enabled Capability
**CAP-005:** Gestión de Estados de Cotización
**Business Value:** Permite reflejar el resultado final de la negociación con el cliente, optimizando el seguimiento de las oportunidades de venta y la precisión en los reportes de estado y pipeline comercial.

**Enables:** CAP-006 (Generación de Reportes de Ventas y Cierre de Oportunidad)
**Orchestrates:** N/A

## 3. User Story
Como usuario,
Quiero cambiar manualmente el estado de una cotización a "Aprobada" o "Rechazada" desde "Calculada",
Para poder indicar el resultado de la negociación con el cliente.

## 4. Functional Description
**Description:** Esta historia de usuario permite a un usuario con los permisos adecuados (ej. Vendedor) actualizar el estado de una cotización de forma manual. Cuando una cotización ha alcanzado el estado "Calculada", el usuario tendrá la opción de marcarla como "Aprobada" o "Rechazada" a través de la interfaz de usuario. El sistema validará que la cotización se encuentre en el estado "Calculada" antes de permitir la actualización. Esta acción refleja el resultado de la interacción o negociación con el cliente y es crucial para el seguimiento del pipeline de ventas.
**Flow:** [HU-136: Cotización en estado "Calculada"] → [HU-137: Cambio manual a "Aprobada" o "Rechazada"] → [HU-XXX: Cierre de oportunidad / Generación de reportes]

## 5. Expected Results


| element | description |
|---|---|
| Data | El campo 'estado' de la entidad 'Cotizacion' se actualizará a 'Aprobada' o 'Rechazada'. Se creará un nuevo registro en la tabla 'HistoricoEstadoCotizacion' con el ID de la cotización, el estado anterior ('Calculada'), el nuevo estado, la fecha (2026-04-21) y el usuario que realizó la acción. |
| States | La cotización pasará del estado 'Calculada' al estado 'Aprobada' o 'Rechazada'. Otros estados (ej. 'Borrador', 'En Revisión') no permitirán esta transición. |
| Notifications | Se mostrará un mensaje de éxito en la UI ('Cotización aprobada/rechazada con éxito'). En caso de error (ej. estado incorrecto), se mostrará un mensaje de advertencia. (Opcional) Notificación interna por email al equipo de ventas o al creador de la cotización. |
| Integrations | (Opcional) Si existe, se podría invocar una API externa de un CRM (Customer Relationship Management) o ERP (Enterprise Resource Planning) para sincronizar el estado de la oportunidad de venta. |
| Kafka | (Opcional) Publicar un evento 'CotizacionEstadoCambiado' con el ID de la cotización, el estado anterior, el nuevo estado y el usuario que realizó la acción. Consumido por servicios de reportes o auditoría. |
| Logs | Registros de nivel 'INFO' para el éxito del cambio de estado. Registros de nivel 'WARN' para intentos fallidos de cambio de estado (ej. estado incorrecto). |
| UI | Los botones 'Aprobar' y 'Rechazar' estarán visibles y habilitados en la pantalla de detalle de la cotización solo cuando su estado sea 'Calculada'. El estado visible de la cotización en la UI se actualizará al nuevo valor. |


## 6. Acceptance Criteria (3-5 criteria)
### AC-001: Cambio de estado a "Aprobada"
**Description:** Valida que una cotización en estado "Calculada" pueda ser cambiada a "Aprobada" por el usuario.

```gherkin
Scenario: Aprobar una cotización en estado "Calculada"
  Given una cotización con ID "COT-001" en estado "Calculada"
  When el usuario selecciona la acción "Aprobar" para la cotización "COT-001"
  Then el estado de la cotización "COT-001" cambia a "Aprobada"
  And el sistema registra el cambio de estado con la fecha actual (2026-04-21) en el historial de la cotización
  And se muestra un mensaje de éxito al usuario
```

### AC-002: Cambio de estado a "Rechazada"
**Description:** Valida que una cotización en estado "Calculada" pueda ser cambiada a "Rechazada" por el usuario.

```gherkin
Scenario: Rechazar una cotización en estado "Calculada"
  Given una cotización con ID "COT-002" en estado "Calculada"
  When el usuario selecciona la acción "Rechazar" para la cotización "COT-002"
  Then el estado de la cotización "COT-002" cambia a "Rechazada"
  And el sistema registra el cambio de estado con la fecha actual (2026-04-21) en el historial de la cotización
  And se muestra un mensaje de éxito al usuario
```

### AC-003: Restricción de cambio de estado desde un estado no "Calculada"
**Description:** Valida que el sistema impida el cambio de estado a "Aprobada" o "Rechazada" si la cotización no está en estado "Calculada".

```gherkin
Scenario: Intentar cambiar el estado de una cotización que no está en "Calculada"
  Given una cotización con ID "COT-003" en estado "Borrador"
  When el usuario intenta seleccionar la acción "Aprobar" para la cotización "COT-003"
  Then el sistema impide la acción
  And se muestra un mensaje de error indicando que la cotización no puede ser aprobada desde su estado actual
  And el estado de la cotización "COT-003" permanece en "Borrador"
```

**BR-001:** Validación de Estado Previo para Aprobación/Rechazo
- Description: Una cotización solo puede ser aprobada o rechazada si su estado actual es "Calculada".
- Trigger: Intento de cambio de estado a "Aprobada" o "Rechazada".
- Logic: `IF cotizacion.estado_actual != "Calculada" THEN RECHAZAR_ACCION_Y_NOTIFICAR_ERROR`.
- Implementation: Servicio de gestión de cotizaciones (backend).
- Exception: N/A.

**BR-002:** Registro de Historial de Estado
- Description: Cada cambio de estado de una cotización debe ser registrado en un historial, incluyendo el estado anterior, el nuevo estado, la fecha y el usuario que realizó la acción.
- Trigger: Cambio exitoso del estado de una cotización.
- Logic: Crear un registro en `HistoricoEstadoCotizacion` con `cotizacionId`, `estadoAnterior`, `nuevoEstado`, `fechaCambio` (2026-04-21), `usuarioId`.
- Implementation: Servicio de gestión de cotizaciones (backend).
- Exception: N/A.

## 10. UX and Navigation Flow
**UX Flow:**
1.  El usuario navega a la pantalla de detalle de una cotización.
2.  Si la cotización está en estado "Calculada", los botones "Aprobar Cotización" y "Rechazar Cotización" están visibles y habilitados.
3.  El usuario hace clic en "Aprobar Cotización" o "Rechazar Cotización".
4.  (Opcional) Se presenta un modal de confirmación: "¿Está seguro de que desea [aprobar/rechazar] esta cotización [ID]?"
5.  Tras la confirmación, el sistema procesa la solicitud.
6.  Si la acción es exitosa, se muestra un mensaje de éxito en la UI y el estado de la cotización se actualiza visualmente en la pantalla.
7.  Si la acción falla (ej. estado incorrecto, cotización no encontrada), se muestra un mensaje de error o advertencia en la UI.
**Messages/Modals:**
-   Éxito: "Cotización [ID] aprobada/rechazada correctamente."
-   Error: "No se pudo [aprobar/rechazar] la cotización [ID]. El estado actual debe ser 'Calculada'."
-   Confirmación (Opcional): "¿Confirma que desea [aprobar/rechazar] la cotización [ID]?"
**Stepper/Breadcrumbs:** No aplica directamente a este cambio de estado.

## 16. Technical Notes and Risks
**Risks:**
1.  **Conflicto de Concurrencia:**
    -   Description: Múltiples usuarios o procesos automáticos intentando cambiar el estado de la misma cotización simultáneamente, lo que podría llevar a estados inconsistentes.
    -   Impact: Datos inconsistentes, errores de usuario, pérdida de información.
    -   Probability: Media.
    -   Mitigation: Implementar bloqueo optimista (ej. campo de versión o timestamp de última actualización) o pesimista a nivel de registro en el backend. Validar el estado actual de la cotización antes de cualquier actualización.
2.  **Permisos Incorrectos:**
    -   Description: Configuración errónea de RBAC que permite a usuarios no autorizados cambiar el estado o deniega el acceso a usuarios legítimos.
    -   Impact: Brechas de seguridad o bloqueo de operaciones críticas.
    -   Probability: Baja-Media.
    -   Mitigation: Pruebas exhaustivas de RBAC, revisión de configuración de roles y políticas de seguridad.
**Technical Debt:** (A ser completado por el equipo operativo según el alcance y el MVP)

## 17. Criticality
**Criticality Level:** Alta
**Justification:** Esta funcionalidad es fundamental para el proceso de ventas, ya que permite a los usuarios reflejar el resultado de la interacción con el cliente. Sin ella, las cotizaciones quedarían estancadas en un estado intermedio, impidiendo la finalización de oportunidades de venta y la medición del rendimiento comercial.
**Feature Impact:** La no implementación o fallo de esta historia bloquea la capacidad de la empresa para cerrar tratos, realizar un seguimiento preciso del pipeline de ventas y generar reportes significativos, afectando directamente los ingresos y la toma de decisiones estratégicas.
**Critical Dependencies:** Impacta directamente en la generación de reportes de ventas, la asignación de recursos y el flujo de trabajo post-venta.
**Recommended Priority:** Sprint Actual (dada la alta prioridad y las dependencias críticas).
