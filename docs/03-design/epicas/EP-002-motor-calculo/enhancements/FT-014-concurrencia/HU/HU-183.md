## 3. User Story
Como Sistema,
Quiero que en caso de conflicto de concurrencia, se notifique al usuario de la existencia de una versión más reciente,
Para que se le informe que sus cambios podrían sobrescribir los de otro.

## 4. Functional Description
**Description:** Esta historia detalla la funcionalidad mediante la cual el sistema alertará al usuario cuando se detecte un conflicto de concurrencia al intentar guardar o modificar una cotización. El propósito principal es informar al usuario que la versión de la cotización con la que está trabajando no es la más actualizada, evitando así la sobrescritura accidental de cambios realizados por otro usuario o la pérdida de datos. La notificación debe ser clara, prominente y guiar al usuario hacia una acción correctiva, como recargar la cotización.
**Flow:** HU-182 (Detectar Conflicto de Concurrencia) → HU-183 (Notificar Usuario de Versión Más Reciente) → [Usuario decide recargar o descartar sus cambios]

## 6. Acceptance Criteria (3-5 criteria)
### AC-001: Notificación clara de conflicto de versión
**Description:** Valida que el sistema notifique al usuario de un conflicto de concurrencia con un mensaje explícito y comprensible.

```gherkin
Scenario: El sistema notifica al usuario sobre un conflicto de versión más reciente
  Given se ha detectado un conflicto de concurrencia al intentar guardar una cotización
  When el sistema notifica al usuario
  Then se muestra un mensaje claro indicando "¡Conflicto de Versión! La cotización ha sido actualizada por otro usuario. Por favor, recargue para ver la versión más reciente."
  And el mensaje es prominente y visible para el usuario
```

### AC-002: Requisito de recarga y acción del usuario
**Description:** Valida que el mensaje de notificación informe al usuario sobre la acción necesaria (recargar) y requiera una interacción.

```gherkin
Scenario: El mensaje de notificación informa sobre la acción de recarga y requiere interacción
  Given el usuario está visualizando el mensaje de conflicto de concurrencia
  When el usuario intenta continuar con sus cambios sin recargar
  Then el sistema le impide el guardado o le advierte sobre la pérdida de sus cambios actuales
  And la notificación ofrece una opción clara para "Recargar Cotización"
```

### AC-003: Notificación bloqueante y con opciones
**Description:** Valida que la notificación sea crítica, que impida la continuación del flujo sin una decisión y que ofrezca opciones al usuario.

```gherkin
Scenario: La notificación de conflicto de concurrencia es bloqueante y ofrece opciones
  Given se ha mostrado una notificación de conflicto de concurrencia
  When el usuario interactúa con la notificación
  Then el sistema presenta al menos una opción para "Recargar Cotización (descartar cambios)"
  And el sistema no permite el guardado de la versión obsoleta
```

**BR-001:** Regla de Notificación de Concurrencia
- Description: Cuando el backend detecta que la versión de la cotización que un usuario intenta guardar es anterior a la versión almacenada en la base de datos, debe instruir al frontend para que muestre una notificación de conflicto.
- Trigger: Intento de guardar/actualizar una cotización por parte del usuario.
- Logic: `IF cotizacion_enviada.version < cotizacion_almacenada.version THEN ENVIAR_ERROR_CONCURRENCIA_FRONTEND`
- Implementation: Servicio de backend (validación de versión y generación de error), Componente de UI (manejo del error y visualización de la notificación).

## 10. UX and Navigation Flow
**UX Flow:**
1.  **Usuario edita cotización:** El usuario está en la pantalla de edición de una cotización.
2.  **Intenta guardar:** El usuario hace clic en el botón "Guardar" o "Aplicar Cambios".
3.  **Sistema detecta conflicto:** El backend detecta que la versión de la cotización es obsoleta.
4.  **Notificación modal:** Se muestra un modal o banner de advertencia superpuesto en la pantalla.
5.  **Mensaje y opciones:** El modal contiene el mensaje de conflicto y botones de acción como "Recargar Cotización" o "Cancelar (y perder cambios)".
6.  **Acción del usuario:** El usuario selecciona una de las opciones.
7.  **Flujo posterior:** Si "Recargar", la página se actualiza con la última versión. Si "Cancelar", el modal se cierra y el usuario puede continuar editando (sabiendo que no podrá guardar la versión actual) o navegar fuera.
**Messages/Modals:**
*   **Título:** "¡Conflicto de Versión!"
*   **Contenido:** "La cotización ha sido actualizada por otro usuario. Por favor, recargue para ver la versión más reciente y evitar sobrescribir cambios."
*   **Botones:** "Recargar Cotización", "Cancelar (Mantener mis cambios, no guardar)"
**Stepper/Breadcrumbs:** No aplica directamente; la notificación es un evento emergente.

## 11. Architecture and Technical Dependencies
- **Frontend (Sistema de Notificación al Usuario):** Componente de UI encargado de recibir el error de concurrencia del backend y renderizar el modal/banner de notificación. Debe manejar la interacción del usuario (ej. clic en "Recargar").
- **Backend (Servicio de Mensajes de Error de Concurrencia):** El servicio que gestiona la lógica de guardado de cotizaciones es responsable de detectar la discrepancia de versiones y de retornar un código de error específico o un mensaje al frontend que indique el conflicto de concurrencia.
- **API Gateway:** Encargado de enrutar las solicitudes de guardado y las respuestas de error entre el frontend y el backend.

## 13. Edge Cases and Exceptions

```gherkin
  And el sistema no permite el guardado de la versión obsoleta
```

### Case 2: Múltiples conflictos de concurrencia en poco tiempo
```gherkin

  When el primer usuario intenta guardar sus nuevos cambios
  Then el sistema detecta un nuevo conflicto y muestra la notificación nuevamente
```

```gherkin

  Then se muestra un mensaje de error apropiado al usuario y la cotización no se actualiza
```

## 16. Technical Notes and Risks
**Risks:**
1.  **Riesgo: Fatiga del usuario por notificaciones.**
    *   Description: Si los conflictos de concurrencia son muy frecuentes, el usuario podría cansarse de ver la notificación, lo que podría llevar a ignorarla o a una mala experiencia.
    *   Impact: Experiencia de usuario negativa, posible pérdida de datos si se ignora la notificación.
    *   Probability: Media.
    *   Mitigation: Investigar la causa raíz de los conflictos frecuentes (ej. flujos de trabajo, diseño de UI) y considerar opciones de resolución de conflictos más avanzadas en futuras historias.
2.  **Riesgo: Problemas de latencia en la recarga.**
    *   Description: Si el proceso de "Recargar Cotización" es lento, el usuario podría frustrarse o pensar que la aplicación no responde.
    *   Impact: Experiencia de usuario negativa.
    *   Probability: Baja.
    *   Mitigation: Optimizar el rendimiento de la carga de cotizaciones y proporcionar indicadores visuales de carga durante el proceso de recarga.
**Technical Debt:** N/A (por ahora)
**Notas de Implementación:**
*   La notificación debe ser un modal o un banner que no se pueda cerrar fácilmente sin tomar una decisión.
*   Los botones de acción deben ser claros y distintivos (ej. "Recargar Cotización" como acción primaria, "Cancelar" como secundaria).
*   Considerar si el "Cancelar" implica la pérdida de los cambios o simplemente cierra el modal sin guardar, permitiendo al usuario seguir editando pero sin poder guardar la versión actual. Se recomienda que implique la pérdida o una advertencia clara.

## 17. Criticality
**Criticality Level:** Alta
**Justification:** Esta historia es fundamental para garantizar la integridad de los datos de las cotizaciones y prevenir la pérdida de trabajo de los usuarios. Sin una notificación clara, los usuarios podrían sobrescribir los cambios de otros sin darse cuenta, llevando a graves inconsistencias en la información y a una experiencia de usuario muy frustrante.
**Feature Impact:** La no implementación o el fallo de esta historia comprometería seriamente la fiabilidad de la funcionalidad de edición de cotizaciones, especialmente en entornos multiusuario, haciendo que la característica sea inestable y propensa a errores.
**Critical Dependencies:** Depende críticamente de la correcta implementación y funcionamiento de HU-182 (Detección de Conflicto de Concurrencia).
**Recommended Priority:** Sprint actual (dada su alta prioridad y dependencia crítica).
