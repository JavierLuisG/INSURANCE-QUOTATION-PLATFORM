## 3. User Story
Como sistema,
Quiero consumir o simular la consulta de `factores_equipo_electronico` del servicio `Plataforma-core-ohs`,
Para aplicar el factor técnico de equipo electrónico en el cálculo de primas.

## 4. Functional Description
**Description:** Esta historia de usuario describe la funcionalidad para obtener los factores técnicos relacionados con el equipo electrónico. El sistema debe ser capaz de consultar estos factores desde el servicio externo `Plataforma-core-ohs`. En caso de que el servicio externo no esté disponible o para propósitos de desarrollo/pruebas, el sistema debe poder simular la consulta utilizando un mock. Una vez obtenidos, los factores deben ser procesados, mapeados a la estructura interna del sistema y estar disponibles para su uso en el motor de cálculo de primas, asegurando que el valor correcto se aplique según la clase de equipo y el nivel de zona.
**Flow:** [Inicio de Cálculo de Primas] → [HU-162: Consumir Factores de Equipo Electrónico] → [Aplicación de Factores en Cálculo]

## 7. Data and Business Rules


| field | type | required | default | validation | catalog | example |
|---|---|---|---|---|---|---|
| clase_equipo_electronico | string | yes | N/A | Debe coincidir con un valor definido en el catálogo de clases de equipo electrónico | CatalogoClasesEquipoElectronico | Portatil, Servidor, Periférico |
| nivel_zona | string | yes | N/A | Debe coincidir con un valor definido en el catálogo de niveles de zona | CatalogoNivelesZona | Zona A, Zona B, Zona C |
| factor_valor | decimal | yes | 1.0 | Valor numérico positivo, con un máximo de 4 decimales | N/A | 1.25, 0.98, 1.05 |


**BR-001:** Mapeo de Factores de Equipo Electrónico
- Description: Los factores recibidos del servicio `Plataforma-core-ohs` deben ser mapeados a la estructura de datos interna del sistema para su correcto procesamiento.
- Trigger: Después de recibir la respuesta de la consulta de `factores_equipo_electronico`.
- Logic:
  ```
  FOR EACH factor_recibido IN response.factores:
      factor_interno.clase_equipo = factor_recibido.clase
      factor_interno.nivel_zona = factor_recibido.zona
      factor_interno.valor = factor_recibido.valor_factor
      ADD factor_interno TO lista_factores_disponibles
  ```
- Implementation: Backend (Adaptador para `Plataforma-core-ohs`)
- Exception: Si la estructura de `factor_recibido` es inválida o incompleta, se registra un error y se notifica al equipo de soporte.

**BR-002:** Aplicación de Factor por Clase y Zona
- Description: Al calcular la prima, el sistema debe identificar y aplicar el factor de equipo electrónico correspondiente a la clase de equipo y nivel de zona de la ubicación asegurada.
- Trigger: Durante el proceso de cálculo de prima para un elemento con equipo electrónico.
- Logic:
  ```
  LET clase_ubicacion = obtenerClaseEquipo(ubicacion_asegurada)
  LET zona_ubicacion = obtenerNivelZona(ubicacion_asegurada)
  LET factor_aplicable = BUSCAR factor EN lista_factores_disponibles
                         WHERE factor.clase_equipo == clase_ubicacion
                         AND factor.nivel_zona == zona_ubicacion
  IF factor_aplicable ES NULL THEN
      USAR valor_factor_default (ej. 1.0)
      REGISTRAR WARNING: "Factor no encontrado para Clase: [clase_ubicacion], Zona: [zona_ubicacion]"
  ELSE
      APLICAR factor_aplicable.valor AL calculo_prima
  ```
- Implementation: Backend (Motor de Cálculo de Primas)
- Exception: Si no se encuentra un factor para la combinación de clase y zona, se debe usar un valor por defecto y registrar una advertencia.

## 16. Technical Notes and Risks
**Risks:**
1.  **Dependencia de Plataforma-core-ohs:**
    -   Description: La disponibilidad y el rendimiento de `Plataforma-core-ohs` son críticos.
    -   Impact: Fallos en el cálculo de primas si el servicio no responde o lo hace lentamente.
    -   Probability: Media.
    -   Mitigation: Implementar Circuit Breaker, reintentos, timeouts, caching de factores y un factor por defecto como fallback. Asegurar monitoreo y alertas.
2.  **Complejidad del Mapeo de Datos:**
    -   Description: La estructura de los factores en `Plataforma-core-ohs` puede ser diferente a la interna.
    -   Impact: Errores en la aplicación del factor si el mapeo es incorrecto.
    -   Probability: Media.
    -   Mitigation: Definición clara del contrato de la API, pruebas de contrato exhaustivas y validación de esquema en tiempo de ejecución.
3.  **Definición de Clases/Zonas:**
    -   Description: La "Nota de Implementación" indica que se debe definir cómo se clasifica el equipo electrónico y su relación con las zonas.
    -   Impact: Bloqueo de la implementación o cálculo incorrecto si esta definición no es clara o cambia.
    -   Probability: Alta (si no se aborda proactivamente).
    -   Mitigation: Sesión de refinamiento con el PO y/o expertos de negocio para definir catálogos de clases de equipo y niveles de zona antes de iniciar la implementación.

**Technical Debt:** Si el mock server (HU-092) se mantiene activo en entornos que no son de desarrollo/pruebas, podría considerarse deuda técnica por riesgo de uso de datos no reales. Asegurar que el uso del mock sea configurable y deshabilitado por defecto en producción.

## 17. Criticality
**Criticality Level:** Media
**Justification:** Es fundamental para la precisión del cálculo de primas, pero la existencia de un mock y la posibilidad de usar un valor por defecto en caso de fallo crítico mitigan su impacto inmediato en la operatividad total, permitiendo un cálculo básico.
**Feature Impact:** Sin esta historia, el cálculo de primas para equipos electrónicos sería incompleto o incorrecto, lo que podría llevar a primas subestimadas o sobreestimadas, afectando la rentabilidad o la competitividad.
**Critical Dependencies:** Cualquier historia de usuario o proceso que dependa del cálculo de primas para equipos electrónicos.
**Recommended Priority:** Sprint actual o siguiente, una vez que la definición de clases/zonas esté clara.
