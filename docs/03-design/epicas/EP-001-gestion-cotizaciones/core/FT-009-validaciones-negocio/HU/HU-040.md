## 2. Enabled Capability
**CAP-003:** Validación de Datos de Ubicación
**Business Value:** Asegura la consistencia y corrección de la información de riesgo, lo que reduce errores manuales, mejora la calidad de los datos para análisis y cálculos de riesgo, y previene problemas regulatorios.
**Requires:** CAP-002: Gestión de Ubicaciones de Riesgo (FT-002)
**Enables:** CAP-004: Cálculo de Primas y Evaluación de Riesgos (datos correctos son fundamentales para estas funcionalidades)
**Orchestrates:** N/A (Principalmente validaciones internas)

## 3. User Story
Como un usuario,
quiero que los datos específicos de cada ubicación de riesgo se validen,
para asegurar la consistencia y corrección de la información de riesgo.

## 4. Functional Description
**Description:** Esta historia de usuario se enfoca en la implementación de validaciones robustas para los datos ingresados por el usuario al crear o modificar una ubicación de riesgo. El sistema debe verificar la validez de campos críticos como el código postal, el valor del bien y los campos obligatorios. En caso de detectar inconsistencias o datos inválidos, el sistema proporcionará retroalimentación clara al usuario, diferenciando entre errores que impiden el guardado y advertencias que requieren confirmación pero permiten continuar. Las reglas de validación deben ser configurables para adaptarse a futuras necesidades de negocio.
**Flow:** HU-009: Consultar y validar código postal de ubicación → **HU-040: Validar datos específicos de cada ubicación de riesgo** → HU-XXX: Guardar/Actualizar Ubicación de Riesgo.

## 6. Acceptance Criteria (3-5 criteria)
### AC-001: Validación de Código Postal Inexistente
**Description:** Valida que el sistema impide guardar una ubicación si el código postal introducido no existe en el catálogo de códigos postales válidos.

```gherkin
Scenario: El sistema muestra un error si el código postal no existe
  Given que estoy en el formulario de creación/edición de una ubicación de riesgo
  And he introducido todos los datos obligatorios válidos, excepto el código postal
  When introduzco un "código postal inexistente" (ej. "99999")
  And intento guardar la ubicación
  Then el sistema muestra un mensaje de error claro indicando que el código postal es inválido
  And la ubicación no es guardada
```

### AC-002: Límite de Valor del Bien Excedido
**Description:** Valida que el sistema reacciona adecuadamente (mostrando una advertencia o error) cuando el valor del bien excede un límite máximo predefinido por las reglas de negocio.

```gherkin
Scenario: El sistema muestra una advertencia o error si el valor del bien excede el límite
  Given que estoy en el formulario de creación/edición de una ubicación de riesgo
  And he introducido todos los datos obligatorios válidos
  When introduzco un "valor del bien" que excede el límite predefinido (ej. "1.000.000.000 USD")
  And intento guardar la ubicación
  Then el sistema muestra una "advertencia o error" según la regla de negocio configurada
  And si es una advertencia, permite el guardado tras confirmación; si es un error, impide el guardado
```

### AC-003: Campos Obligatorios Vacíos
**Description:** Valida que el sistema impide guardar una ubicación si algún campo obligatorio está vacío, indicando claramente al usuario qué campos deben completarse.

```gherkin
Scenario: El sistema indica los campos obligatorios vacíos y no permite guardar
  Given que estoy en el formulario de creación/edición de una ubicación de riesgo
  When dejo un "campo obligatorio" (ej. "dirección", "uso", "tipo de bien") vacío
  And intento guardar la ubicación
  Then el sistema resalta el campo vacío
  And muestra un mensaje de error indicando que el campo es obligatorio
  And la ubicación no es guardada
```

## 7. Data and Business Rules


| field | type | required | default | validation | catalog | example |
|---|---|---|---|---|---|---|
| codigoPostal | string | yes | N/A | Formato de 5 dígitos numéricos; debe existir en el catálogo de códigos postales. | Catálogo de Códigos Postales (servicio externo/interno) | 28001 |
| valorBien | number | yes | 0 | Valor numérico positivo; hasta dos decimales; no debe exceder el límite máximo configurado. | N/A | 150000.50 |
| direccion | string | yes | N/A | Máximo 255 caracteres. | N/A | Calle Mayor 123, 1º A |
| usoUbicacion | string | yes | N/A | Debe ser uno de los valores definidos en el catálogo. | Catálogo de Usos (ej. Residencial, Comercial, Industrial) | Residencial |
| tipoBien | string | yes | N/A | Debe ser uno de los valores definidos en el catálogo. | Catálogo de Tipos de Bien (ej. Vivienda, Oficina, Nave Industrial) | Vivienda |


**BR-001:** Validación de Existencia de Código Postal
- Description: El código postal ingresado por el usuario debe ser un código postal geográficamente válido y existente.
- Trigger: Al intentar guardar la ubicación de riesgo o al perder el foco del campo código postal.
- Logic: `IF codigoPostal NOT IN catalogoDeCodigosPostales THEN ERROR("Código postal inexistente")`
- Implementation: Módulo de validación de datos de ubicación (backend), utilizando el servicio de validación de código postal (HU-009).
- Exception: N/A

**BR-002:** Límite de Valor del Bien
- Description: El valor del bien asegurado no debe exceder un umbral máximo predefinido por la política de la empresa. Este umbral puede ser configurable.
- Trigger: Al intentar guardar la ubicación de riesgo.
- Logic: `IF valorBien > limiteMaximoConfigurable THEN WARNING/ERROR("El valor del bien excede el límite")`
- Implementation: Módulo de validación de datos de ubicación (backend).
- Exception: La acción (advertencia vs. error) puede variar según el tipo de bien o el perfil de riesgo.

**BR-003:** Campos Obligatorios
- Description: Ciertos campos son obligatorios para la creación o edición de una ubicación de riesgo y no pueden estar vacíos o nulos.
- Trigger: Al intentar guardar la ubicación de riesgo.
- Logic: `IF campo IS NULL OR IS_EMPTY THEN ERROR("El campo [Nombre del Campo] es obligatorio")` (Aplicado a dirección, usoUbicacion, tipoBien, etc.)
- Implementation: Validaciones tanto en el frontend como en el backend.
- Exception: N/A

## 16. Technical Notes and Risks
**Risks:**
1.  **Complejidad en la configuración de reglas de validación:**
    *   Description: La implementación de un motor de reglas de validación altamente configurable y escalable (como se indica en las notas de implementación) puede introducir una complejidad significativa y requerir un tiempo de desarrollo considerable.
    *   Impact: Retrasos en la entrega, mayor costo de mantenimiento y posible sobreingeniería si la configuración dinámica no es estrictamente necesaria en el MVP.
    *   Probability: Media.
    *   Mitigation: Priorizar las reglas de validación más críticas y hardcodearlas inicialmente, evolucionando hacia un sistema configurable si el valor de negocio y el tiempo lo justifican. Evaluar el uso de frameworks de reglas de negocio (BRMS) si el alcance de la configuración es amplio.
2.  **Rendimiento y disponibilidad del servicio de validación de código postal:**
    *   Description: Si el servicio externo o interno de validación de códigos postales (dependencia de HU-009) es lento o inestable, afectará directamente la experiencia del usuario y la capacidad de guardar ubicaciones.
    *   Impact: Baja usabilidad, errores frecuentes al intentar guardar, frustración del usuario, posibles cuellos de botella en la aplicación.
    *   Probability: Media.
    *   Mitigation: Implementar caché para códigos postales consultados frecuentemente. Diseñar el sistema de validación con tolerancia a fallos (circuit breaker, reintentos) y un manejo de errores elegante en caso de indisponibilidad del servicio.
**Technical Debt:** N/A (Se llenará por el equipo operativo según el alcance y el MVP)

## 17. Criticality
**Criticality Level:** Alta
**Justification:** Esta historia es fundamental para garantizar la calidad, fiabilidad y consistencia de los datos de riesgo, lo cual es crítico para cualquier sistema de seguros o gestión de riesgos. Datos incorrectos pueden llevar a cálculos de primas erróneos, decisiones de negocio equivocadas, incumplimiento normativo y pérdidas financieras.
**Feature Impact:** Sin una validación adecuada, la funcionalidad de "Gestión Dinámica de Ubicaciones de Riesgo" (FT-002) sería inestable y los datos almacenados no serían confiables. Esto impactaría negativamente a todas las funcionalidades downstream que dependen de esta información (ej. cálculo de primas, emisión de pólizas, análisis de riesgo).
**Critical Dependencies:** Todas las historias de usuario y funcionalidades que consumen datos de ubicación de riesgo.
**Recommended Priority:** Sprint actual (dada la prioridad "Alta" y su papel como habilitador crítico para otras funcionalidades).
