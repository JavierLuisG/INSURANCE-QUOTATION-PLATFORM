## 3. User Story
Como **usuario del sistema de gestión de cotizaciones**,
Quiero **permitir la actualización parcial de campos de la cotización sin afectar otros datos**,
Para **optimizar las operaciones de guardado y reducir la carga de datos**.

## 4. Functional Description
**Description:** Esta historia de usuario implementa la capacidad de modificar selectivamente uno o más campos de una cotización existente. El sistema recibirá una solicitud de actualización que contendrá solo los campos a modificar. Se asegurará que únicamente estos campos sean actualizados en la base de datos, manteniendo intactos todos los demás datos de la cotización. Adicionalmente, se gestionará la actualización automática de los metadatos `fechaUltimaActualizacion` y `version` con cada operación de guardado parcial exitosa, basándose en la funcionalidad de HU-149.
**Flow:** [HU-XXX (Obtener Detalle de Cotización)] → [HU-152 (Actualización Parcial de Cotización)] → [HU-XXX (Visualizar Cotización Actualizada)]

## 6. Acceptance Criteria
### AC-001: Actualización selectiva de campos de cotización
**Description:** Valida que solo los campos proporcionados en la solicitud de actualización parcial se modifiquen en la base de datos, dejando los demás campos de la cotización intactos.

```gherkin
Scenario: Actualizar solo el estado de una cotización
  Given una cotización existente con ID "COT-001" y los campos { "nombre": "Cotización de Prueba", "estado": "Borrador", "monto": 1000.00 }
  When el usuario envía una solicitud de actualización parcial para la cotización "COT-001" con { "estado": "Aprobado" }
  Then la cotización "COT-001" en la base de datos debe tener los campos { "nombre": "Cotización de Prueba", "estado": "Aprobado", "monto": 1000.00 }
  And el campo "nombre" no debe haber sido modificado
  And el campo "monto" no debe haber sido modificado
```

### AC-002: Actualización de metadatos de control (`fechaUltimaActualizacion` y `version`)
**Description:** Asegura que, tras una actualización parcial exitosa, los campos `fechaUltimaActualizacion` y `version` de la cotización se actualicen automáticamente.

```gherkin
Scenario: Metadatos actualizados tras una modificación parcial exitosa
  Given una cotización existente con ID "COT-002" con "fechaUltimaActualizacion" = "2026-04-20T10:00:00Z" y "version" = 1
  When se realiza una actualización parcial exitosa en la cotización "COT-002" modificando el campo "estado"
  Then el campo "fechaUltimaActualizacion" de la cotización "COT-002" debe ser posterior a "2026-04-20T10:00:00Z" (fecha y hora actual)
  And el campo "version" de la cotización "COT-002" debe ser 2
```

### AC-003: Integridad de datos para campos no modificados
**Description:** Verifica que cualquier campo de la cotización que no se incluya explícitamente en la solicitud de actualización parcial mantenga su valor original sin alteración.

```gherkin
Scenario: Los campos no especificados permanecen sin cambios
  Given una cotización existente con ID "COT-003" y campos { "cliente": "Empresa Alfa", "referencia": "REF-ABC", "descuento": 0.05 }
  When el usuario envía una solicitud de actualización parcial para la cotización "COT-003" con { "descuento": 0.10 }
  Then el campo "cliente" de la cotización "COT-003" debe seguir siendo "Empresa Alfa"
  And el campo "referencia" de la cotización "COT-003" debe seguir siendo "REF-ABC"
```

**BR-001: Actualización de `fechaUltimaActualizacion`**
- Description: Cada vez que se realiza una operación de actualización exitosa sobre una cotización (parcial o completa), el campo `fechaUltimaActualizacion` debe ser actualizado a la fecha y hora actual del sistema.
- Trigger: Post-persistencia de cualquier cambio en una cotización.
- Logic: `cotizacion.fechaUltimaActualizacion = DateTime.now();`
- Implementation: Capa de persistencia o servicio de dominio de cotizaciones.
- Exception: N/A

**BR-002: Incremento de `version`**
- Description: Tras cualquier actualización exitosa de una cotización, el campo `version` debe incrementarse en 1. Esto se basa en la funcionalidad provista por HU-149.
- Trigger: Post-persistencia de cualquier cambio en una cotización.
- Logic: `cotizacion.version = cotizacion.version + 1;`
- Implementation: Servicio de dominio de cotizaciones, posiblemente orquestado por la capa de persistencia.
- Exception: N/A

## 11. Architecture and Technical Dependencies
- **Backend (API de Actualización Parcial):** Se implementará un endpoint RESTful (ej. `PATCH /api/v1/cotizaciones/{id}`) que acepte un DTO específico para actualizaciones parciales (o un `Map<String, Object>`) y lo mapee a la entidad de cotización.

## 13. Edge Cases and Exceptions
### Case 1: Cotización no encontrada
```gherkin
Scenario: Intento de actualización de una cotización inexistente
  Given una solicitud de actualización parcial para la cotización con ID "COT-999"
  When el sistema intenta procesar la solicitud
  Then el sistema debe responder con un código de estado HTTP 404 Not Found
  And un mensaje de error indicando "Cotización con ID COT-999 no encontrada"
```

### Case 2: Campos de actualización inválidos o no permitidos
```gherkin
Scenario: Intento de actualización con un campo no válido o protegido
  Given una cotización existente con ID "COT-001"
  When el usuario envía una solicitud de actualización parcial para "COT-001" con { "idCotizacion": "NUEVO-ID", "campoInvalido": "valor" }
  Then el sistema debe responder con un código de estado HTTP 400 Bad Request
  And un mensaje de error detallando que "idCotizacion" no puede ser modificado y "campoInvalido" no existe
```

### Case 3: Error de concurrencia
```gherkin
Scenario: Actualización concurrente de la misma cotización
  Given la cotización "COT-001" tiene "version" = 1
  And el Usuario A inicia una actualización para "COT-001"
  And el Usuario B inicia una actualización para "COT-001"
  When el Usuario A completa su actualización (incrementando la versión a 2)
  And el Usuario B intenta completar su actualización
  Then el sistema debe responder al Usuario B con un código de estado HTTP 409 Conflict
  And un mensaje de error indicando "La cotización ha sido modificada por otro usuario. Por favor, recargue y vuelva a intentar."
```

## 16. Technical Notes and Risks
**Risks:**
1.  **Complejidad del mapeo de actualización parcial:**
    - Description: La implementación de la lógica para aplicar solo los campos modificados puede ser compleja, especialmente con objetos anidados o colecciones, y si no se gestiona correctamente, puede llevar a sobrescribir datos no deseados o a un rendimiento deficiente.
    - Impact: Errores en la actualización de datos, inconsistencia de datos, mayor tiempo de desarrollo y depuración.
    - Probability: Media
    - Mitigation: Utilizar librerías de mapeo bien establecidas (ej. MapStruct, ModelMapper configurado para `null` o `ignore`), definir DTOs de entrada específicos para el `PATCH`, y realizar pruebas exhaustivas.
2.  **Manejo de concurrencia y versiones:**
    - Description: Aunque HU-149 provee la versión, la lógica para usarla en un mecanismo de bloqueo optimista debe implementarse correctamente en esta historia para evitar la pérdida de actualizaciones concurrentes.
    - Impact: Pérdida de datos, cotizaciones con información incorrecta debido a sobrescrituras.
    - Probability: Media
    - Mitigation: Implementar bloqueo optimista utilizando el campo `version` (ej. `WHERE id = ? AND version = ?`), y manejar el `409 Conflict` en el cliente.

**Technical Debt:** No se identifica deuda técnica inicial para esta historia. Se priorizará una implementación robusta de mapeo y concurrencia.

## 17. Criticality
**Criticality Level:** Media
**Justification:** Esta funcionalidad mejora significativamente la eficiencia operativa y la experiencia del usuario al editar cotizaciones, reduciendo la fricción y el riesgo de errores al enviar datos redundantes. No es un bloqueador para el flujo principal de creación/consulta, pero es un optimizador clave.
**Feature Impact:** La no implementación o fallo de esta historia significaría que todas las actualizaciones de cotizaciones requerirían el envío de la cotización completa, lo que podría generar mayor carga de red, latencia y un mayor riesgo de errores por sobrescritura accidental de campos.
**Critical Dependencies:** La correcta implementación de HU-149 (Incrementar Versión) es esencial para el control de versiones y la gestión de concurrencia en las actualizaciones.
**Recommended Priority:** Sprint actual o próximo.

## 18. Identified Assumptions
1.  **Existencia y funcionalidad de HU-149:**
    - Description: Se asume que la historia HU-149, que define el incremento automático del campo `version` en cada edición, estará implementada y funcionando correctamente antes o en conjunto con esta historia.
    - Impact if false: El control de versiones de las cotizaciones no funcionará, afectando la trazabilidad y el manejo de concurrencia.
    - Requires validation from: Equipo de Desarrollo, Product Owner.
2.  **Definición de campos actualizables y no actualizables:**
    - Description: Se asume que existe una lista clara y acordada de qué campos de la entidad 'Cotización' pueden ser modificados a través de la actualización parcial y cuáles son de solo lectura o requieren un proceso de actualización diferente.
    - Impact if false: Riesgo de permitir la modificación de campos sensibles o críticos que no deberían ser alterados directamente, o de rechazar actualizaciones válidas.
    - Requires validation from: Product Owner, Arquitectos de Solución.
3.  **Mecanismo de identificación única de cotizaciones:**
    - Description: Se asume que cada cotización tiene un identificador único y estable (ej. UUID) que permite al sistema localizar y actualizar la cotización específica de manera fiable.
    - Impact if false: Imposibilidad de identificar la cotización a actualizar o riesgo de actualizar cotizaciones incorrectas.
    - Requires validation from: Equipo de Desarrollo.
