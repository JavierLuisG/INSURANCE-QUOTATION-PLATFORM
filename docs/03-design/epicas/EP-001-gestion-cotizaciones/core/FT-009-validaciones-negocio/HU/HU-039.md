## 3. User Story
Como un **usuario**,
quiero que **los datos generales de la cotización se validen según reglas de negocio**,
para que **se asegure la calidad de la información**.

## 4. Functional Description
**Description:** Esta historia de usuario describe la funcionalidad para validar los datos generales de una cotización introducidos por el usuario. El sistema debe aplicar una serie de reglas de negocio para verificar la corrección y completitud de la información, como el formato del RFC, la coherencia de las fechas de vigencia y la presencia de datos en campos obligatorios. En caso de que alguna validación falle, el sistema debe informar al usuario con un mensaje de error claro y descriptivo.
**Flow:** [FT-001: Creación y Edición de Datos Generales de la Cotización] → [HU-039: Validar datos generales de la cotización] → [HU-XXX: Guardar Cotización (si la validación es exitosa)]

## 6. Acceptance Criteria (3-5 criteria)
### AC-001: Validación de formato de RFC
**Description:** El sistema debe verificar que el RFC introducido por el usuario cumpla con un formato válido.
```gherkin
Scenario: Intento de guardar con RFC de formato incorrecto
  Given que estoy en el formulario de creación/edición de cotizaciones
  And he introducido un RFC con formato incorrecto (ej. "RFC123")
  When intento guardar la cotización
  Then el sistema muestra un mensaje de error de validación indicando que el formato del RFC es incorrecto.
```

### AC-002: Validación de fechas de vigencia
**Description:** El sistema debe asegurar que la fecha de fin de vigencia no sea anterior a la fecha de inicio de vigencia.
```gherkin
Scenario: Intento de guardar con fecha de fin de vigencia anterior a la de inicio
  Given que estoy en el formulario de creación/edición de cotizaciones
  And he introducido una fecha de inicio de vigencia (ej. "2026-05-01")
  And he introducido una fecha de fin de vigencia anterior a la de inicio (ej. "2026-04-30")
  When intento guardar la cotización
  Then el sistema muestra un mensaje de error indicando que la fecha de fin de vigencia no puede ser anterior a la fecha de inicio.
```

### AC-003: Validación de campos obligatorios
**Description:** El sistema debe verificar que todos los campos marcados como obligatorios, como el "Nombre Asegurado", contengan información.
```gherkin
Scenario: Intento de guardar con un campo obligatorio vacío
  Given que estoy en el formulario de creación/edición de cotizaciones
  And el campo "Nombre Asegurado" es obligatorio y está vacío
  And el resto de los campos son válidos
  When intento guardar la cotización
  Then el sistema me indica que el campo "Nombre Asegurado" es obligatorio y debe ser completado.
```

**BR-001:** Validación de formato de RFC
- Description: Asegura que el RFC introducido cumpla con el formato estándar requerido.
- Trigger: Al intentar guardar la cotización.
- Logic: El campo `rfc_asegurado` debe coincidir con la expresión regular `^[A-Z&Ñ]{3,4}[0-9]{2}(0[1-9]|1[0-2])(0[1-9]|1[0-9]|2[0-9]|3[0-1])[A-Z0-9]{2}[0-9A]$`.
- Implementation: Módulo de validación de datos generales (backend) y validaciones en el formulario (frontend).
- Exception: N/A

**BR-002:** Validación de secuencia de fechas de vigencia
- Description: Asegura que la fecha de fin de vigencia no sea anterior a la fecha de inicio de vigencia.
- Trigger: Al intentar guardar la cotización.
- Logic: `fecha_fin_vigencia` >= `fecha_inicio_vigencia`.
- Implementation: Módulo de validación de datos generales (backend) y validaciones en el formulario (frontend).
- Exception: N/A

**BR-003:** Validación de campos obligatorios
- Description: Asegura que todos los campos marcados como obligatorios contengan un valor.
- Trigger: Al intentar guardar la cotización.
- Logic: Para cada campo marcado como `required: yes`, su valor no debe ser nulo o vacío.
- Implementation: Módulo de validación de datos generales (backend) y validaciones en el formulario (frontend).

## 16. Technical Notes and Risks
**Risks:**
1.  **Consistencia de Validaciones (Alta, Media, Mitigación: Pruebas automatizadas y revisión de código)**:
    -   Description: Riesgo de que las validaciones implementadas en el frontend no sean idénticas o consistentes con las del backend, llevando a una experiencia de usuario inconsistente o a fallos de seguridad.
    -   Impact: Inconsistencia en la experiencia del usuario, posibles vulnerabilidades, frustración del usuario.
    -   Probability: Media
    -   Mitigation: Reutilizar lógica de validación (si es posible), definir un contrato de validación claro, implementar pruebas de integración exhaustivas y end-to-end.
2.  **Claridad de Mensajes de Error (Media, Baja, Mitigación: Revisión UX y pruebas de usuario)**:
    -   Description: Los mensajes de error podrían no ser lo suficientemente claros o útiles para que el usuario corrija los datos.
    -   Impact: Frustración del usuario, aumento de llamadas a soporte.
    -   Probability: Baja (se indicó en las notas de implementación)
    -   Mitigation: Realizar pruebas de usuario, obtener feedback de UX, estandarizar mensajes de error.

## 17. Criticality
**Criticality Level:** Alta
**Justification:** La historia es de alta prioridad según el usuario. Es fundamental para garantizar la integridad y calidad de los datos de las cotizaciones, lo cual es crítico para el negocio.
**Feature Impact:** La no implementación o fallo de esta historia resultaría en la posibilidad de guardar cotizaciones con datos incorrectos o inválidos, lo que podría llevar a errores en la emisión de pólizas, problemas legales o financieros, y una baja confianza en el sistema.
**Critical Dependencies:** La funcionalidad de "Creación y Edición de Datos Generales de la Cotización" (FT-001) depende directamente de estas validaciones para su correcto funcionamiento.
**Recommended Priority:** Sprint actual / Inmediata

## 18. Identified Assumptions
1.  **Formato de RFC (RFC del SAT)**
    -   Description: Se asume que el formato de RFC a validar es el estándar definido por el SAT en México para personas físicas y morales.
    -   Impact if false: Las validaciones podrían rechazar RFCs válidos o aceptar inválidos, causando problemas con el registro de clientes.
    -   Requires validation from: Equipo de Negocio / Legal.
2.  **Lista de Campos Obligatorios**
    -   Description: Se asume que la lista de campos obligatorios, además del "Nombre Asegurado", ya está definida y es conocida.
    -   Impact if false: Se podrían guardar cotizaciones incompletas o se solicitarían campos no necesarios, afectando la usabilidad.
    -   Requires validation from: Equipo de Negocio / Product Owner.
