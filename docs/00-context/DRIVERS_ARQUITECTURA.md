# Drivers de Arquitectura

## Requisitos Funcionales Arquitectónicamente Relevantes


| id | nombre | descripcion | justificacion |
|---|---|---|---|
| RFR-001 | Gestión de Folios con Idempotencia | La solución debe permitir la captura y gestión de folios únicos para cada cotización, asegurando la idempotencia en su creación para evitar duplicados. | Crítico para la unicidad del identificador de cotización y la integridad del sistema. Requiere una lógica de backend robusta, posiblemente con mecanismos de bloqueo o control transaccional para evitar condiciones de carrera. |
| RFR-002 | Gestión Dinámica de Ubicaciones de Riesgo | El sistema debe permitir el registro, consulta, edición y eliminación de hasta 10 ubicaciones de riesgo por cotización, cada una con sus configuraciones y datos específicos. | Impacta el modelo de datos (estructura de datos anidadas o colecciones relacionadas), el diseño de la interfaz de usuario (patrón maestro-detalle o pestañas) y la lógica de persistencia para manejar agregados complejos. |
| RFR-003 | Cálculo de Prima Neta y Comercial Detallado | La solución debe calcular la prima neta, la prima comercial y el desglose de primas por cada ubicación de riesgo, aplicando reglas de negocio y factores técnicos. | Es la funcionalidad central del negocio. Requiere un motor de cálculo performante, preciso y trazable, con acceso eficiente a datos de referencia (tarifas y catálogos) y lógica de persistencia transaccional para los resultados financieros. |
| RFR-004 | Integración con Servicios de Referencia (Plataforma-core-ohs) | El sistema debe consumir o simular servicios externos para obtener catálogos (suscriptores, agentes, giros, CP, clasificación de riesgo, garantías) y tarifas (incendio, CAT, FHM, equipo electrónico). | Es una dependencia externa crítica para la funcionalidad y precisión del cálculo. Impacta la resiliencia del sistema (manejo de fallos, latencia), la estrategia de caché y el diseño de los contratos de integración. |
| RFR-005 | Persistencia de Cotizaciones y Parámetros en MongoDB | La información de cotizaciones, parámetros de cálculo y tarifas debe persistirse en colecciones específicas, preferentemente en MongoDB. | Define la tecnología de persistencia principal, impactando el diseño del esquema de datos, las estrategias de indexación, la gestión de la atomicidad de las operaciones y la escalabilidad del almacenamiento. |
| RFR-006 | Gestión de Concurrencia con Versionado Optimista | El sistema debe manejar actualizaciones concurrentes de cotizaciones mediante un mecanismo de versionado optimista, incrementando un campo de versión y actualizando metadatos en cada edición. | Esencial para la integridad de los datos, evitando la pérdida de información en entornos multiusuario. Impacta la capa de persistencia, la lógica de negocio del backend y la experiencia de usuario en caso de conflicto. |
| RFR-007 | Gestión del Ciclo de Vida de la Cotización | La cotización debe transitar por diferentes estados (Borrador, Calculada, Aprobada, Rechazada, Emitida) con transiciones automáticas y manuales, y validaciones asociadas. | Impacta el modelo de datos para incluir el estado y la lógica de negocio para gestionar las transiciones, asegurando que las acciones solo se permitan en los estados válidos. |

## Preocupaciones Arquitectónicas


| id | concerns | razonamiento |
|---|---|---|
| PAC-001 | Complejidad del Motor de Cálculo de Primas | La ausencia de una fórmula actuarial real y la necesidad de implementar una lógica 'consistente, trazable y documentada' con factores técnicos y reglas de negocio, introduce el riesgo de errores y dificultad en la precisión, especialmente con hasta 10 ubicaciones por cotización. Se requiere un diseño modular y altamente testeable. |
| PAC-002 | Dependencia Crítica del Servicio Externo (Plataforma-core-ohs) | El cotizador depende fuertemente de un servicio externo (simulado o real) para catálogos y tarifas. Su inestabilidad, latencia o fallo podría paralizar el sistema o generar datos inconsistentes, impactando directamente la fiabilidad y el rendimiento. La simulación debe ser muy robusta para no introducir problemas ocultos. |
| PAC-003 | Manejo de Concurrencia y Consistencia de Datos | La edición concurrente de cotizaciones por múltiples usuarios, combinada con la necesidad de versionado optimista y persistencia atómica en MongoDB (que no tiene transacciones ACID multi-documento por defecto), plantea un desafío significativo para asegurar la integridad de los datos y evitar la pérdida de información. |
| PAC-004 | Rendimiento y Escalabilidad bajo Carga | Cumplir con los tiempos de respuesta (<500ms UI, <1.5s CRUD, <3s cálculo para 10 ubicaciones) y soportar hasta 500 usuarios concurrentes requiere una arquitectura escalable, optimización de consultas, uso de caché y un diseño eficiente tanto en el frontend como en el backend. La agregación de datos de múltiples ubicaciones para el cálculo total es un punto crítico. |
| PAC-005 | Seguridad de Datos Sensibles | El manejo de información de asegurados y detalles de ubicaciones de riesgo requiere cifrado en tránsito (TLS 1.2+) y en reposo (AES-256), además de mecanismos robustos de autenticación y autorización. Un fallo en cualquiera de estos puntos podría tener graves consecuencias legales y de reputación. |
| PAC-006 | Gestión de Datos Maestros y Caché | La necesidad de acceder a catálogos y tarifas actualizadas de un servicio externo y la implementación de una estrategia de caché (TTL, actualización programada) para optimizar el rendimiento, introduce complejidad en la gestión de la frescura y consistencia de los datos entre la fuente, la caché y el sistema. |
| PAC-007 | Garantizar la Trazabilidad y Auditabilidad | La exigencia de una lógica de cálculo trazable, registro de parámetros utilizados y versionado de cotizaciones para auditoría, implica un diseño cuidadoso de la persistencia y los metadatos para no sobrecargar el modelo de datos principal ni impactar el rendimiento. |


## Supuestos

*   **Contratos de `Plataforma-core-ohs` Estables**: Se asume que los contratos de la API REST del servicio `Plataforma-core-ohs` (simulado o real) para catálogos y tarifas son estables y bien definidos, lo que permitirá diseñar las integraciones y el mock server de forma precisa.
*   **Fórmulas de Cálculo Simplificadas Suficientes**: Se asume que las 'fórmulas simplificadas y documentadas' para el cálculo de primas serán suficientes para el alcance del proyecto y no requerirán la implementación de una lógica actuarial compleja no especificada.
*   **Límite de Ubicaciones Fijo**: Se asume que el límite de 10 ubicaciones por cotización es una restricción fija y adecuada para las necesidades actuales del negocio.
*   **Disponibilidad de Herramientas de Desarrollo y Pruebas**: Se asume que las herramientas necesarias para el desarrollo (IDE, gestores de dependencias) y las pruebas (herramientas de cobertura como JaCoCo/Istanbul, herramientas de carga como JMeter/Gatling) estarán disponibles y configuradas.
*   **Autenticación y Autorización Interna Simplificada**: Se asume que la autenticación y autorización se basarán en un modelo interno de usuario/contraseña y roles, sin necesidad de integración con sistemas de identidad corporativos más complejos (ej. SSO, LDAP) en esta fase.
*   **Datos de Prueba Representativos para Mock**: Se asume que los datos de prueba utilizados para poblar el mock server de `Plataforma-core-ohs` serán representativos de los datos reales, permitiendo un desarrollo y pruebas realistas.

## Restricciones Técnicas


| id | restriccion | razonamiento | flexibilidad | alternativa | interesado |
|---|---|---|---|---|---|
| RT-001 | Persistencia de Cotización como Agregado Principal | La cotización debe ser tratada como una unidad transaccional y de consistencia, con sus ubicaciones y coberturas anidadas o fuertemente relacionadas. | Baja | Modelos de datos desagregados con consistencia eventual, pero esto aumentaría la complejidad de gestión de integridad. | Desarrollador, Analista Funcional |
| RT-002 | Escrituras por Actualización Parcial | Las operaciones de modificación de cotizaciones y ubicaciones deben permitir actualizar solo los campos modificados para optimizar el rendimiento y el uso de la red. | Media | Actualizaciones completas de documentos, lo que podría generar mayor tráfico de red y menor eficiencia. | Desarrollador |
| RT-003 | Versionado Optimista | Todas las ediciones de cotizaciones deben implementar un mecanismo de versionado optimista para prevenir conflictos de concurrencia y asegurar la integridad de los datos. | Baja | Bloqueo pesimista, pero esto impactaría negativamente la escalabilidad y experiencia de usuario. | Desarrollador, Evaluador Técnico |
| RT-004 | Cobertura de Pruebas Unitarias Mínima (80%) | El código del backend y frontend debe alcanzar una cobertura mínima del 80% en pruebas unitarias para garantizar la calidad y facilitar el mantenimiento. | Baja | Menor cobertura de pruebas, pero esto aumentaría el riesgo de defectos y el costo de mantenimiento. | Desarrollador, Evaluador Técnico |
| RT-005 | 3 Flujos Críticos con Pruebas Automatizadas | Se deben implementar pruebas automatizadas para al menos 3 flujos de negocio críticos para validar la funcionalidad end-to-end y prevenir regresiones. | Baja | Solo pruebas manuales o menos flujos automatizados, lo que aumentaría el riesgo de regresiones y el tiempo de QA. | Desarrollador, Evaluador Técnico |
| RT-006 | Uso de Metodología ASSD | La documentación y los entregables deben seguir la metodología ASSD para asegurar un estándar de calidad y claridad en la arquitectura. | Baja | Documentación ad-hoc, lo que generaría inconsistencias y dificultaría la comprensión del sistema. | Analista Funcional, Desarrollador, Evaluador Técnico |
| RT-007 | Persistencia en MongoDB | La persistencia de la información de cotizaciones se realizará preferentemente en MongoDB, lo que implica un diseño de esquema NoSQL. | Media | Uso de otra base de datos NoSQL o una relacional, pero se desviaría de la preferencia establecida, requiriendo justificación. | Desarrollador, Evaluador Técnico |
| RT-008 | Cifrado con TLS 1.2+ en Tránsito | Todas las comunicaciones de datos sensibles deben utilizar TLS 1.2 o superior para proteger la confidencialidad e integridad. | Baja | Protocolos de cifrado más débiles, lo que comprometería la seguridad y el cumplimiento normativo. | Desarrollador, Equipo de Seguridad |
| RT-009 | Cifrado AES-256 en Reposo | Los datos sensibles almacenados en la base de datos deben ser cifrados utilizando algoritmos estándar de la industria como AES-256. | Baja | Algoritmos de cifrado menos robustos o ausencia de cifrado, lo que expondría datos críticos. | Desarrollador, Equipo de Seguridad |


## Fuera de Alcance Técnico


| id | descripcion_exclusion | justificacion | implicacion |
|---|---|---|---|
| OOS-001 | Replicación exacta de una fórmula actuarial real | El proyecto se centrará en una lógica de cálculo simplificada y documentada, no en la implementación de una fórmula actuarial compleja y real, si no fue entregada. | Los resultados de la prima serán representativos y consistentes, pero no necesariamente idénticos a los de un sistema actuarial real. Se prioriza la trazabilidad y la consistencia sobre la exactitud actuarial compleja. |
| OOS-002 | Implementación de un servicio real de 'Plataforma-core-ohs' | El alcance explícitamente permite y fomenta el uso de un stub, mock server o fixtures versionadas para simular este servicio externo, en lugar de construirlo o integrarse a uno real en esta fase. | El desarrollo no dependerá de la disponibilidad o estado de un servicio externo real, pero la simulación debe ser suficientemente robusta para replicar los contratos y comportamientos esperados, incluyendo escenarios de error. |
| OOS-003 | Desarrollo de un pipeline de CI o 'docker-compose.yml' como entregables obligatorios | Estas herramientas son opcionales y no se consideran entregables mandatorios del proyecto, aunque pueden usarse internamente para facilitar el desarrollo. | La ausencia de un pipeline de CI/CD formal puede requerir procesos de despliegue manuales o menos automatizados. La falta de un docker-compose.yml obligatorio implica que el entorno local de desarrollo puede variar entre los participantes, aunque se espera que la solución sea ejecutable. |
| OOS-004 | Cobertura de pruebas completa (100%) | El proyecto establece un requisito mínimo del 80% de cobertura en pruebas unitarias y 3 flujos críticos automatizados, no una cobertura exhaustiva del 100%. | Algunas partes del código o flujos menos críticos podrían no tener cobertura de pruebas automatizadas, aumentando un riesgo marginal de defectos en esas áreas, pero permitiendo enfocar los esfuerzos de prueba en lo más relevante. |
| OOS-005 | Integración con sistemas de identidad corporativos (SSO, LDAP) | El RNF-007 especifica 'autenticación interna con gestión de usuarios propia basada en credenciales', lo que excluye integraciones más complejas con sistemas de Single Sign-On o directorios empresariales. | El sistema tendrá su propio almacén de usuarios y credenciales, lo que podría requerir una gestión manual de usuarios y no se beneficiará de la experiencia de inicio de sesión unificada de otros sistemas. Esto simplifica el alcance inicial de seguridad. |
