## 2. Enabled Capability
**CAP-138:** Validación Pre-Cálculo de Prima
**Business Value:** Asegurar la integridad de los datos de las cotizaciones, evitar cálculos erróneos, reducir retrabajos y mejorar la experiencia del usuario al proporcionar retroalimentación temprana sobre datos inválidos.
**Requires:** CAP-169 (Prevenir Ejecución de Cálculo cuando no hay ubicaciones válidas) - Esta historia se basa en la capacidad de *detener* el cálculo, que es la esencia de CAP-169.

**Orchestrates:** Motor de Validación de Reglas de Negocio (BRMS)

## 3. User Story
Como un **usuario**,
Quiero que el sistema me impida calcular una cotización si no existe ninguna ubicación calculable o si hay coberturas con parámetros erróneos,
Para evitar cálculos erróneos y asegurar la calidad de los datos.

## 4. Functional Description
**Description:** Esta historia de usuario describe el comportamiento del sistema para validar las condiciones de una cotización antes de proceder con el cálculo de la prima. El sistema debe verificar que al menos una de las ubicaciones asociadas a la cotización tenga un `estadoValidacion` de `COMPLETA`. Además, debe identificar si existen coberturas no definidas o con parámetros erróneos. Si no hay ninguna ubicación en estado `COMPLETA`, el cálculo no se iniciará y se mostrarán los errores. Si hay ubicaciones válidas pero también existen coberturas o parámetros inválidos, el cálculo procederá solo para las ubicaciones válidas, y se notificarán los errores de las coberturas/parámetros. El objetivo es guiar al usuario a corregir los datos antes de obtener un cálculo final, o permitir un cálculo parcial si es posible.
**Flow:** [Configuración de Cotización/Ubicaciones] → [Esta historia (Validación Pre-Cálculo)] → [Cálculo de Prima (si es válido) / Mostrar Errores (si es inválido)]

## 5. Expected Results


| element | description |
|---|---|
| Data | Si la validación falla (no hay ubicaciones válidas), no se crea ni actualiza ningún dato de prima calculada. Los estados de validación de ubicaciones y coberturas no cambian por esta acción. |
| States | Si la validación falla, el estado de la cotización permanece en 'Pendiente de Cálculo' o similar. Si el cálculo procede (parcial o totalmente), el estado puede transicionar a 'En Cálculo' o 'Cálculo Parcial'. |
| Notifications | Mensajes de error específicos en la interfaz de usuario indicando qué ubicaciones o coberturas son inválidas y por qué. Ej: 'No se puede calcular la prima. Revise la validación de las ubicaciones.', 'Cobertura [Nombre] tiene parámetros inválidos.' |
| Integrations | El Motor de Cálculo de Prima NO es invocado si no hay ubicaciones con 'estadoValidacion: COMPLETA'. El Motor de Validación de Reglas de Negocio (BRMS) es invocado para verificar las condiciones. |
| Kafka | No se publican eventos relacionados con el inicio del cálculo de prima si la validación falla completamente. Si el cálculo procede parcialmente, se publican eventos para las ubicaciones válidas. |
| Logs | Se registran logs de nivel 'INFO' para el inicio del proceso de validación y de nivel 'WARN' o 'ERROR' si se detectan fallos de validación, detallando la razón y las entidades afectadas. |
| UI | El botón de 'Calcular Prima' puede estar deshabilitado o mostrar un tooltip explicativo si no hay ubicaciones válidas. Al intentar calcular, se muestra un modal o un banner con los mensajes de error/advertencia relevantes, resaltando los campos inválidos si aplica. |


## 6. Acceptance Criteria
### AC-001: Prevenir cálculo si no hay ubicaciones con estado `COMPLETA`
**Description:** Valida que el sistema bloquea el cálculo de la prima si ninguna de las ubicaciones de la cotización ha completado su proceso de validación.

```gherkin
Scenario: No hay ubicaciones válidas para calcular la prima
  Given una cotización con ubicaciones donde ninguna tiene "estadoValidacion: COMPLETA"
  And el usuario intenta calcular la prima
  When el sistema valida las ubicaciones
  Then el sistema muestra los errores de validación de las ubicaciones
  And el sistema no invoca el motor de cálculo de prima
```

### AC-002: Proceder con cálculo parcial si hay ubicaciones válidas y coberturas inválidas
**Description:** Verifica que el sistema permite calcular la prima para las ubicaciones que sí están válidas, incluso si existen coberturas con parámetros erróneos o no definidas, notificando al usuario sobre estas últimas.

```gherkin
Scenario: Algunas ubicaciones son válidas, pero hay coberturas no definidas o con parámetros erróneos
  Given una cotización con al menos una ubicación con "estadoValidacion: COMPLETA"
  And la cotización tiene coberturas no definidas o con parámetros erróneos en otras ubicaciones o a nivel global
  When el usuario intenta calcular la prima
  Then el sistema procede con el cálculo de la prima para las ubicaciones válidas
  And el sistema muestra mensajes de advertencia o error sobre las coberturas inválidas
```

### AC-003: Permitir cálculo cuando al menos una ubicación es completamente válida
**Description:** Asegura que el cálculo de la prima se realiza sin impedimentos si al menos una ubicación ha pasado todas sus validaciones.

```gherkin
Scenario: Todas las validaciones son exitosas en al menos una ubicación
  Given una cotización con al menos una ubicación con "estadoValidacion: COMPLETA"
  And no hay impedimentos críticos de validación que bloqueen el cálculo para esta ubicación
  When el usuario intenta calcular la prima
  Then el sistema procede con el cálculo de la prima sin impedimentos
```

**BR-138-001:** Verificación de Ubicaciones Calculables
- Description: Antes de iniciar cualquier cálculo de prima, el sistema debe verificar que al menos una de las ubicaciones de la cotización tiene su `estadoValidacion` establecido en `COMPLETA`.
- Trigger: Intento de cálculo de prima por parte del usuario.
- Logic:
  ```
  IF cotizacion.ubicaciones.ANY(ubicacion => ubicacion.estadoValidacion == "COMPLETA")
    THEN Permitir inicio del proceso de cálculo (total o parcial)
  ELSE
    THEN Impedir cálculo y mostrar error
  ```
- Implementation: Servicio de Validación de Cotizaciones (parte del backend), utilizando el Motor de Validación de Reglas de Negocio.
- Exception: N/A

**BR-138-002:** Verificación de Coberturas y Parámetros
- Description: El sistema debe identificar si existen coberturas no definidas o con parámetros erróneos dentro de la cotización, incluso si hay ubicaciones válidas para el cálculo.
- Trigger: Intento de cálculo de prima por parte del usuario.
- Logic:
  ```
  FOR EACH ubicacion in cotizacion.ubicaciones
    FOR EACH cobertura in ubicacion.coberturas
      IF cobertura.isDefined() AND cobertura.parametrosAreValid()
        THEN Considerar cobertura válida para cálculo en esa ubicación
      ELSE
        THEN Marcar cobertura como inválida y generar advertencia/error
  ```
- Implementation: Servicio de Validación de Cotizaciones (parte del backend), utilizando el Motor de Validación de Reglas de Negocio.
- Exception: N/A

## 10. UX and Navigation Flow
**UX Flow:**
1.  Usuario navega a la pantalla de detalle de una cotización.
2.  Usuario hace clic en el botón "Calcular Prima".
3.  El sistema ejecuta la validación de ubicaciones y coberturas.
4.  **Caso A (No ubicaciones válidas):** Se muestra un modal o un mensaje de error en la pantalla indicando que no se puede proceder y listando las ubicaciones con problemas. El botón "Calcular Prima" permanece en su estado original (no se inicia el cálculo).
5.  **Caso B (Algunas ubicaciones válidas, otras con coberturas/parámetros inválidos):** El cálculo procede para las ubicaciones válidas. Se muestra un mensaje de advertencia o un resumen de errores/advertencias indicando las coberturas o parámetros que no pudieron ser considerados o que necesitan corrección.
6.  **Caso C (Al menos una ubicación completamente válida y sin errores críticos):** El cálculo procede normalmente.
**Messages/Modals:**
*   **Error:** "No se puede calcular la prima. Ninguna de las ubicaciones cumple los requisitos de validación. Revise las ubicaciones con estado 'COMPLETA'."
*   **Advertencia:** "Cálculo realizado. Sin embargo, se encontraron errores en las siguientes coberturas/parámetros: [Detalles]. El cálculo no los ha incluido o puede ser inexacto."
*   **Éxito:** (Si el cálculo procede) "Cálculo de prima iniciado exitosamente."
**Stepper/Breadcrumbs:** N/A (Esta historia es una acción dentro de un paso existente).

## 11. Architecture and Technical Dependencies
-   **Backend Service (Servicio de Cotizaciones):** Orquesta la llamada al motor de validación.
-   **Motor de Validación de Reglas de Negocio (BRMS):** Componente crítico para evaluar las reglas definidas (estado de ubicación, validez de parámetros de cobertura). Debe ser configurable y escalable.
-   **Base de Datos (DB):** Para consultar los estados de validación de ubicaciones y los detalles de las coberturas.
-   **Servicio de Cálculo de Prima:** Es la dependencia que *no* debe ser llamada si la validación falla.
-   **Timeout/Retries:** El BRMS debe tener tiempos de respuesta optimizados para no impactar la UX. No se esperan reintentos para la validación misma, sino una respuesta síncrona.

## 16. Technical Notes and Risks
**Risks:**
1.  **Complejidad del BRMS:** La lógica de validación puede volverse compleja rápidamente.
    -   *Impacto:* Dificultad en mantenimiento, errores en validación.
    -   *Probabilidad:* Media.
    -   *Mitigación:* Definir reglas claras, usar un BRMS robusto, implementar pruebas exhaustivas para cada regla.
2.  **Rendimiento del Servicio de Validación:** Un BRMS lento podría impactar negativamente la experiencia del usuario.
    -   *Impacto:* Tiempos de espera prolongados para el usuario.
    -   *Probabilidad:* Media.
    -   *Mitigación:* Optimizar consultas a BD, asegurar que el BRMS sea eficiente, monitorear latencia y escalar si es necesario.
3.  **Claridad de Mensajes de Error:** Mensajes poco claros pueden frustrar al usuario.
    -   *Impacto:* Mala UX, incremento de tickets de soporte.
    -   *Probabilidad:* Baja (con revisión de UX).
    -   *Mitigación:* Colaboración cercana con UX/Diseño, pruebas de usuario.

**Technical Debt:** La implementación inicial del BRMS podría ser básica (ej. lógica hardcodeada en lugar de un motor de reglas configurable). Se debería planificar una refactorización para un motor de reglas externo si la complejidad aumenta.

## 17. Criticality
**Criticality Level:** Alta
**Justification:** Esta historia es crítica porque impacta directamente la calidad de los datos de las cotizaciones y la confianza del usuario en el sistema de cálculo. Prevenir cálculos erróneos es fundamental para la precisión del negocio y la reputación.
**Feature Impact:** Sin esta validación, la funcionalidad de cálculo de prima podría generar resultados incorrectos, llevando a cotizaciones inexactas, pérdidas financieras, insatisfacción del cliente y retrabajos significativos.
**Critical Dependencies:** El Motor de Cálculo de Prima depende críticamente de que los datos que recibe sean válidos.
**Recommended Priority:** Sprint actual / Próximo sprint (dada su prioridad "Alta" y la dependencia con HU-169).

## 18. Identified Assumptions
1.  **Estados de Validación de Ubicación:**
    -   Description: Se asume que el `estadoValidacion` de cada `ubicacion` es actualizado de forma fiable por un proceso previo (ej. un servicio de validación de ubicaciones) antes de que el usuario intente calcular la prima.
    -   Impact if false: Si los estados no son correctos o están desactualizados, la validación pre-cálculo podría permitir cálculos con datos inválidos o bloquear cálculos válidos.
    -   Requires validation from: Equipo de Backend / Dueño de Producto del módulo de Ubicaciones.
2.  **Reglas de Validación de Coberturas:**
    -   Description: Se asume que existen reglas claras y definidas para determinar cuándo una cobertura o sus parámetros son "no definidos" o "erróneos".
    -   Impact if false: El sistema podría no detectar coberturas inválidas o podría bloquear coberturas válidas, llevando a cálculos incorrectos o bloqueos innecesarios.
    -   Requires validation from: Dueño de Producto / Actuarios / Equipo de Backend del Motor de Reglas de Negocio.
