## Refinamiento de Historias de Usuario

## 1. Identificación General
**Feature:** Gestión de Cotizaciones y Pólizas
**Capability:** CAP-012 - Validación de Suscripción
**Actor:** Usuario (Agente de Seguros/Asegurado)
**Bounded Context:** Cotización/Suscripción
**Story Points:** 3

## 2. Enabled Capability
**CAP-012:** Validación de Sumas Aseguradas
**Business Value:** Evita errores en la cotización, asegura la coherencia con las políticas de suscripción, reduce el riesgo de emisión de pólizas inviables o no conformes y mejora la eficiencia del proceso de cotización al detectar problemas tempranamente.
**Requires:** CAP-011 - Gestión de Reglas de Suscripción (para obtener los rangos de validación)
**Enables:** CAP-013 - Generación de Cotización Válida, CAP-014 - Emisión de Póliza
**Orchestrates:** Módulo de reglas de validación

## 3. User Story
Como usuario,
quiero que el sistema valide que las sumas aseguradas de cada ubicación estén dentro de los rangos predefinidos,
para evitar errores en la cotización y asegurar que los montos sean coherentes con las políticas de suscripción.

## 4. Functional Description
**Description:** El sistema debe verificar que cada suma asegurada ingresada por el usuario para una ubicación específica, cumpla con los límites mínimos y máximos establecidos en las políticas de suscripción. Esta validación se ejecutará durante el proceso de cotización. Si una suma asegurada está fuera de rango, se reportará un error claro al usuario, indicando la ubicación y el tipo de incumplimiento (menor al mínimo o mayor al máximo). Los rangos de validación serán configurables y podrán depender de factores como el tipo de riesgo o la zona geográfica.
**Flow:** [Ingreso de Ubicaciones y Sumas Aseguradas] → [Esta historia: Validación de Rangos de Suma Asegurada] → [Cálculo de Prima / Reporte de Errores al Usuario]

## 5. Expected Results


| element | description |
|---|---|
| Data | El estado de la suma asegurada (válida/inválida) y el mensaje de error asociado se almacenan temporalmente en la sesión de cotización. |
| States | El estado de la cotización puede cambiar a 'En Validación con Errores' si alguna suma asegurada es inválida, o a 'Válida para Cálculo' si todas son correctas. |
| Notifications | Mensajes de error en la interfaz de usuario (modales o mensajes inline) para cada suma asegurada fuera de rango. |
| Integrations | Se invoca a FT-010 (Servicio de Configuración de Suscripción) para obtener los rangos de validación aplicables. |
| Kafka | Potencialmente, se podría publicar un evento 'SumaAseguradaValidada' o 'SumaAseguradaInvalida' para sistemas downstream, aunque no es un requisito explícito en la descripción. |
| Logs | Mensajes de INFO para validaciones exitosas y WARNING/ERROR para sumas aseguradas que no cumplen con los rangos, incluyendo detalles de la ubicación y el valor. |
| UI | Indicadores visuales de error (por ejemplo, resaltado en rojo, iconos de advertencia) junto a los campos de entrada de suma asegurada, y un resumen de errores en la pantalla de cotización. |


## 6. Acceptance Criteria
### AC-001: Suma Asegurada Válida
**Description:** Valida que una suma asegurada dentro del rango permitido sea aceptada por el sistema.

```gherkin
Scenario: Suma asegurada dentro del rango permitido
  Given que el rango permitido para una ubicación específica es entre 50.000 y 500.000
  And que el usuario ingresa una suma asegurada de 250.000 para esa ubicación
  When se ejecuta la validación de la suma asegurada
  Then la suma asegurada se considera válida
  And no se reporta ningún error específico para esa suma asegurada
```

### AC-002: Suma Asegurada por Debajo del Mínimo
**Description:** Valida que una suma asegurada por debajo del mínimo permitido genere un error específico.

```gherkin
Scenario: Suma asegurada por debajo del mínimo
  Given que el rango permitido para una ubicación específica es entre 50.000 y 500.000
  And que el usuario ingresa una suma asegurada de 45.000 para esa ubicación
  When se ejecuta la validación de la suma asegurada
  Then el sistema reporta un error específico para esa suma asegurada
  And el mensaje de error indica que el valor está por debajo del mínimo permitido (ej. 'La suma asegurada es inferior al mínimo de 50.000').
```

### AC-003: Suma Asegurada por Encima del Máximo
**Description:** Valida que una suma asegurada por encima del máximo permitido genere un error específico.

```gherkin
Scenario: Suma asegurada por encima del máximo
  Given que el rango permitido para una ubicación específica es entre 50.000 y 500.000
  And que el usuario ingresa una suma asegurada de 550.000 para esa ubicación
  When se ejecuta la validación de la suma asegurada
  Then el sistema reporta un error específico para esa suma asegurada
  And el mensaje de error indica que el valor está por encima del máximo permitido (ej. 'La suma asegurada excede el máximo de 500.000').
```

## 7. Data and Business Rules


| field | type | required | default | validation | catalog | example |
|---|---|---|---|---|---|---|
| sumaAsegurada | Decimal | yes | N/A | Mayor que 0, formato monetario (ej. 100000.00) | N/A | 150000.00 |
| idUbicacion | UUID/String | yes | N/A | Formato UUID o alfanumérico | N/A | loc-a1b2c3d4 |
| rangoMinimo | Decimal | yes | N/A | Mayor que 0 | Obtenido de FT-010 | 50000.00 |
| rangoMaximo | Decimal | yes | N/A | Mayor que rangoMinimo | Obtenido de FT-010 | 500000.00 |
| tipoRiesgo | String | yes | N/A | N/A | Incendio, Robo, Terremoto, etc. | Incendio |
| zonaGeografica | String | yes | N/A | N/A | Zona A, Zona B, Zona C, etc. | Zona A |


**BR-001:** Validación de Rango de Suma Asegurada por Ubicación
- Description: Para cada ubicación en una cotización, la suma asegurada ingresada debe estar comprendida entre un valor mínimo y un valor máximo predefinidos, los cuales pueden variar según el tipo de riesgo y la zona geográfica.
- Trigger: Al finalizar el ingreso o modificación de las sumas aseguradas para una cotización, o al intentar avanzar al siguiente paso del flujo de cotización.
- Logic: `IF (sumaAsegurada < rangoMinimo OR sumaAsegurada > rangoMaximo) THEN ReportarErrorDeRango(sumaAsegurada, idUbicacion, rangoMinimo, rangoMaximo)`
- Implementation: Módulo de reglas de validación (backend).
- Exception: N/A

## 9. Administrative Functionality (if applicable)
**Description:** Permitir a los usuarios con el rol de "Administrador de Suscripción" configurar y gestionar los rangos mínimos y máximos para las sumas aseguradas. Esta funcionalidad debe permitir definir rangos condicionales (ej. por tipo de riesgo, zona).

```gherkin
Scenario: Actualización de rangos de suma asegurada por administrador
  Given que un usuario con rol "Administrador de Suscripción" ha iniciado sesión
  When el administrador navega a la sección de configuración de reglas de suscripción
  And selecciona la opción para gestionar rangos de suma asegurada
  And actualiza el rango máximo para el 'Tipo de Riesgo: Incendio' en 'Zona A' a 600.000
  Then el sistema guarda el nuevo rango de validación
  And las futuras cotizaciones aplicarán este nuevo rango para 'Incendio' en 'Zona A'
  And se genera un registro de auditoría de la modificación
```

## 10. UX and Navigation Flow
**UX Flow:** [Pantalla de Ingreso de Datos de Cotización (con campos para Sumas Aseguradas por Ubicación)] → [Validación en tiempo real (al perder el foco del campo) o al intentar 'Guardar' / 'Continuar'] → [Mostrar errores inline junto al campo afectado y/o un resumen de errores en la parte superior de la pantalla]
**Messages/Modals:**
- Mensaje de error para suma por debajo del mínimo: "La suma asegurada ingresada ([Valor]) está por debajo del mínimo permitido ([Mínimo]) para esta ubicación."
- Mensaje de error para suma por encima del máximo: "La suma asegurada ingresada ([Valor]) excede el máximo permitido ([Máximo]) para esta ubicación."
- Mensaje de éxito (implícito): No se muestra mensaje si es válido, simplemente se permite continuar.
**Stepper/Breadcrumbs:** (Contexto de cotización) [Datos del Cliente] → [Ubicaciones y Sumas Aseguradas] → [Validación] → [Resumen y Cálculo de Prima]

## 11. Architecture and Technical Dependencies
- **Módulo de reglas de validación (Backend Service):** Encapsula la lógica de negocio para la validación de rangos. Deberá ser desacoplado y reutilizable.
- **Componente de reporte de errores (Shared Library/Service):** Maneja la estandarización y presentación de mensajes de error a la interfaz de usuario y a los logs.
- **Servicio de Configuración de Suscripción (FT-010):** Servicio externo (o microservicio interno) que provee los rangos de validación dinámicamente, potencialmente basado en `tipoRiesgo`, `zonaGeografica` y otros factores.
    - **Propósito:** Fuente de verdad para las reglas de negocio de suscripción.
    - **Timeout:** 500ms
    - **Retries:** 2 (con backoff exponencial)
- **Circuit Breaker:** Implementado para la llamada a FT-010 para manejar fallos de forma robusta.

## 16. Technical Notes and Risks
**Risks:**
1.  **Disponibilidad y Latencia de FT-010:**
    *   **Descripción:** Si el servicio que provee los rangos (FT-010) tiene alta latencia o no está disponible, la validación de sumas aseguradas se verá afectada o bloqueada.
    *   **Impacto:** Fallos en la creación de cotizaciones, mala experiencia de usuario, posibles cotizaciones incorrectas si se implementa un fallback inadecuado.
    *   **Probabilidad:** Media.
    *   **Mitigación:** Implementar Circuit Breaker con un mecanismo de fallback robusto (ej. rangos por defecto muy restrictivos o muy amplios según el apetito de riesgo), caching de rangos, y monitoreo proactivo de FT-010.
2.  **Complejidad de las Reglas de Rangos:**
    *   **Descripción:** A medida que los rangos dependen de más factores (ej. tipo de cliente, edad del asegurado, historial de siniestros), la lógica para determinar el rango correcto puede volverse muy compleja y difícil de mantener.
    *   **Impacto:** Errores en la validación, alta deuda técnica, dificultad para escalar el sistema.
    *   **Probabilidad:** Media.
    *   **Mitigación:** Diseñar el módulo de reglas de validación de forma extensible, quizás utilizando un motor de reglas de negocio (BRMS) si la complejidad justifica la inversión, y mantener una clara separación de responsabilidades.

**Technical Debt:** El módulo de reglas de validación podría evolucionar a un microservicio de BRMS dedicado si la lógica de suscripción crece significativamente en complejidad y número de reglas.

## 17. Criticality
**Criticality Level:** Alta
**Justification:** Esta historia es fundamental para la integridad de los datos de cotización y para asegurar que las pólizas cumplan con las políticas de suscripción de la compañía. Un fallo en esta validación podría resultar en pérdidas financieras significativas, incumplimiento normativo, o la emisión de pólizas que no pueden ser cubiertas.
**Feature Impact:** Sin esta validación, la funcionalidad de cotización completa sería inestable, generaría resultados incorrectos y podría comprometer la viabilidad del negocio al emitir pólizas con riesgos no cubiertos o infravalorados.
**Critical Dependencies:** Todas las historias de usuario que impliquen la creación, modificación o aprobación de cotizaciones con sumas aseguradas.
**Recommended Priority:** Sprint actual / Inmediata.

## 18. Identified Assumptions
1.  **Disponibilidad y Consistencia de los Rangos de Validación:**
    *   Description: Se asume que los rangos mínimos y máximos para las sumas aseguradas, condicionados por tipo de riesgo y zona, estarán siempre disponibles a través de FT-010 y serán consistentes (ej. rangoMinimo <= rangoMaximo).
    *   Impact if false: El sistema no podrá realizar las validaciones correctamente, lo que resultará en cotizaciones erróneas o bloqueadas.
    *   Requires validation from: Equipo de Arquitectura, Equipo de Suscripción, Dueño de FT-010.
2.  **Formato de Entrada de Suma Asegurada:**
    *   Description: Se asume que la suma asegurada ingresada por el usuario siempre será un valor numérico válido (positivo y dentro de un formato esperado antes de la validación de rango).
    *   Impact if false: El sistema podría fallar al intentar procesar valores no numéricos o generar errores de tipo de dato antes de llegar a la validación de rango.
    *   Requires validation from: Equipo de UX/UI, Equipo de Desarrollo.
3.  **Estrategia de Fallback para Rangos Inaccesibles:**
    *   Description: Se asume que existe una estrategia definida para el caso en que FT-010 no esté disponible o no retorne rangos para un criterio específico (ej. usar rangos por defecto, bloquear la cotización).
    *   Impact if false: Comportamiento impredecible del sistema en escenarios de error, riesgo de operar con datos de validación incorrectos.
    *   Requires validation from: Equipo de Arquitectura, Equipo de Suscripción.
