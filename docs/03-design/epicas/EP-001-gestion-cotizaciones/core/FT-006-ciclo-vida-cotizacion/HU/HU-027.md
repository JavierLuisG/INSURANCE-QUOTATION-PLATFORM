## 2. Enabled Capability
**CAP-027:** Gestión de Ciclo de Vida de Cotizaciones
**Business Value:** Permite finalizar formalmente el ciclo de vida de una cotización, indicando que está lista para la emisión de una póliza y bloqueando futuras modificaciones, lo que contribuye a la integridad del proceso de negocio.
**Requires:** CAP-026 - Transición de Estado de Cotización (Aprobada/Rechazada)
**Enables:** CAP-XXX - Emisión de Póliza (potencialmente)
**Orchestrates:** N/A

## 3. User Story
Como un **usuario**,
quiero **poder establecer el estado de una cotización a "Emitida" una vez que ha sido aprobada**,
para **finalizar el ciclo de vida**.

## 4. Functional Description
**Description:** Esta historia de usuario permite que un usuario autorizado cambie el estado de una cotización de "Aprobada" a "Emitida". Este cambio de estado representa la culminación del proceso de cotización, indicando que la cotización ha sido aceptada por el cliente y está lista para la emisión formal de una póliza. Al establecerse como "Emitida", la cotización debe bloquearse para futuras ediciones. El sistema validará que solo las cotizaciones en estado "Aprobada" puedan realizar esta transición.
**Flow:** HU-026 (Cambiar estado a "Aprobada") → **HU-027 (Establecer estado "Emitida")** → [Posible HU-XXX: Emisión de Póliza]

## 5. Expected Results


| element | description |
|---|---|
| Data | El campo 'estado' de la entidad 'Cotización' se actualiza a 'Emitida'. Se registra la fecha y hora de emisión. |
| States | La cotización transiciona del estado 'Aprobada' al estado 'Emitida'. La cotización se considera finalizada y sus campos se bloquean para edición. |
| Notifications | Posible notificación interna o a sistemas externos sobre la cotización emitida (ej. a un sistema de emisión de pólizas). |
| Integrations | Si aplica, el sistema podría invocar un servicio externo para iniciar el proceso de emisión de pólizas. |
| Kafka | Podría publicarse un evento 'QuotationEmittedEvent' para notificar a otros servicios del sistema. |
| Logs | Se registra una entrada de log a nivel INFO o DEBUG indicando el cambio de estado de la cotización y el usuario que realizó la acción. |
| UI | En la interfaz de usuario, el botón 'Emitir' se habilita para cotizaciones 'Aprobadas' y se deshabilita/oculta para otros estados. Una vez emitida, el estado visible en la UI cambia a 'Emitida' y los campos de edición se bloquean o se muestran como solo lectura. |


## 6. Acceptance Criteria
### AC-001: Actualización de estado a "Emitida" desde "Aprobada"
**Description:** Valida que una cotización en estado "Aprobada" puede ser exitosamente cambiada a "Emitida".

```gherkin
Scenario: Actualizar estado de cotización aprobada a "Emitida"
  Given el estado de la cotización es "Aprobada"
  When selecciono la opción "Emitir"
  Then el estado de la cotización se actualiza a "Emitida"
  And la cotización se considera finalizada y no permite ediciones
```

### AC-002: Restricción de cambio de estado a "Emitida" desde un estado no "Aprobada"
**Description:** Valida que el sistema impide la transición a "Emitida" si la cotización no se encuentra en el estado "Aprobada".

```gherkin
Scenario: Intentar emitir una cotización en estado no aprobado
  Given el estado de la cotización NO es "Aprobada" (ej. "Pendiente" o "Rechazada")
  When intento cambiar el estado a "Emitida"
  Then el sistema me impide la acción
  And se muestra un mensaje de error o advertencia al usuario
  And el estado de la cotización permanece sin cambios
```

### AC-003: Visibilidad y bloqueo de cotización emitida
**Description:** Valida que una vez emitida, el nuevo estado es visible y la cotización se bloquea para futuras modificaciones.

```gherkin
Scenario: Consultar cotización con estado "Emitida"
  Given el estado de la cotización es "Emitida"
  When consulto la cotización en la interfaz de usuario
  Then el estado visible es "Emitida"
  And los campos de edición de la cotización están deshabilitados o en modo solo lectura
```

**BR-001: Transición de estado a "Emitida"**
- Description: Una cotización solo puede transicionar al estado "Emitida" si su estado actual es "Aprobada".
- Trigger: Intento de un usuario de cambiar el estado de una cotización a "Emitida".
- Logic: `IF cotizacion.estado_actual == "Aprobada" THEN cotizacion.estado_nuevo = "Emitida" ELSE REJECT_ACTION`
- Implementation: Servicio de gestión de cotizaciones (backend), parte de FT-009.
- Exception: Intentar emitir una cotización en cualquier otro estado.

**BR-002: Bloqueo de edición de cotización emitida**
- Description: Una vez que una cotización ha sido establecida en estado "Emitida", no se permite ninguna modificación posterior a sus detalles (ej. productos, precios, datos del cliente).
- Trigger: Intento de un usuario de editar una cotización que está en estado "Emitida".
- Logic: `IF cotizacion.estado == "Emitida" THEN REJECT_EDIT_ACTION`
- Implementation: Servicio de gestión de cotizaciones (backend) y lógica de UI (frontend).

## 10. UX and Navigation Flow
**UX Flow:** Vista de Detalle de Cotización (estado "Aprobada") → Botón/Opción "Emitir" (habilitado) → (Opcional: Modal de Confirmación "Una vez emitida, la cotización no podrá ser modificada. ¿Desea continuar?") → Vista de Detalle de Cotización (estado "Emitida", campos deshabilitados/solo lectura, botón "Emitir" oculto/deshabilitado).
**Messages/Modals:**

*   **Error:** "No se pudo emitir la cotización {ID_COTIZACION}. Solo las cotizaciones 'Aprobadas' pueden ser emitidas."

**Stepper/Breadcrumbs:** El estado "Emitida" podría representarse como el paso final en un indicador visual del ciclo de vida de la cotización.

## 11. Architecture and Technical Dependencies
- **Backend: API de Cotizaciones:** Se requiere un endpoint (ej. `PUT /api/cotizaciones/{id}/estado` o `POST /api/cotizaciones/{id}/emitir`) para manejar la solicitud de cambio de estado.
- **Lógica de Transiciones de Estado:** Módulo o servicio que implementa las reglas de negocio (BR-001, BR-002) para las transiciones de estado de cotizaciones (parte de FT-009).
- **Frontend: Componente de Detalle de Cotización:** Implementación del botón/opción "Emitir" y la lógica de habilitación/deshabilitación basada en el estado actual de la cotización y los permisos del usuario.
- **Servicio de Auditoría:** Para registrar la acción de emisión de cotización (sección 9).
- **Sistema de Emisión de Pólizas (opcional):** Si la emisión de la cotización desencadena un proceso en un sistema externo, se requerirá una integración (ej. vía API REST, Kafka).

## 16. Technical Notes and Risks
**Risks:**
1.  **Inconsistencia de estado entre sistemas:**
    *   Description: Si hay una integración con un sistema de emisión de pólizas, existe el riesgo de que la cotización se marque como "Emitida" localmente, pero falle la creación de la póliza en el sistema externo, llevando a una inconsistencia.
    *   Impact: Proceso de negocio roto, confusión del usuario, necesidad de conciliación manual.
    *   Probability: Media.
    *   Mitigation: Implementar mecanismos de reintento, colas de mensajes (Kafka) para la comunicación asíncrona, y un panel de monitoreo para transacciones fallidas.
2.  **Complejidad en el bloqueo de edición:**
    *   Description: Asegurar que todos los puntos de entrada (UI y API) para la edición de una cotización respeten el estado "Emitida" y bloqueen las modificaciones.
    *   Impact: Integridad de los datos comprometida si una cotización emitida puede ser alterada.
    *   Probability: Baja (si se implementa cuidadosamente).
    *   Mitigation: Centralizar la lógica de validación de estado en el backend y aplicar deshabilitación/modo solo lectura en el frontend.

**Technical Debt:** N/A (Se determinará por el equipo operativo según el alcance y el MVP).

## 17. Criticality
**Criticality Level:** Media
**Justification:** Es una etapa esencial y final del ciclo de vida de la cotización. Si bien no bloquea la creación o aprobación de cotizaciones, su ausencia impide la finalización formal del proceso y la transición a la emisión de una póliza, lo cual es un objetivo de negocio clave.
**Feature Impact:** Sin esta funcionalidad, el flujo de gestión de cotizaciones queda incompleto, no permitiendo cerrar el ciclo y potencialmente retrasando la emisión de pólizas.
**Critical Dependencies:** Depende críticamente de HU-026 para que la cotización alcance el estado "Aprobada" y de FT-009 para asegurar la correcta aplicación de las reglas de negocio.
**Recommended Priority:** Sprint actual o próximo, ya que es una pieza fundamental para completar el flujo principal de cotizaciones.

## 18. Identified Assumptions
1.  **Permisos de Usuario y Roles Definidos:**
    *   Description: Se asume que existe un sistema de gestión de roles y permisos (RBAC) que define claramente qué usuarios están autorizados para realizar la acción de "Emitir" una cotización.
    *   Impact if false: Riesgo de que usuarios no autorizados puedan emitir cotizaciones, llevando a errores operativos o violaciones de seguridad.
    *   Requires validation from: Product Owner y Equipo de Seguridad.
2.  **No Reversión del Estado "Emitida":**
    *   Description: Se asume que una vez que una cotización ha sido "Emitida", no existe un requerimiento de negocio para revertir este estado a uno anterior (ej. "Aprobada" o "Pendiente").
    *   Impact if false: Si se requiere reversión, esta historia no la contempla y se necesitarían flujos de negocio y desarrollo adicionales para manejar tales escenarios.
    *   Requires validation from: Product Owner y Equipo de Negocio.
3.  **Integración con Emisión de Pólizas es Posterior/Asíncrona (si aplica):**
    *   Description: Se asume que si la emisión de la cotización desencadena una acción en un sistema de emisión de pólizas, esta integración puede ser asíncrona o manejarse en una historia de usuario posterior.
    *   Impact if false: Si la emisión de la póliza es una acción síncrona y obligatoria dentro de esta misma historia, aumentaría significativamente la complejidad y los riesgos de la HU-027.
    *   Requires validation from: Arquitecto y Product Owner.
