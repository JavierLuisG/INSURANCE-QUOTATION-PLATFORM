Además, contempla la posibilidad de utilizar datos en caché o valores por defecto como estrategia de fallback y la notificación adecuada de los errores a usuarios y equipos de operación.

## 6. Acceptance Criteria (3-5 criteria)
### AC-001: Manejo de indisponibilidad total del servicio externo
**Description:** Valida que el sistema detecta y reacciona correctamente cuando `Plataforma-core-ohs` no está accesible o no responde, aplicando patrones de resiliencia y notificando adecuadamente.

```gherkin
Scenario: El servicio Plataforma-core-ohs no está disponible
  Given el servicio "Plataforma-core-ohs" no responde a las solicitudes
  And el sistema intenta consultar "Plataforma-core-ohs" para una operación
  When se detecta la indisponibilidad del servicio externo
  Then el sistema activa el Circuit Breaker para "Plataforma-core-ohs"
  And se registra un error de comunicación de nivel ERROR
  And se notifica al equipo de operaciones sobre la indisponibilidad
  And el sistema aplica una estrategia de fallback (ej. retorna datos cacheados o un mensaje de error controlado al usuario)
```

### AC-002: Manejo de respuestas inconsistentes o malformadas
**Description:** Valida que el sistema puede procesar respuestas de `Plataforma-core-ohs` que no cumplen con el formato o la lógica esperada, registrando el incidente.

```gherkin
Scenario: Respuesta inconsistente de Plataforma-core-ohs
  Given el servicio "Plataforma-core-ohs" está disponible y responde
  And el sistema consulta "Plataforma-core-ohs"
  When la respuesta recibida contiene datos malformados o inconsistentes según el contrato esperado
  Then el sistema maneja la inconsistencia según reglas de negocio (ej. ignora el campo, usa un valor por defecto seguro)
  And se registra un evento de advertencia o error sobre la inconsistencia de la respuesta
  And se notifica al equipo de operaciones si la inconsistencia es crítica o recurrente
```

### AC-003: Aplicación de política de reintentos para errores transitorios
**Description:** Valida que el sistema aplica una política de reintentos para errores de comunicación temporales, evitando fallos inmediatos.

```gherkin
Scenario: Reintento exitoso tras un error transitorio
  Given el servicio "Plataforma-core-ohs" experimenta un error de red temporal (ej. timeout)
  When el sistema intenta una operación dependiente de "Plataforma-core-ohs"
  Then el sistema reintenta la operación con un backoff exponencial configurado
  And el segundo intento es exitoso
  And se registra un evento de advertencia (WARN) sobre el reintento
  And la operación se completa con éxito y se notifica al usuario (si aplica)
```

**BR-001: Política de Reintentos (Retry)**
- Description: Define cómo y cuántas veces el sistema intentará invocar `Plataforma-core-ohs` en caso de errores transitorios.
- Trigger: Errores de comunicación (ej. timeouts, conexión rechazada, HTTP 5xx excepto 501/505).
- Logic:
    - Número máximo de reintentos: 3
    - Estrategia de espera: Backoff exponencial con jitter (ej. 1s, 2s, 4s +/- 250ms).
- Implementation: Capa de Integración del Backend (ej. con Resilience4j o Spring Retry).
- Exception: No se reintenta para errores 4xx (errores del cliente) o errores de negocio específicos.

**BR-002: Lógica del Circuit Breaker**
- Description: Protege el sistema de fallos continuos del servicio externo, abriendo el circuito para evitar sobrecargarlo y permitir su recuperación.
- Trigger: Una tasa o número de fallos consecutivos al invocar `Plataforma-core-ohs` excede un umbral.
- Logic:
    - Umbral de fallos: 5 fallos en un período de 10 segundos.
    - Tiempo de espera (estado "OPEN"): 30 segundos.
    - Estado "HALF_OPEN": Después del tiempo de espera, permite 1 solicitud de prueba. Si falla, vuelve a "OPEN"; si tiene éxito, pasa a "CLOSED".
- Implementation: Capa de Integración del Backend (ej. con Resilience4j).
- Exception: N/A

**BR-003: Estrategia de Fallback por Indisponibilidad**
- Description: Define la acción a tomar cuando `Plataforma-core-ohs` no está disponible o falla persistentemente (Circuit Breaker abierto o reintentos agotados).
- Trigger: Fallo persistente de `Plataforma-core-ohs` o Circuit Breaker en estado "OPEN".
- Logic:
    - Si hay datos en caché válidos y recientes para la solicitud: Utilizar los datos cacheados.
    - Si no hay datos en caché válidos: Retornar un mensaje de error genérico al usuario o, si es posible, valores por defecto seguros.
- Implementation: Capa de Integración, Servicio de Caché.
- Exception: N/A

- **Sistema de Monitoreo y Alertas (ej. Prometheus/Grafana, PagerDuty):** Para la recolección de métricas de resiliencia y la notificación proactiva de incidentes.

## 16. Technical Notes and Risks
**Risks:**
1.  **Complejidad de la configuración de patrones de resiliencia:**
    *   Descripción: La configuración óptima de Circuit Breakers, Retries y Fallbacks requiere un buen entendimiento del comportamiento del servicio `Plataforma-core-ohs` y de la carga esperada.
    *   Impacto: Una configuración incorrecta puede llevar a un Circuit Breaker que se abre demasiado pronto (falsos positivos) o demasiado tarde (exponiendo al sistema a fallos prolongados).
    *   Probabilidad: Media.
    *   Mitigación: Utilizar bibliotecas de resiliencia probadas, realizar pruebas de carga y de fallos (Chaos Engineering ligero), documentar y revisar las configuraciones con expertos.
2.  **Exposición de información sensible en logs de errores:**
    *   Descripción: Los mensajes de error de `Plataforma-core-ohs` o los payloads de las solicitudes podrían contener datos confidenciales.
    *   Impacto: Incumplimiento de normativas de privacidad (ej. GDPR, CCPA), riesgo de seguridad.
    *   Probabilidad: Baja (con buenas prácticas).
    *   Mitigación: Implementar sanitización automática o enmascaramiento de datos en los logs, auditoría regular de los logs.
3.  **Impacto en el rendimiento por reintentos excesivos:**
    *   Descripción: Una política de reintentos mal diseñada puede sobrecargar el sistema llamador y, paradójicamente, al propio servicio `Plataforma-core-ohs` cuando este se está recuperando.
    *   Impacto: Degradación del rendimiento del cotizador, posibles efectos de "bola de nieve" en la infraestructura.
    *   Probabilidad: Media.
    *   Mitigación: Asegurar el uso de backoff exponencial con jitter, limitar el número máximo de reintentos y que el Circuit Breaker actúe antes de que los reintentos se conviertan en un problema.

**Technical Debt:**
- La implementación inicial del fallback podría ser genérica (ej. mensaje de error estándar). Refinarla para ofrecer fallbacks más específicos o datos parciales por tipo de consulta podría ser deuda técnica futura.
- La configuración del Circuit Breaker y Retry podría estar inicialmente en archivos de configuración locales. Externalizar esta configuración a un sistema de gestión centralizado (ej. Spring Cloud Config, Consul) sería una mejora posterior.

## 17. Criticality
**Criticality Level:** Alta
**Justification:** El servicio `Plataforma-core-ohs` es un componente crítico para la operación del cotizador. Sin un manejo robusto de errores, cualquier interrupción o degradación de este servicio externo impactaría directamente la capacidad del sistema para generar cotizaciones, lo que es una función central del negocio.
**Feature Impact:** La no implementación o el fallo de esta historia expondría al cotizador a caídas completas o comportamientos erráticos, resultando en una mala experiencia de usuario, pérdida de oportunidades de negocio y daños a la reputación.
**Critical Dependencies:** Todas las historias de usuario que implican la invocación de `Plataforma-core-ohs` (HU-144, HU-145, HU-146, HU-147) dependen críticamente de esta funcionalidad.
**Recommended Priority:** Sprint actual. Es fundamental para la estabilidad del producto.

    - Description: Se asume que existen datos que pueden ser utilizados de forma segura como fallback (ej. datos cacheados, valores por defecto) o que el negocio acepta la degradación de la experiencia del usuario (ej. un mensaje de error genérico) en caso de fallo crítico de `Plataforma-core-ohs`.
    - Impact if false: La estrategia de fallback podría no ser aplicable o no generar el valor esperado, dejando al sistema sin una opción de recuperación efectiva.
    - Requires validation from: Product Owner, Arquitectos de Solución.
