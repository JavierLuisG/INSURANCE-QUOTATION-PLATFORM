## 1. Identificación General
**Feature:** Recuperación de Catálogos
**Capability:** CAP-003 - Gestión de Catálogos
**Actor:** Sistema (Cotizador)
**Bounded Context:** Módulo de Cotización
**Story Points:** 3

## 2. Enabled Capability
**CAP-003:** Gestión de Catálogos
**Business Value:** Asegurar que el formulario de cotización disponga de una lista de agentes actualizada, permitiendo la selección y persistencia correcta del agente.
**Requires:** CAP-002 (Asumiendo que HU-068 habilita una capacidad previa, por ejemplo, la inicialización del formulario de cotización)
**Enables:** CAP-004 (Permite completar y guardar cotizaciones con agentes válidos)
**Orchestrates:** Plataforma-core-ohs (o su mock)

## 3. User Story
Como sistema,
Quiero recuperar el catálogo de agentes desde el servicio `Plataforma-core-ohs` (o su mock),
Para ofrecer una lista actualizada en el formulario de cotización.

## 4. Functional Description
**Description:** Esta historia de usuario describe cómo el módulo de cotización se integra con el servicio `Plataforma-core-ohs` (o un mock) para obtener una lista de agentes. El objetivo es asegurar que la lista de agentes disponible para la selección en el formulario de cotización esté siempre actualizada. Se contempla una estrategia de reintento y notificación en caso de que el servicio de agentes esté inactivo. Finalmente, se asegura que el ID del agente seleccionado sea el valor persistido al guardar una cotización.
**Flow:** HU-068 (Inicialización del formulario de cotización) → HU-070 (Recuperación y visualización del catálogo de agentes) → HU-112 (Editar Datos Generales de la Cotización)

## 6. Acceptance Criteria
### AC-001: Recuperación exitosa del catálogo de agentes
**Description:** Valida que el sistema pueda obtener correctamente la lista de agentes con sus IDs y nombres del servicio externo.

```gherkin
Scenario: El cotizador recupera exitosamente el catálogo de agentes
  Given que el cotizador necesita el catálogo de agentes
  When realiza una solicitud al servicio Plataforma-core-ohs (o su mock)
  Then recibe una lista de agentes con sus IDs y nombres
```

### AC-002: Manejo de inactividad del servicio de agentes
**Description:** Valida que, ante la inactividad del servicio de agentes, el sistema aplique una estrategia de reintento y notifique el fallo si la recuperación no es posible.

```gherkin
Scenario: El cotizador maneja la inactividad del servicio de agentes
  Given que el servicio de agentes Plataforma-core-ohs está temporalmente inactivo
  When el cotizador intenta recuperar el catálogo
  Then se aplica la estrategia de reintento
  And si falla después de los reintentos, se notifica el incidente
```

### AC-003: Persistencia correcta del ID del agente
**Description:** Valida que al guardar el formulario de cotización, el identificador único del agente seleccionado sea persistido y no solo su nombre.

```gherkin
Scenario: El ID del agente seleccionado se persiste correctamente
  Given que el usuario ha seleccionado un agente en el formulario de cotización
  When el formulario de cotización es guardado
  Then el ID del agente seleccionado se persiste correctamente con la cotización
```

| field | type | required | default | validation | catalog | example |
|---|---|---|---|---|---|---|
| agenteId | UUID/String | yes | N/A | Formato UUID o cadena alfanumérica única | Catálogo de Agentes (Plataforma-core-ohs) | a1b2c3d4-e5f6-7890-1234-567890abcdef |
| agenteNombre | String | yes | N/A | No vacío, longitud máxima 100 caracteres | Catálogo de Agentes (Plataforma-core-ohs) | Juan Pérez |
| cotizacionAgenteId | UUID/String | yes | N/A | Debe ser uno de los IDs del catálogo de agentes disponibles | N/A | a1b2c3d4-e5f6-7890-1234-567890abcdef |


**BR-001:** Persistencia del Agente por ID
- Description: Al guardar una cotización, el sistema debe almacenar el identificador único (ID) del agente seleccionado, no solo su nombre visible.
- Trigger: Al guardar una nueva cotización o actualizar una existente.
- Logic: `cotizacion.agenteId = agenteSeleccionado.id`
- Implementation: Servicio de persistencia de cotizaciones.
- Exception: Si el `agenteId` no es válido o no existe en el catálogo, la cotización no debe guardarse o debe marcarse con un error.

## 11. Architecture and Technical Dependencies
- **Plataforma-core-ohs**: Servicio REST para la gestión y provisión del catálogo de agentes.
    - Propósito: Suministrar la lista de agentes con sus IDs y nombres.
    - Timeout: 5000 ms (configurable)
    - Retries: 3 intentos con backoff exponencial.
- **Cliente API REST**: Módulo dentro del cotizador encargado de realizar las llamadas HTTP a `Plataforma-core-ohs`.
- **Capa de mapeo de datos**: Componente para transformar la respuesta del servicio externo al modelo de datos interno del cotizador.
- **Repositorio de catálogos**: Componente dentro del cotizador para almacenar temporalmente o en caché el catálogo de agentes.
- **Circuit Breaker**: Implementación de un patrón Circuit Breaker para `Plataforma-core-ohs` para manejar fallos prolongados y evitar sobrecargar el servicio.

## 16. Technical Notes and Risks
**Risks:**
1.  **Disponibilidad de `Plataforma-core-ohs`**:
    -   Descripción: Si el servicio `Plataforma-core-ohs` no está disponible o responde lentamente, afectará la capacidad del cotizador para cargar el catálogo de agentes.
    -   Impacto: Los usuarios no podrán seleccionar agentes o verán información desactualizada, impidiendo la creación de cotizaciones válidas.
    -   Probabilidad: Media
    -   Mitigación: Implementación de Circuit Breaker, estrategia de reintentos, caché del catálogo de agentes (si la frescura no es crítica en tiempo real), monitoreo proactivo del servicio.
2.  **Consistencia del ID del agente**:
    -   Descripción: Un error en el mapeo o persistencia podría llevar a que el nombre del agente sea guardado en lugar del ID, o que el ID guardado no corresponda a un agente válido.
    -   Impacto: Integridad de los datos comprometida, imposibilidad de referenciar correctamente al agente en procesos posteriores.
    -   Probabilidad: Baja (con pruebas adecuadas)
    -   Mitigación: Pruebas unitarias y de integración exhaustivas, validación de datos en el punto de persistencia.

**Technical Debt:** No identificado inicialmente. Se rellenará por el equipo operativo según el alcance y el MVP.

## 17. Criticality
**Criticality Level:** Alta
**Justification:** Esta historia es fundamental para el funcionamiento básico del módulo de cotización, ya que sin un catálogo de agentes, los usuarios no pueden seleccionar un agente, lo cual es un requisito clave para completar una cotización.
**Feature Impact:** La no implementación o el fallo de esta historia paralizaría la funcionalidad central del formulario de cotización y, por extensión, la capacidad del sistema para generar cotizaciones válidas.
**Critical Dependencies:** El formulario de cotización y cualquier proceso que necesite asociar una cotización a un agente válido.
**Recommended Priority:** Sprint actual (2026-04-21)
