## 2. Enabled Capability
**CAP-001:** Gestión de Transición de Estados de Cotización
**Business Value:** Asegura la integridad financiera de las cotizaciones al evitar aprobaciones prematuras o con datos no validados. Reduce errores y retrabajos en el proceso de ventas.
**Requires:** CAP-002 (Cálculo de Cotización), CAP-003 (Gestión de Estados de Cotización)
**Enables:** CAP-004 (Aprobación de Cotización), CAP-005 (Generación de Pedido a partir de Cotización)
**Orchestrates:** N/A

## 3. User Story
Como un **usuario**,
Quiero que el sistema me impida aprobar una cotización si no ha sido previamente calculada,
Para asegurar que solo se aprueban cotizaciones con información financiera validada.

## 4. Functional Description
**Description:** Esta historia de usuario implementa una regla de negocio crítica para el proceso de gestión de cotizaciones. Su objetivo es garantizar que una cotización solo pueda pasar al estado "Aprobada" si ha alcanzado previamente el estado "Calculada". El sistema debe validar el estado actual de la cotización antes de permitir el cambio a "Aprobada", mostrando un mensaje de error claro si la transición no es válida. Esto previene la aprobación de cotizaciones con datos financieros incompletos o no validados, manteniendo la integridad del proceso de ventas.
**Flow:** HU-136 (Actualización Automática a Estado "Calculada") → [HU-139 - No se puede aprobar sin cálculo previo] → HU-XXX (Generación de Pedido a partir de Cotización Aprobada - *ejemplo de siguiente paso lógico*)

## 5. Expected Results


| element | description |
|---|---|
| Data | El campo 'quote_status' de la cotización se actualiza a 'Aprobada' si la condición es válida. No hay cambios en el estado si la condición no es válida. |
| States | Si la cotización está en estado 'Calculada', su estado final será 'Aprobada'. Si está en 'Borrador', 'Pendiente de Cálculo' o 'Rechazada', su estado permanecerá inalterado. |
| Notifications | Se muestra un mensaje de error en la interfaz de usuario (modal o toast) si la transición no es válida (ej. 'La cotización debe estar en estado 'Calculada' para ser aprobada.'). |
| Integrations | No se esperan integraciones directas con servicios externos como resultado de esta historia, a menos que un cambio de estado gatille un evento en un sistema externo (no especificado). |
| Kafka | Posiblemente se publique un evento 'QuoteStatusUpdated' con el nuevo estado 'Aprobada' o un 'QuoteApprovalFailed' si la validación falla (depende de la arquitectura de eventos). |
| Logs | Se generará un log de nivel INFO para transiciones exitosas a 'Aprobada'. Se generará un log de nivel WARN o ERROR para intentos fallidos de aprobación debido a un estado inválido, incluyendo el ID de la cotización y el estado actual. |
| UI | El botón/opción 'Aprobar' puede deshabilitarse si la cotización no está en estado 'Calculada'. Al intentar la acción, se mostrará un mensaje de éxito o un modal/toast con el mensaje de error correspondiente. El estado de la cotización se actualizará visualmente en la pantalla de detalle. |

**BR-001:** Regla de Transición de Aprobación de Cotización
- Description: Una cotización solo puede ser aprobada si su estado actual es "Calculada". Cualquier otro estado impide la aprobación directa.
- Trigger: Intento de cambiar el estado de una cotización a "Aprobada".
- Logic:
  ```
  FUNCTION puedeAprobarCotizacion(cotizacion: Cotizacion): boolean
    IF cotizacion.estado == "Calculada" THEN
      RETURN TRUE
    ELSE
      RETURN FALSE
    END IF
  END FUNCTION
  ```
- Implementation: Backend (Servicio de Cotizaciones, Lógica de Dominio).
- Exception: N/A

**Stepper/Breadcrumbs:** El estado actual de la cotización debe ser visible en la interfaz de usuario (ej. una etiqueta o un campo de texto) y actualizarse automáticamente tras una aprobación exitosa.

## 16. Technical Notes and Risks
**Risks:**
1.  **Complejidad de la Lógica de Estados:** La implementación de reglas de transición estrictas puede volverse compleja si el número de estados y transiciones aumenta significativamente en el futuro.
    -   Description: La gestión de las transiciones entre múltiples estados puede introducir errores si no se modela adecuadamente.
    -   Impact: Inconsistencia en los datos de las cotizaciones, procesos de negocio rotos, necesidad de retrabajo.
    -   Probability: Media.
    -   Mitigation: Utilizar un patrón de diseño como "State Machine" para encapsular la lógica de transición, asegurando que todas las reglas se apliquen de forma consistente y centralizada.
**Technical Debt:** N/A (A ser llenado por el equipo operativo según el alcance y MVP)

## 17. Criticality
**Criticality Level:** Alta
**Justification:** Esta historia es fundamental para la integridad de los datos financieros y la fiabilidad del proceso de cotización. Evita que se aprueben cotizaciones con errores o datos no validados, lo que podría tener un impacto financiero significativo en la empresa al aprobar transacciones incorrectas.
**Feature Impact:** Sin esta historia, la funcionalidad de "Gestión de Cotizaciones" carecería de una validación crítica, permitiendo la aprobación de cotizaciones inválidas y comprometiendo la confianza en el sistema y la precisión de los reportes financieros.
**Critical Dependencies:** La correcta ejecución y fiabilidad de HU-136 (Actualización Automática a Estado "Calculada") es esencial para que las cotizaciones puedan llegar al estado "Calculada" y, por ende, puedan ser aprobadas de forma legítima.
**Recommended Priority:** Sprint Actual

## 18. Identified Assumptions
1.  **Existencia de un mecanismo de cambio de estado en la UI/API**:
    -   Description: Se asume que existe una interfaz de usuario (botón "Aprobar") o un endpoint API que permite al usuario o a otro sistema intentar cambiar el estado de una cotización a "Aprobada".
    -   Impact if false: El usuario no podría interactuar con la funcionalidad, haciendo que la regla de negocio sea inútil.
    -   Requires validation from: Equipo de UX/Frontend, Equipo de Backend.
2.  **Definición clara y exhaustiva de los estados de cotización**:
    -   Description: Se asume que los estados "Borrador", "Pendiente de Cálculo", "Calculada", "Aprobada", "Rechazada" están bien definidos, son mutuamente excluyentes y cubren todos los posibles escenarios del ciclo de vida de una cotización relevante para esta historia.
    -   Impact if false: Ambigüedad en la lógica de negocio, lo que podría llevar a transiciones de estado erróneas o a la necesidad de estados adicionales no contemplados.
    -   Requires validation from: Dueño de Producto, Analistas de Negocio.
