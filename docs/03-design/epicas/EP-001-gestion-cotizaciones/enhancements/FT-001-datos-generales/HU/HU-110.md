## 3. User Story
Como un usuario,
Quiero iniciar una nueva cotización con un folio único,
Para comenzar el proceso de registro de datos.

## 4. Functional Description
**Description:** Esta historia de usuario describe el proceso mediante el cual un usuario puede iniciar la creación de una nueva cotización dentro del sistema. Al solicitar una nueva cotización, el sistema debe generar y asignar un folio único e irrepetible. La cotización se creará con un estado inicial de "Borrador" para permitir al usuario continuar con el registro de datos en etapas posteriores. La generación del folio debe ser robusta, manejando posibles reintentos, y el folio se mostrará al usuario inmediatamente después de su creación.
**Flow:** [Acceso a Interfaz de Creación de Cotizaciones] → [Esta Historia (Crear Nueva Cotización)] → [HU-XXX (Editar/Registrar Datos de Cotización)]

## 6. Acceptance Criteria
### AC-001: Generación y Asignación de Folio Único
**Description:** Valida que al solicitar una nueva cotización, el sistema genere un folio único y lo asigne correctamente a la nueva cotización.

```gherkin
Scenario: El sistema genera y asigna un folio único al crear una nueva cotización
  Given que estoy en la interfaz de creación de cotizaciones
  When solicito crear una nueva cotización
  Then se genera un folio único (ej. 'COT-20260421-0001')
  And este folio es asignado a la nueva cotización
  And el folio se muestra al usuario en la interfaz
```

### AC-002: Idempotencia en la Asignación del Folio
**Description:** Asegura que la operación de asignación de folio sea idempotente, previniendo la creación de folios duplicados o cotizaciones múltiples para una misma solicitud.

```gherkin
Scenario: La operación de asignación de folio es idempotente
  Given que se ha intentado crear una nueva cotización y se generó un folio 'COT-20260421-0002'
  When se produce un reintento de la misma solicitud de creación de cotización (con la misma transacción subyacente o identificador)
  Then no se crea un nuevo folio duplicado
  And la cotización original con el folio 'COT-20260421-0002' permanece como la única cotización creada para esa solicitud
```

### AC-003: Estado Inicial de la Cotización
**Description:** Verifica que toda nueva cotización creada inicie con el estado "Borrador".

```gherkin
Scenario: Toda nueva cotización tiene un estado inicial de "Borrador"
  Given que se ha creado exitosamente una nueva cotización con un folio único
  When consulto el estado de dicha cotización
  Then su estado inicial es "Borrador"
```

## 7. Data and Business Rules


| field | type | required | default | validation | catalog | example |
|---|---|---|---|---|---|---|
| folio | String | yes | N/A | Alfanumérico único, generado por el Servicio de Folios (ej. COT-YYYYMMDD-SEQ) | N/A | COT-20260421-0001 |
| estado | String | yes | Borrador | Debe ser uno de los valores del catálogo de estados de cotización | EstadosCotizacion (Borrador, Enviada, Aceptada, Rechazada, Cancelada) | Borrador |
| fechaCreacion | DateTime | yes | Fecha y hora actual del sistema | Formato ISO 8601 | N/A | 2026-04-21T10:30:00Z |
| usuarioCreacion | String | yes | Usuario autenticado | ID o nombre de usuario del actor | N/A | juan.perez |


**BR-001:** Generación de Folio Único
- Description: Cada nueva cotización debe tener un folio alfanumérico único e irrepetible generado por el Servicio de Folios.
- Trigger: Al solicitar la creación de una nueva cotización.
- Logic: El sistema invoca al Servicio de Folios para obtener un nuevo identificador.
- Implementation: Backend (API de Cotizaciones) interactuando con el Servicio de Folios.
- Exception: Si el Servicio de Folios no responde o devuelve un error, se debe manejar con reintentos o notificar al usuario.

**BR-002:** Estado Inicial "Borrador"
- Description: Toda nueva cotización debe ser creada con el estado por defecto "Borrador".
- Trigger: Después de la creación exitosa de un nuevo registro de cotización.
- Logic: Asignar el valor "Borrador" al campo 'estado'.
- Implementation: Backend (API de Cotizaciones).

**BR-003:** Idempotencia en la Creación de Cotización
- Description: La operación de creación de una cotización con un folio único debe ser idempotente para evitar duplicados en caso de reintentos de la misma solicitud.
- Trigger: Intentos repetidos de crear una cotización bajo las mismas condiciones de solicitud (si aplicable, por ejemplo, con un ID de transacción único).
- Logic: El sistema debe verificar si ya existe una cotización para la solicitud específica antes de crear una nueva, o el Servicio de Folios debe garantizar la unicidad incluso con reintentos.
- Implementation: Backend (API de Cotizaciones) y Servicio de Folios.

## 11. Architecture and Technical Dependencies
- **Backend (API de Cotizaciones):** Servicio principal encargado de la lógica de negocio para la creación de cotizaciones y la persistencia en la base de datos.
- **Servicio de Folios:** Componente externo (microservicio) responsable de generar folios alfanuméricos únicos y garantizar su no duplicidad.
    - Propósito: Proveer identificadores únicos.
    - Timeout: 500ms
    - Retries: 3 reintentos con backoff exponencial.
- **Base de Datos:** Persistencia de los datos de la cotización.
- **Frontend (Formulario de Creación):** Interfaz de usuario para iniciar la creación y mostrar el folio.

## 16. Technical Notes and Risks
**Risks:**
1.  **Disponibilidad del Servicio de Folios:**
    -   Descripción: Si el Servicio de Folios no está disponible, la creación de cotizaciones se bloquea.
    -   Impacto: Alta, interrupción del flujo principal de negocio.
    -   Probabilidad: Media.
    -   Mitigación: Implementar Circuit Breaker y retries con backoff exponencial. Monitoreo proactivo del Servicio de Folios. Considerar un mecanismo de generación de folios de respaldo temporal si el impacto es crítico.
2.  **Rendimiento del Servicio de Folios:**
    -   Descripción: Una alta concurrencia podría saturar el Servicio de Folios, afectando la latencia de la creación de cotizaciones.
    -   Impacto: Media, degrada la experiencia del usuario.
    -   Probabilidad: Baja a media (dependiendo del volumen).
    -   Mitigación: Optimización del Servicio de Folios, escalabilidad horizontal, pruebas de carga.
3.  **Consistencia de datos:**
    -   Descripción: Errores en la implementación de idempotencia podrían llevar a folios duplicados o registros de cotización inconsistentes.
    -   Impacto: Alta, problemas de integridad de datos y contabilidad.
    -   Probabilidad: Baja (con buena implementación y pruebas).
    -   Mitigación: Revisiones de código, pruebas de idempotencia rigurosas, uso de transacciones distribuidas o patrones de compensación si aplica.

## 17. Criticality
**Criticality Level:** Alta
**Justification:** Es el punto de entrada fundamental para cualquier actividad de cotización. Sin la capacidad de crear nuevas cotizaciones, el proceso de ventas no puede iniciarse.
**Feature Impact:** La no implementación o el fallo de esta historia bloquea completamente la funcionalidad de "Gestión de Cotizaciones" y, por extensión, partes clave del proceso de ventas.
**Critical Dependencies:** Todas las historias relacionadas con la edición, visualización, envío y gestión del ciclo de vida de una cotización dependen directamente de que esta historia funcione correctamente.
