## 2. Enabled Capability
**CAP-003:** Gestión de Estados de Cotización
**Business Value:** Asegura la trazabilidad y el estado final de las pólizas, indicando formalmente su emisión y previniendo modificaciones no deseadas.
**Requires:** CAP-002 (Gestión de Aprobación/Rechazo de Cotizaciones)

**Orchestrates:** N/A

## 3. User Story
Como un usuario,
Quiero poder establecer el estado de una cotización como "Emitida" una vez que ha sido "Aprobada",
Para indicar que la póliza ha sido formalmente emitida y es un estado terminal.

## 4. Functional Description
**Description:** Esta historia de usuario permite a un usuario cambiar el estado de una cotización de "Aprobada" a "Emitida". El estado "Emitida" es un estado terminal, lo que significa que una vez que una cotización alcanza este estado, no puede ser modificada ni su estado puede ser cambiado a ningún otro. El sistema debe validar que la cotización esté en estado "Aprobada" antes de permitir la transición a "Emitida" y debe impedir cualquier modificación o cambio de estado posterior una vez que está "Emitida".
**Flow:** [HU-137: Cambiar Manualmente Estado a "Aprobada" o "Rechazada"] → [HU-141: Establecer Estado "Emitida"] → [Notificación al cliente (posible HU futura) / Archivo de cotización]

## 6. Acceptance Criteria (3-5 criteria)
### AC-001: Transición de "Aprobada" a "Emitida"
**Description:** Valida que una cotización en estado "Aprobada" puede cambiar a "Emitida" al seleccionar la acción correspondiente.

```gherkin
Scenario: El usuario establece el estado de una cotización 'Aprobada' a 'Emitida'
  Given una cotización con ID "COT-123" en estado "Aprobada"
  When el usuario selecciona la opción "Emitir" para la cotización "COT-123"
  Then el estado de la cotización "COT-123" cambia a "Emitida"
  And el sistema muestra un mensaje de éxito
```

### AC-002: Imposibilidad de modificación en estado "Emitida"
**Description:** Valida que una cotización en estado "Emitida" no puede ser modificada.

```gherkin
Scenario: El usuario intenta modificar una cotización en estado 'Emitida'
  Given una cotización con ID "COT-124" en estado "Emitida"
  When el usuario intenta editar cualquier campo de la cotización "COT-124"
  Then el sistema impide la modificación
  And el sistema notifica que la cotización está en un estado terminal
```

### AC-003: Imposibilidad de cambiar estado a "Emitida" desde estados inválidos
**Description:** Valida que solo las cotizaciones en estado "Aprobada" pueden transicionar a "Emitida".

```gherkin
Scenario: El usuario intenta establecer una cotización en estado 'Pendiente' a 'Emitida'
  Given una cotización con ID "COT-125" en estado "Pendiente"
  When el usuario intenta cambiar el estado de la cotización "COT-125" a "Emitida"
  Then el sistema impide el cambio de estado
  And el sistema notifica que la transición no es válida desde el estado actual
```

**BR-001:** Transición de estado a "Emitida"
- Description: Una cotización solo puede transicionar al estado "Emitida" si su estado actual es "Aprobada".
- Trigger: Intento de cambio de estado de una cotización a "Emitida".
- Logic: `IF quote.status == "Aprobada" THEN quote.status = "Emitida" ELSE REJECT_TRANSITION`
- Implementation: Servicio de gestión de cotizaciones (Backend).
- Exception: N/A

**BR-002:** Estado "Emitida" como terminal
- Description: Una vez que una cotización está en estado "Emitida", no puede ser modificada ni su estado puede ser cambiado a ningún otro.
- Trigger: Intento de modificación o cambio de estado de una cotización en estado "Emitida".
- Logic: `IF quote.status == "Emitida" THEN REJECT_MODIFICATION_OR_STATE_CHANGE`
- Implementation: Servicio de gestión de cotizaciones (Backend) y lógica de UI (Frontend).
- Exception: N/A

## 10. UX and Navigation Flow
**UX Flow:**
1.  Usuario navega a la vista de detalle de una cotización.
2.  Si la cotización está en estado "Aprobada", el botón "Emitir" está visible y habilitado.
3.  Usuario hace clic en el botón "Emitir".
4.  El sistema procesa la solicitud.
5.  Si es exitoso, la página se actualiza mostrando el estado "Emitida", los campos de edición se deshabilitan y un mensaje de éxito aparece.
6.  Si falla (ej. estado inválido), se muestra un mensaje de error.

**Messages/Modals:**
*   **Éxito:** "Cotización [ID] emitida exitosamente."
*   **Error (Estado Inválido):** "No se puede emitir la cotización [ID]. El estado actual debe ser 'Aprobada'."
*   **Error (Cotización Emitida):** "La cotización [ID] ya ha sido emitida y no puede ser modificada."
*   **Advertencia (Intento de Edición):** "Esta cotización ha sido emitida y no se puede editar."

**Stepper/Breadcrumbs:** No aplica directamente, pero el estado de la cotización debe ser claramente visible en la interfaz.

## 16. Technical Notes and Risks
**Risks:**
1.  **Riesgo: Manejo inadecuado del estado terminal.**
    - Descripción: Si la lógica de negocio para el estado "Emitida" no es robusta, podría permitir modificaciones o transiciones de estado no deseadas.
    - Impacto: Inconsistencia de datos, errores en la información de la póliza emitida.
    - Probabilidad: Media
    - Mitigación: Implementar validaciones estrictas en el backend (BR-002), pruebas exhaustivas de regresión para todos los flujos de modificación y cambio de estado.
2.  **Riesgo: Problemas de concurrencia.**
    - Descripción: Múltiples usuarios intentando emitir la misma cotización simultáneamente.
    - Impacto: Errores inconsistentes para el usuario, posible corrupción de datos si no se maneja correctamente.
    - Probabilidad: Baja (dependiendo del volumen de usuarios)
    - Mitigación: Implementar control de concurrencia optimista (ej. versión de registro) o pesimista a nivel de base de datos/servicio.

**Technical Debt:** N/A para esta historia en particular.

## 17. Criticality
**Criticality Level:** Media
**Justification:** El estado "Emitida" es crucial para el ciclo de vida de la cotización, ya que marca el punto final de la negociación y el inicio de la validez de la póliza. Un fallo aquí podría impedir la formalización de pólizas.
**Feature Impact:** Sin esta funcionalidad, el proceso de formalización de pólizas no puede completarse en el sistema, dejando cotizaciones "Aprobadas" en un limbo sin un estado final claro.
**Critical Dependencies:** La emisión de pólizas formales y cualquier proceso posterior (facturación, gestión de siniestros) dependen de que una cotización pueda alcanzar este estado.
**Recommended Priority:** Sprint actual o siguiente.

## 18. Identified Assumptions
1.  **El estado "Aprobada" es el único pre-requisito para "Emitida".**
    - Descripción: Se asume que no hay otros estados intermedios o condiciones adicionales (ej. pago inicial) que deban cumplirse antes de que una cotización pueda ser emitida.
    - Impact if false: La lógica de negocio sería incompleta y podría permitir emisiones prematuras o bloquear emisiones válidas.
    - Requires validation from: Product Owner, Equipo de Negocio.
2.  **La acción de "Emitir" es manual.**
    - Descripción: Se asume que un usuario debe activar explícitamente la transición a "Emitida", y no es un proceso automático.
    - Impact if false: Se necesitaría un mecanismo de automatización (ej. un cron job, un evento externo) y la historia de usuario debería re-evaluarse.
    - Requires validation from: Product Owner, Equipo de Negocio.
3.  **El estado "Emitida" es verdaderamente terminal.**
    - Descripción: Se asume que no habrá requisitos futuros para anular, modificar o reabrir una cotización "Emitida" a través de transiciones de estado directas. Cualquier cambio posterior requeriría un nuevo proceso (ej. cancelación de póliza, nueva cotización).
    - Impact if false: La lógica de negocio actual sería demasiado restrictiva y requeriría una refactorización significativa para permitir transiciones de salida.
    - Requires validation from: Product Owner, Equipo de Negocio.
