## 1. Identificación General / General Identification
**Feature:** Gestión de Direcciones
**Capability:** CAP-012 - Validación y Autocompletado de Código Postal
**Actor:** Usuario
**Bounded Context:** Gestión de Direcciones
**Story Points:** 3

## 2. Enabled Capability
**CAP-012:** Validación y Autocompletado de Código Postal
**Business Value:** Asegurar la exactitud de las direcciones ingresadas, mejorar la experiencia del usuario al reducir errores y el tiempo de captura, y facilitar procesos posteriores que dependan de direcciones correctas (ej. envíos, facturación).
**Requires:** FT-007 (Integración con Servicios de Referencia para Catálogos de CP), FT-009 (Implementación de Reglas de Negocio y Validaciones)
**Enables:** Creación/Actualización de Direcciones de Ubicación, Cálculo de Prima por Zona de Riesgo
**Orchestrates:** Plataforma-core-ohs (Servicio de Catálogo de CP)

## 3. User Story
Como un **usuario**,
quiero **introducir el código postal de una ubicación y que se valide contra un catálogo**,
para que **asegurar la exactitud de la dirección**.

## 4. Functional Description
**Description:** El usuario ingresa un código postal en un campo de texto dedicado dentro de un formulario de dirección. El sistema debe validar este código postal contra un catálogo de códigos postales oficial, accesible a través del servicio `Plataforma-core-ohs`. Si el código postal es válido, el sistema debe autocompletar o sugerir campos relacionados como estado, ciudad y colonia. Si el código postal es inválido o inexistente, se mostrará un mensaje de error claro al usuario. La interacción debe ser eficiente, y en caso de latencia del servicio externo, se debe mostrar un indicador de carga.
**Flow:** (Captura de Dirección) → (HU-009: Validación de Código Postal) → (Continuar con Captura de Dirección o Mostrar Mensaje de Error)

## 6. Acceptance Criteria (3-5 criteria)
### AC-001: Validación de Código Postal contra Catálogo
**Description:** Valida que el código postal introducido por el usuario es correctamente verificado contra el catálogo de códigos postales.

```gherkin
Scenario: Validación exitosa de código postal contra catálogo
  Given el usuario está en el formulario de ubicación
  And el campo "Código Postal" está visible y editable
  When el usuario introduce un código postal válido (ej. "03100")
  Then el sistema valida el código postal contra el catálogo de CP a través de 'Plataforma-core-ohs'
```

### AC-002: Autocompletado de Datos Relacionados para CP Válido
**Description:** Asegura que, al introducir un código postal válido, el sistema autocompleta o sugiere datos geográficos relacionados (estado, ciudad, colonia).

```gherkin
Scenario: Autocompletado de datos geográficos para CP válido
  Given el usuario ha introducido un código postal válido (ej. "03100")
  When el sistema lo valida exitosamente
  Then los campos "Estado", "Ciudad" y "Colonia" se autocompletan o se muestran sugerencias
  And los datos autocompletados corresponden al código postal "03100" (ej. "Ciudad de México", "Benito Juárez", "Del Valle")
```

### AC-003: Manejo de Código Postal Inválido o Inexistente
**Description:** Valida que el sistema muestre un mensaje de error apropiado cuando se introduce un código postal que no existe en el catálogo o es inválido.

```gherkin
Scenario: Mostrar mensaje de error para código postal inválido
  Given el usuario está en el formulario de ubicación
  When el usuario introduce un código postal inválido o inexistente (ej. "99999" o "ABCDE")
  Then el sistema muestra un mensaje de error "El código postal ingresado no es válido o no existe."
  And los campos "Estado", "Ciudad" y "Colonia" no se autocompletan
```

## 7. Data and Business Rules


| field | type | required | default | validation | catalog | example |
|---|---|---|---|---|---|---|
| codigo_postal | String | yes |  | Regex: ^[0-9]{5}$ (5 dígitos numéricos); Validación de existencia contra catálogo de CP. | Plataforma-core-ohs | 03100 |
| estado | String | yes (si el CP es válido) |  | Basado en catálogo de CP. | Plataforma-core-ohs | Ciudad de México |
| ciudad | String | yes (si el CP es válido) |  | Basado en catálogo de CP. | Plataforma-core-ohs | Benito Juárez |
| colonia | String | yes (si el CP es válido) |  | Basado en catálogo de CP; puede ser una selección si hay múltiples colonias. | Plataforma-core-ohs | Del Valle |


**BR-001:** Validación de Formato de Código Postal
- Description: El código postal introducido debe cumplir con el formato estándar de 5 dígitos numéricos.
- Trigger: Al introducir el código postal en el campo y al intentar guardar la dirección.
- Logic: `IF length(codigo_postal) == 5 AND IS_NUMERIC(codigo_postal) THEN Válido ELSE Inválido`
- Implementation: Frontend (validación inicial) y Backend (validación final).
- Exception: N/A

**BR-002:** Validación de Existencia de Código Postal
- Description: El código postal, una vez validado su formato, debe existir en el catálogo oficial de códigos postales.
- Trigger: Después de la validación de formato, al perder el foco del campo de código postal o al hacer clic en una acción de validación/guardado.
- Logic: `CALL Plataforma-core-ohs.validatePostalCode(codigo_postal) RETURN {isValid: boolean, data: {estado, ciudad, colonias[]}}`
- Implementation: Backend (API de cotizaciones).
- Exception: Error de comunicación con `Plataforma-core-ohs`.

## 10. UX and Navigation Flow
**UX Flow:**

2.  Usuario ingresa el código postal en el campo designado.

## 11. Architecture and Technical Dependencies
- `API de cotizaciones` (Backend): Actúa como el servicio orquestador, recibiendo la solicitud de validación de CP del frontend y comunicándose con `Plataforma-core-ohs`.
- `Plataforma-core-ohs` (Servicio de Catálogo de CP):
    - Propósito: Proporcionar la fuente de verdad para los códigos postales y sus datos geográficos asociados.
    - Timeout: 500ms para la respuesta del servicio externo.
    - Retries: 1 intento de reintento con backoff exponencial en caso de fallos transitorios.
- `Frontend`: Responsable de la UI del campo de CP, la lógica de autocompletado/sugerencias, el manejo del estado de carga y la visualización de mensajes de error.
- `Circuit Breaker`: Implementación de un Circuit Breaker en el backend para la integración con `Plataforma-core-ohs` para prevenir la propagación de fallos y mejorar la resiliencia.

## 16. Technical Notes and Risks
**Risks:**
1.  **Latencia y Disponibilidad del Servicio Externo (`Plataforma-core-ohs`)**:
    - Descripción: El servicio de catálogo de CP puede experimentar alta latencia o periodos de inactividad, impactando directamente la experiencia del usuario y la eficiencia de la captura de direcciones.
    - Impacto: Retrasos en la captura, frustración del usuario, posible abandono de la operación, errores en la validación.
    - Probabilidad: Media.
    - Mitigación: Implementar Circuit Breaker y retries con backoff exponencial. Definir timeouts estrictos. Mostrar indicadores de carga claros en la UI. Considerar cacheo a corto plazo de CPs frecuentes si los datos no cambian con alta frecuencia.
2.  **Discrepancia o Desactualización de Datos del Catálogo**:
    - Descripción: El catálogo de códigos postales en `Plataforma-core-ohs` podría contener datos incorrectos o desactualizados.
    - Impacto: Validaciones incorrectas (rechazar CP válido, aceptar CP inválido), autocompletado erróneo, impacto negativo en la calidad de los datos de dirección.
    - Probabilidad: Baja a Media.
    - Mitigación: Establecer un proceso de sincronización regular con la fuente oficial de datos. Implementar monitoreo de calidad de datos y un mecanismo para reportar y corregir incidencias.

## 17. Criticality
**Criticality Level:** High
**Justification:** La exactitud de las direcciones es una base fundamental para múltiples procesos de negocio críticos (logística, facturación, atención al cliente). Una validación de CP deficiente resultaría en errores operativos costosos y una experiencia de usuario muy negativa.
**Feature Impact:** Sin una validación de CP precisa y eficiente, la funcionalidad general de "Gestión de Direcciones" sería inestable y poco confiable, afectando gravemente cualquier funcionalidad que dependa de direcciones correctas (ej. cotizaciones de envío, gestión de pedidos).
**Critical Dependencies:** Todas las historias de usuario relacionadas con la captura, almacenamiento o uso de direcciones.
**Recommended Priority:** Sprint actual (considerando la prioridad 'Alta' y la estimación de 3 puntos).

## 18. Identified Assumptions
1.  **Disponibilidad y Precisión del Servicio `Plataforma-core-ohs`**
    - Description: Se asume que el servicio `Plataforma-core-ohs` estará disponible, será confiable y proporcionará un catálogo de códigos postales actualizado y preciso en todo momento.
    - Impact if false: Validaciones erróneas, autocompletado incorrecto, impacto negativo en la experiencia del usuario y en la calidad de los datos de dirección.
    - Requires validation from: Equipo de `Plataforma-core-ohs` / Arquitectura de Datos.
2.  **Formato Consistente de Códigos Postales**
    - Description: Se asume que todos los códigos postales en el catálogo y los que serán ingresados por los usuarios seguirán un formato numérico de 5 dígitos (ej. `NNNNN`).
    - Impact if false: Fallos en la validación de formato, incluso si el CP es lógicamente correcto, o falta de detección de CPs inválidos.
    - Requires validation from: Equipo de Negocio / Equipo de `Plataforma-core-ohs`.
