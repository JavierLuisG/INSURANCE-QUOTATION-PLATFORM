## 3. User Story
Como sistema,
Quiero proporcionar mensajes de error claros y útiles cuando las validaciones fallen,
Para que pueda guiar al usuario en la corrección de los datos.

## 4. Functional Description
**Description:** Esta historia de usuario se enfoca en la presentación de mensajes de error al usuario cuando las validaciones de datos fallan. El sistema debe identificar los campos erróneos y el motivo específico del fallo, mostrando esta información de manera clara, concisa y orientada a la solución. En caso de múltiples errores, estos deben agruparse o presentarse de forma que facilite su comprensión y corrección. Los errores clasificados como críticos deben tener una distinción visual para indicar la urgencia y la necesidad de acción inmediata por parte del usuario.
**Flow:** HU-154 (Validar Datos Generales de la Cotización) / HU-155 (Validar Datos Específicos de Ubicación de Riesgo) → HU-157 (Presentación de Mensajes de Error) → HU-XXX (Corrección de Datos por el Usuario)

## 6. Acceptance Criteria (3-5 criteria)
### AC-001: Mensaje de error por campo específico
**Description:** Valida que, al fallar una validación de un campo, el sistema muestre un mensaje de error que indique claramente el campo y el motivo del fallo.

```gherkin
Scenario: Mostrar mensaje de error claro para un campo individual
  Given el usuario ha introducido datos inválidos en el campo "Nombre Cliente" (ej. vacío)
  And el sistema intenta validar los datos
  When la validación del campo "Nombre Cliente" falla
  Then el sistema muestra un mensaje de error "El campo 'Nombre Cliente' es obligatorio" junto al campo "Nombre Cliente"
  And el campo "Nombre Cliente" se resalta visualmente como erróneo
```

### AC-002: Presentación organizada de múltiples errores
**Description:** Valida que, al fallar múltiples validaciones, los errores se presenten de forma estructurada y fácil de entender.

```gherkin
Scenario: Mostrar múltiples mensajes de error de forma organizada
  Given el usuario ha introducido datos inválidos en los campos "Email" (ej. formato incorrecto) y "Teléfono" (ej. longitud incorrecta)
  And el sistema intenta validar los datos
  When múltiples validaciones fallan
  Then el sistema muestra un mensaje de error "El formato del Email es inválido" junto al campo "Email"
  And el sistema muestra un mensaje de error "El Teléfono debe tener 10 dígitos" junto al campo "Teléfono"
  And ambos campos se resaltan visualmente como erróneos
  And los mensajes de error son fáciles de identificar y asociar a su campo correspondiente
```

### AC-003: Destacar errores críticos
**Description:** Valida que los errores considerados críticos se destaquen visualmente para la acción inmediata del usuario.

```gherkin
Scenario: Destacar visualmente un error crítico
  Given el usuario ha intentado guardar una cotización sin seleccionar el "Tipo de Cobertura" (clasificado como crítico)
  And el sistema intenta validar los datos
  When la validación del campo "Tipo de Cobertura" falla y se reporta con severidad 'CRITICAL'
  Then el sistema muestra un mensaje de error "Debe seleccionar un Tipo de Cobertura" junto al campo "Tipo de Cobertura"
  And el mensaje de error y el campo se presentan con un estilo visual que indica su criticidad (ej. color rojo intenso, icono de alerta prominente)
```

**BR-001: Formato de Mensaje de Error Amigable**
- Description: Todos los mensajes de error mostrados al usuario deben ser claros, concisos, redactados en lenguaje natural y orientados a la solución, evitando jerga técnica.
- Trigger: Al generar cualquier mensaje de error para ser presentado en la interfaz de usuario.
- Logic: Los mensajes deben explicar 'qué' está mal y, si es posible, 'cómo' corregirlo.
- Implementation: Servicio de Mensajes de Error (Backend) y Componente de UI para Errores (Frontend).
- Exception: N/A

**BR-002: Mapeo de Errores a Campos de UI**
- Description: Cada error de validación debe ser mapeado correctamente a su campo de entrada correspondiente en la interfaz de usuario para una indicación visual precisa.
- Trigger: Cuando el frontend recibe una lista de errores del backend.
- Logic: Utilizar el campo `field` del objeto de error para localizar el elemento HTML correspondiente en la UI.
- Implementation: Componente de UI para Errores (Frontend).
- Exception: Errores generales del sistema que no están asociados a un campo específico.

**BR-003: Visualización Diferenciada de Errores Críticos**
- Description: Los errores clasificados con `severity: 'CRITICAL'` deben tener una representación visual claramente distintiva en la UI para enfatizar su importancia y requerir atención inmediata.
- Trigger: Al renderizar un mensaje de error con `severity: 'CRITICAL'`.
- Logic: Aplicar estilos CSS específicos (ej. color, tamaño de fuente, iconos de alerta, animaciones) que los diferencien de otros errores.
- Implementation: Componente de UI para Errores (Frontend).
- Exception: N/A

## 10. UX and Navigation Flow
**UX Flow:** Usuario interactúa con formulario → Usuario envía datos → El sistema valida los datos → Si hay errores, el sistema permanece en la misma pantalla/paso → Mensajes de error aparecen en la UI junto a los campos afectados y/o en un resumen → Usuario corrige datos → Usuario reintenta enviar.
**Messages/Modals:**
*   **Mensajes Inline:** Texto descriptivo en rojo (o color apropiado para la severidad) debajo o al lado del campo de entrada.
*   **Resumen de Errores:** Un banner o sección en la parte superior del formulario que lista todos los errores, con enlaces a los campos correspondientes. (Opcional, para formularios con muchos campos).
*   **Modales/Alertas Críticas:** Para errores que impiden la continuación y requieren una acción específica, se podría usar un modal con un mensaje claro y opciones de acción.
**Stepper/Breadcrumbs:** Los errores se muestran en el paso actual del stepper/navegación, sin forzar al usuario a retroceder o avanzar hasta que los errores sean resueltos.

## 11. Architecture and Technical Dependencies
- **Frontend (Sistema de Notificaciones/Validaciones de UI):** Componente o módulo encargado de recibir la respuesta de validación del backend, interpretar la estructura de errores y renderizar los mensajes y resaltados visuales en la interfaz. Deberá mapear los `field` del error a los IDs de los elementos HTML.
- **Backend (Servicio de Mensajes de Error):** Un servicio o capa dentro del backend que centraliza la generación y estandarización de los objetos de error. Recibe códigos de error de los validadores de negocio y devuelve objetos de error estructurados (con `errorCode`, `field`, `message`, `severity`) al frontend.
- **Validadores de Negocio:** Lógica de validación dentro de los servicios del backend (ej. en HU-154, HU-155) que invocan al Servicio de Mensajes de Error cuando una regla de negocio no se cumple.

## 13. Edge Cases and Exceptions
### Case 1: No hay errores de validación
```gherkin

  Given el usuario ha introducido datos válidos en todos los campos
  When el sistema intenta validar los datos
  Then el sistema no muestra ningún mensaje de error
  And el sistema permite continuar con la siguiente acción (ej. guardar, siguiente paso en el flujo)
```
### Case 2: Error general del sistema no asociado a un campo
```gherkin
Scenario: Mostrar un error general del sistema
  Given ocurre un error inesperado en el backend (ej. fallo de conexión a base de datos, servicio externo no disponible)
  When el sistema intenta procesar la solicitud del usuario
  Then el sistema muestra un mensaje de error general (ej. "Ocurrió un error inesperado. Por favor, intente de nuevo más tarde o contacte a soporte.")
  And este mensaje no está asociado a un campo específico, sino que se muestra en una posición destacada del formulario o como un modal.
```
### Case 3: Demasiados errores de validación
```gherkin
Scenario: Manejar un gran número de errores de validación
  Given el usuario ha introducido datos inválidos en una gran cantidad de campos (ej. >10)
  When el sistema intenta validar los datos
  Then el sistema muestra un resumen de los errores en la parte superior del formulario
  And los errores individuales se muestran inline junto a sus respectivos campos (si es viable), o el resumen proporciona enlaces directos a los campos.
  And la interfaz de usuario sigue siendo responsiva y usable.
```

## 16. Technical Notes and Risks
**Risks:**
1.  **Consistencia de Mensajes:** Si la creación y gestión de mensajes de error no se centraliza, podría haber inconsistencias en la redacción, el tono o la información proporcionada a lo largo del sistema.
    *   Impacto: Confusión del usuario, mala experiencia, aumento de tickets de soporte.
    *   Probabilidad: Media.
    *   Mitigación: Implementar un servicio centralizado de mensajes de error en el backend y un componente de UI estandarizado para la presentación.
2.  **Exposición de Información Sensible:** Un manejo inadecuado de excepciones o errores en el backend podría resultar en la exposición de detalles técnicos sensibles (ej. stack traces, nombres de tablas de DB) al usuario final.
    *   Impacto: Riesgo de seguridad, vulnerabilidad del sistema.
    *   Probabilidad: Baja (si se siguen buenas prácticas).
    *   Mitigación: Implementar una capa de filtrado o transformación de errores en el límite del sistema (ej. API Gateway, controlador REST) para asegurar que solo los mensajes seguros y amigables se envían al frontend.
3.  **Rendimiento de la UI con Múltiples Errores:** Renderizar un gran número de mensajes de error simultáneamente, especialmente con resaltados complejos, podría impactar negativamente el rendimiento y la fluidez de la interfaz de usuario.
    *   Impacto: UI lenta, mala experiencia de usuario.
    *   Probabilidad: Baja (depende del diseño del formulario y la cantidad de validaciones).
    *   Mitigación: Optimizar el componente de UI para errores, considerar estrategias de resumen o paginación para un número excesivo de errores.

## 17. Criticality
**Criticality Level:** Alta
**Justification:** La capacidad de guiar al usuario de manera efectiva cuando ocurren errores de validación es fundamental para la usabilidad del sistema y la finalización exitosa de los flujos de negocio (ej. creación de cotizaciones). Una mala gestión de errores genera frustración, abandono de tareas y aumenta la necesidad de soporte.
**Feature Impact:** La falta de mensajes de error claros y útiles bloquearía a los usuarios al intentar completar cualquier formulario o proceso de cotización, haciendo que las validaciones (HU-154, HU-155) sean ineficaces desde la perspectiva del usuario.
**Critical Dependencies:** Las historias de validación (HU-154, HU-155) dependen críticamente de esta HU para que sus resultados sean comprensibles y accionables por el usuario final.
**Recommended Priority:** Sprint actual o próximo, ya que es un habilitador clave para la usabilidad y la experiencia del usuario.

## 18. Identified Assumptions
1.  **Estructura de Errores Estandarizada desde Backend:**
    *   Description: Se asume que el backend proporcionará una estructura de datos de error consistente y estandarizada (ej. JSON con `errorCode`, `field`, `message`, `severity`) para que el frontend pueda procesarla de manera uniforme.
    *   Impact if false: El frontend requerirá lógica de mapeo compleja y propensa a errores, o la presentación de errores será inconsistente.
    *   Requires validation from: Equipo de Backend.
2.  **Clasificación de Severidad de Errores:**
    *   Description: Se asume que el equipo de negocio/producto, en conjunto con UX, definirá qué tipos de errores deben clasificarse como 'WARN', 'ERROR' o 'CRITICAL' para poder aplicar la diferenciación visual adecuada.
    *   Impact if false: La distinción visual de errores podría ser arbitraria o no alineada con las expectativas del negocio sobre la importancia de cada error.
    *   Requires validation from: Product Owner / Equipo de Negocio / UX.
3.  **Capacidad del Frontend para Resaltar Campos Dinámicamente:**
    *   Description: Se asume que el framework o librería de UI actual permite resaltar campos específicos y mostrar mensajes inline de manera eficiente y dinámica, sin requerir una refactorización mayor de los componentes de formulario existentes.
    *   Impact if false: Podría requerir un esfuerzo de implementación mayor de lo estimado o comprometer la experiencia de usuario si no se pueden aplicar los resaltados deseados.
    *   Requires validation from: Equipo de Frontend.
