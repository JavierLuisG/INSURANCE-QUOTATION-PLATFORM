## 3. User Story
Como sistema,
Quiero implementar reglas de validación para los datos específicos de cada ubicación de riesgo (ej., valor del bien, año de construcción),
Para asegurar la integridad de la información utilizada en la evaluación del riesgo.

## 4. Functional Description
**Description:** Esta historia de usuario se centra en la implementación de un conjunto de reglas de validación para los datos asociados a una ubicación de riesgo. El objetivo principal es garantizar que la información ingresada cumpla con los requisitos de negocio y técnicos antes de ser almacenada o utilizada en procesos posteriores de evaluación de riesgo. Las validaciones incluirán comprobaciones de rango para valores numéricos, consistencia para fechas (como el año de construcción) y verificación de la obligatoriedad de campos clave. El sistema debe ser capaz de identificar datos inválidos y proporcionar retroalimentación clara al usuario.
**Flow:** HU-116 (Editar Detalles de Ubicación de Riesgo) → **Esta historia (Validar Datos Específicos de Ubicación de Riesgo)** → [Guardar Ubicación de Riesgo (si la validación es exitosa)]

## 6. Acceptance Criteria (3-5 criteria)
### AC-001: Validación de rango para el valor del bien
**Description:** Este criterio valida que el campo 'valor del bien' esté dentro de un rango numérico predefinido y permitido, asegurando que los valores extremos o irreales sean rechazados.

```gherkin
Scenario: El valor del bien está dentro del rango permitido
  Given que el usuario está editando los detalles de una ubicación de riesgo
  And el campo "valor del bien" tiene un valor numérico entre 0 y 1,000,000,000
  When el sistema valida los datos de la ubicación
  Then la validación del "valor del bien" es exitosa

Scenario: El valor del bien está fuera del rango permitido
  Given que el usuario está editando los detalles de una ubicación de riesgo
  And el campo "valor del bien" tiene un valor de -100
  When el sistema valida los datos de la ubicación
  Then la validación del "valor del bien" falla
  And el sistema muestra el mensaje de error "El valor del bien debe ser un número positivo."
```

### AC-002: Validación de año de construcción
**Description:** Este criterio asegura que el año de construcción ingresado sea un año válido (número entero, no en el futuro) y consistente con los límites lógicos para la construcción de bienes.

```gherkin
Scenario: El año de construcción es válido y consistente
  Given que el usuario está editando los detalles de una ubicación de riesgo
  And el campo "año de construcción" tiene un valor numérico entre 1000 y el año actual (2026)
  When el sistema valida los datos de la ubicación
  Then la validación del "año de construcción" es exitosa

Scenario: El año de construcción es inválido (futuro)
  Given que el usuario está editando los detalles de una ubicación de riesgo
  And el campo "año de construcción" tiene un valor de 2027
  When el sistema valida los datos de la ubicación
  Then la validación del "año de construcción" falla
  And el sistema muestra el mensaje de error "El año de construcción no puede ser en el futuro."
```

### AC-003: Manejo de campos obligatorios vacíos
**Description:** Este criterio garantiza que el sistema identifique y notifique al usuario si un campo marcado como obligatorio para una ubicación de riesgo se deja vacío.

```gherkin
Scenario: Un campo obligatorio de una ubicación está vacío
  Given que el usuario está editando los detalles de una ubicación de riesgo
  And el campo "nombre de la ubicación" es obligatorio
  And el campo "nombre de la ubicación" está vacío
  When el sistema intenta guardar la ubicación
  Then el sistema muestra un mensaje de error claro "El campo 'nombre de la ubicación' es obligatorio y no puede estar vacío."
  And la ubicación no se guarda
```

| field | type | required | default | validation | catalog | example |

**BR-001:** Rango de Valor del Bien
- Description: El valor monetario asignado a un bien debe estar dentro de un rango predefinido para evitar valores erróneos o irreales.
- Trigger: Al intentar guardar o actualizar los detalles de una ubicación de riesgo.
- Logic: `valor_bien` >= 0 AND `valor_bien` <= 1,000,000,000.
- Implementation: Módulo de Validación de Datos de Ubicación (Backend).
- Exception: Si el valor está fuera del rango, se genera un error de validación.

**BR-002:** Año de Construcción Válido
- Description: El año de construcción de un bien debe ser un año válido y no puede ser en el futuro.
- Trigger: Al intentar guardar o actualizar los detalles de una ubicación de riesgo.
- Logic: `anio_construccion` es un número entero AND `anio_construccion` >= 1000 AND `anio_construccion` <= 2026 (año actual).
- Implementation: Módulo de Validación de Datos de Ubicación (Backend).
- Exception: Si el año es inválido (ej. futuro, texto, muy antiguo), se genera un error de validación.

**BR-003:** Campos Obligatorios de Ubicación
- Description: Ciertos campos son esenciales para la correcta identificación y evaluación de una ubicación de riesgo y no pueden estar vacíos.
- Trigger: Al intentar guardar o actualizar los detalles de una ubicación de riesgo.
- Logic: Para cada campo marcado como obligatorio (ej. `nombre_ubicacion`, `valor_bien`, `anio_construccion`), verificar que no esté nulo o vacío.
- Implementation: Módulo de Validación de Datos de Ubicación (Backend).
- Exception: Si un campo obligatorio está vacío, se genera un error de validación.

## 16. Technical Notes and Risks
**Risks:**
1.  **Complejidad de la configuración de reglas:** Si las reglas se hacen demasiado dinámicas y configurables, podría aumentar la complejidad del módulo de validación y la interfaz de administración.
    *   Impacto: Mayor tiempo de desarrollo, posibles errores en la aplicación de reglas, dificultad de mantenimiento.
    *   Probabilidad: Media.
    *   Mitigación: Priorizar la configuración de los parámetros clave de las reglas (ej. rangos, valores permitidos) y limitar la capacidad de definir lógica completamente nueva sin intervención de código.
2.  **Rendimiento en validaciones masivas:** Si se requiere validar un gran volumen de datos de ubicaciones de riesgo simultáneamente, la latencia podría ser un problema.
    *   Impacto: Experiencia de usuario degradada, retrasos en procesos batch.
    *   Probabilidad: Baja (para esta HU, se enfoca en validación individual).
    *   Mitigación: Diseñar el módulo de validación para ser eficiente y considerar mecanismos de validación asíncrona para cargas masivas en futuras historias.

**Technical Debt:** N/A (A ser llenado por el equipo operativo según el alcance y el MVP)

## 17. Criticality
**Criticality Level:** Alta
**Justification:** La integridad de los datos de las ubicaciones de riesgo es fundamental para la precisión de la evaluación de riesgos. Sin validaciones robustas, el sistema podría operar con información incorrecta, llevando a decisiones de negocio erróneas o a la subestimación/sobreestimación de riesgos.
**Feature Impact:** La no implementación o el fallo de esta historia impactaría directamente la fiabilidad de toda la funcionalidad de "Gestión de Riesgos", haciendo que las evaluaciones y los informes carezcan de credibilidad.
**Critical Dependencies:** Todas las historias que consuman o utilicen datos de ubicaciones de riesgo (ej. Evaluación de Riesgos, Generación de Informes).
**Recommended Priority:** Sprint actual o próximo.
