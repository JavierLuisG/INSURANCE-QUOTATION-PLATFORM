## 3. User Story
Como sistema,
Quiero que todos los parámetros y tarifas cargados estén disponibles para el Motor de Validación y el Motor Central de Cálculo,
Para asegurar que ambos motores operan con la información más reciente y correcta.

## 4. Functional Description
**Description:** Esta historia de usuario describe la necesidad de que el sistema garantice que todos los parámetros y tarifas que han sido cargados y gestionados (a través de historias previas como HU-159 a HU-163) sean accesibles de manera oportuna y consistente para el Motor de Validación y el Motor Central de Cálculo. El objetivo principal es asegurar que cualquier operación de validación o cálculo utilice siempre la versión más reciente y correcta de los datos, incluyendo cualquier actualización que pueda ocurrir.
**Flow:** [Carga y Actualización de Parámetros (HU-159 a HU-163)] → [Disponibilidad de Parámetros para Motores (HU-164)] → [Ejecución de Validación / Ejecución de Cálculo Central]

**BR-001:** Consistencia de Parámetros
- Description: Los valores de los parámetros y tarifas deben ser consistentes a través de todas las consultas realizadas por los motores, reflejando siempre la última versión activa.
- Trigger: Cada vez que un motor solicita un parámetro o tarifa.
- Logic: El sistema debe consultar la fuente de datos autoritativa (Repositorios de Parámetros) o una caché sincronizada.
- Implementation: Servicios de Consulta de Parámetros.
- Exception: N/A

**BR-002:** Vigencia de Parámetros
- Description: Los motores solo deben acceder a los parámetros y tarifas que están dentro de su período de vigencia (`fecha_vigencia_inicio` y `fecha_vigencia_fin`).
- Trigger: Cada vez que un motor solicita un parámetro o tarifa.
- Logic: `(fecha_actual >= fecha_vigencia_inicio) AND (fecha_actual <= fecha_vigencia_fin OR fecha_vigencia_fin IS NULL)`
- Implementation: Servicios de Consulta de Parámetros.
- Exception: Si se solicita un parámetro no vigente, debe retornar un error o un valor por defecto configurable.

## 11. Architecture and Technical Dependencies
- **Repositorios de Parámetros:** Base de datos o servicio de configuración que almacena los parámetros y tarifas. (e.g., PostgreSQL, MongoDB, HashiCorp Vault, Spring Cloud Config).
- **Servicios de Consulta de Parámetros:** Microservicio o módulo que expone una interfaz común para que los motores puedan consultar los parámetros.
- **Mecanismo de Caché:** Implementación de caché (e.g., Redis, Caffeine) para mejorar el rendimiento de las consultas y reducir la carga en la base de datos, con una estrategia de invalidación o actualización adecuada para asegurar la frescura de los datos.
- **Circuit Breaker:** Implementar Circuit Breaker en los motores al llamar a los Servicios de Consulta de Parámetros para manejar fallos transitorios y prevenir cascadas de errores.

### Case 2: Parámetro con formato inválido
```gherkin
Scenario: Parámetro con formato de valor inválido
  Given un parámetro 'TasaInteres' está cargado con un 'valor_parametro' que no corresponde a su 'tipo_dato' (ej. 'abc' para NUMERICO)
  And el Motor Central de Cálculo intenta utilizar 'TasaInteres'
  When el Motor Central de Cálculo recupera el parámetro y intenta parsearlo
  Then el Motor Central de Cálculo debe manejar la excepción de formato inválido
  And se debe registrar un error en los logs del Motor Central de Cálculo
```

### Case 3: Error de conexión con el repositorio de parámetros
```gherkin
Scenario: Falla en la conexión al repositorio de parámetros
  Given el Servicio de Consulta de Parámetros intenta acceder a la base de datos de parámetros
  When la conexión a la base de datos falla o se agota el tiempo de espera
  Then el Servicio de Consulta de Parámetros debe utilizar el mecanismo de caché para servir los datos (si aplica)
  And si la caché no está disponible o el parámetro no está en caché, debe retornar un error adecuado a los motores (ej. HTTP 500 Internal Server Error)
  And se debe activar el Circuit Breaker para el acceso a la base de datos
```

## 16. Technical Notes and Risks
**Risks:**
1.  **Riesgo: Rendimiento del acceso a parámetros.**
    -   Descripción: Un alto volumen de solicitudes de parámetros por parte de los motores podría generar un cuello de botella si el acceso a la fuente de datos es lento.
    -   Impacto: Ralentización de los cálculos y validaciones, afectando la experiencia del usuario y el procesamiento en tiempo real.
    -   Probabilidad: Media.
    -   Mitigación: Implementación de una capa de caché robusta con políticas de invalidación/actualización adecuadas. Optimización de las consultas a la base de datos de parámetros.
2.  **Riesgo: Inconsistencia de datos entre caché y fuente principal.**
    -   Descripción: Si la caché no se actualiza correctamente tras un cambio en los parámetros, los motores podrían operar con datos desactualizados.
    -   Impacto: Cálculos y validaciones incorrectos, resultando en errores de negocio.
    -   Probabilidad: Media.
    -   Mitigación: Implementar una estrategia de caché "write-through" o "cache-aside" con TTL (Time-To-Live) corto, o invalidación explícita de caché al actualizar parámetros.

    -   Description: Se asume que existe un mecanismo eficaz y oportuno para actualizar los parámetros y tarifas, y que estos cambios son propagados y persisten correctamente en la fuente de datos autoritativa.
