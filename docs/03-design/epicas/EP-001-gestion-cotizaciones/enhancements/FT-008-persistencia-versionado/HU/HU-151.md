## 3. User Story
Como sistema,
Quiero prevenir la sobrescritura de cambios si una versión más reciente ya fue guardada (versionado optimista),
Para evitar la pérdida de datos en ediciones concurrentes.

## 4. Functional Description
**Description:** Esta historia de usuario implementa el mecanismo de versionado optimista para las cotizaciones. Cuando un usuario intenta guardar una cotización, el sistema debe comparar el número de versión de la cotización que se está intentando guardar con la versión actual de la cotización en la base de datos. Si la versión en la base de datos es más reciente, se detecta un conflicto de concurrencia y se rechaza la operación de guardado, notificando al usuario. Si las versiones coinciden, la operación de guardado procede y se incrementa el número de versión en la base de datos.
**Flow:** HU-149 (Incrementar Versión en Ediciones de Cotización) → HU-151 (Prevenir Sobrescritura con Versionado Optimista) → (Éxito en Guardado o Notificación de Error)

**BR-001:** Lógica de Comparación de Versiones
- Description: Antes de persistir una cotización, el sistema debe comparar el número de `version` de la cotización proporcionada por el cliente con el número de `version` actual de la cotización en la base de datos.
- Trigger: Intento de guardado/actualización de una cotización.
- Logic:
  ```
  IF cotizacion_enviada.version < cotizacion_db.version THEN
    RECHAZAR_OPERACION("La cotización ha sido modificada por otro usuario.")
  ELSE IF cotizacion_enviada.version == cotizacion_db.version THEN
    PERMITIR_GUARDADO_E_INCREMENTAR_VERSION(cotizacion_db.version + 1)
  ELSE
    // Esto no debería ocurrir si el cliente siempre envía la última versión que vio.
    // Podría indicar un problema en el cliente o una versión futura que aún no se ha guardado.
    // Por simplicidad, se asume que solo se reciben versiones iguales o anteriores.
    RECHAZAR_OPERACION("Error de versión inesperado.")
  END IF
  ```
- Implementation: Backend (Lógica de Control de Concurrencia en Persistencia).

## 16. Technical Notes and Risks
**Risks:**
1.  **Riesgo: Impacto en el rendimiento:**
    *   Descripción: La verificación de la versión en cada operación de guardado podría añadir una pequeña sobrecarga.
    *   Impacto: Latencia ligeramente mayor en las operaciones de guardado.
    *   Probabilidad: Baja
    *   Mitigación: Optimizar las consultas a la base de datos y asegurar índices adecuados en el campo de versión.
2.  **Riesgo: Manejo de errores en el frontend:**
    *   Descripción: Si el frontend no maneja correctamente el mensaje de error de conflicto, la experiencia del usuario podría ser pobre.
    *   Impacto: Usuarios frustrados, posibles reintentos fallidos.
    *   Probabilidad: Media
    *   Mitigación: Definir claramente el mensaje de error y el comportamiento esperado del frontend (ej., recargar la cotización).

**Technical Debt:** N/A

## 17. Criticality
**Criticality Level:** Alta
**Justification:** Esta historia es fundamental para la integridad de los datos de las cotizaciones y para prevenir la pérdida de trabajo de los usuarios en entornos concurrentes. Sin ella, las ediciones de múltiples usuarios podrían llevar a sobrescrituras no deseadas y datos inconsistentes.
**Feature Impact:** La no implementación o el fallo de esta historia podría invalidar la fiabilidad de toda la funcionalidad de edición de cotizaciones, haciendo que el sistema sea inestable y propenso a errores graves de datos.
**Critical Dependencies:** Todas las historias que impliquen la edición o guardado de cotizaciones dependen críticamente de esta funcionalidad para la consistencia de datos.
**Recommended Priority:** Sprint actual / Próximo sprint (dada la prioridad Alta y las dependencias)
