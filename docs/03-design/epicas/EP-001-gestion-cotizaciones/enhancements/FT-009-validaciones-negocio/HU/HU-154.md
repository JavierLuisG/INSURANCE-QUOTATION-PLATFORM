## 2. Enabled Capability
**CAP-001:** Validación de Datos Generales de Cotización
**Business Value:** Reduce errores en la entrada de datos, mejora la calidad de la información de las cotizaciones, y previene inconsistencias que podrían afectar procesos posteriores como la facturación o la generación de contratos.
**Requires:** CAP-002 (Edición de Datos Generales de Cotización, asociado a HU-112)
**Enables:** CAP-003 (Guardar Cotización), CAP-004 (Generación/Procesamiento de Cotización)
**Orchestrates:** N/A

## 3. User Story
Como Sistema,
Quiero implementar reglas de validación para los datos generales de la cotización (por ejemplo, formato de RFC, rangos de vigencia),
Para asegurar la consistencia y corrección de la información inicial.

## 4. Functional Description
**Description:** Esta historia de usuario se enfoca en la implementación de las reglas de validación necesarias para los datos generales de una cotización. El sistema verificará el formato de campos clave como el RFC del cliente, la coherencia de las fechas de inicio y fin de vigencia, y la obligatoriedad de campos esenciales. Estas validaciones se aplicarán tanto en la interfaz de usuario (frontend) para proporcionar retroalimentación inmediata al usuario como en el backend para garantizar la integridad de los datos antes de su persistencia. El objetivo principal es prevenir la entrada de datos erróneos o inconsistentes, mejorando la calidad y fiabilidad de la información desde el origen.
**Flow:** HU-112 (Editar Datos Generales de la Cotización) → HU-154 (Validar Datos Generales de la Cotización) → HU-153 (Guardar Cotización Validada)

## 5. Expected Results


| element | description |
|---|---|
| Data | El estado de la cotización no se modifica ni se persiste si existen errores de validación. Los datos de la cotización solo se actualizan si cumplen con todas las reglas de validación. |
| States | Si hay errores de validación, la cotización permanece en su estado anterior (ej., 'Borrador') y el guardado es bloqueado. Si los datos son válidos, la cotización puede proceder al siguiente estado (ej., 'Lista para guardar'). |
| Notifications | Mensajes de error específicos en la interfaz de usuario indicando el campo y la naturaleza del error. No se esperan notificaciones por correo electrónico o modales de confirmación de error, solo feedback directo en la pantalla. |
| Integrations | No se esperan integraciones con servicios externos para esta validación interna. |
| Kafka | No se publican ni consumen eventos de Kafka directamente relacionados con el proceso de validación de datos generales. |
| Logs | Registros de INFO para intentos de validación exitosos y WARN/ERROR para fallos de validación, incluyendo detalles del campo, valor y regla fallida. Niveles configurables. |
| UI | Campos no válidos resaltados visualmente (ej., borde rojo), mensajes de error visibles junto a los campos afectados, y el botón de 'Guardar' deshabilitado o con un mensaje de advertencia si la cotización contiene errores de validación críticos. |


## 6. Acceptance Criteria (3-5 criteria)
### AC-001: Validación de formato de RFC
**Description:** Valida que el RFC ingresado por el usuario cumpla con el formato requerido por la autoridad fiscal (ej. SAT en México).

```gherkin
Scenario: El sistema valida el formato de un RFC
  Given el usuario ha ingresado "XAXX010101000" en el campo RFC
  When se activa la validación del campo RFC
  Then el sistema debe indicar que el RFC es válido
  And el sistema no muestra ningún mensaje de error de formato para el RFC
```

```gherkin
Scenario: El sistema rechaza un RFC con formato inválido
  Given el usuario ha ingresado "RFC_INVALIDO" en el campo RFC
  When se activa la validación del campo RFC
  Then el sistema debe indicar que el RFC es inválido
  And el sistema muestra un mensaje de error claro como "El formato del RFC es incorrecto."
```

### AC-002: Validación de rangos de vigencia
**Description:** Verifica que las fechas de inicio y fin de vigencia sean coherentes (la fecha de inicio no es posterior a la de fin) y estén dentro de rangos válidos si los hubiera.

```gherkin
Scenario: El sistema valida fechas de vigencia coherentes
  Given el usuario ha seleccionado "2026-04-21" como Fecha de Inicio de Vigencia
  And el usuario ha seleccionado "2026-05-21" como Fecha de Fin de Vigencia
  When se activa la validación de las fechas de vigencia
  Then el sistema debe indicar que las fechas de vigencia son válidas
  And el sistema no muestra ningún mensaje de error de vigencia
```

```gherkin
Scenario: El sistema rechaza fechas de vigencia inconsistentes
  Given el usuario ha seleccionado "2026-05-21" como Fecha de Inicio de Vigencia
  And el usuario ha seleccionado "2026-04-21" como Fecha de Fin de Vigencia
  When se activa la validación de las fechas de vigencia
  Then el sistema debe indicar que las fechas de vigencia son inválidas
  And el sistema muestra un mensaje de error claro como "La fecha de inicio de vigencia no puede ser posterior a la fecha de fin."
```

### AC-003: Validación de campos obligatorios
**Description:** Asegura que todos los campos marcados como obligatorios estén completos antes de permitir el guardado de la cotización.

```gherkin
Scenario: El sistema no permite guardar si un campo obligatorio está vacío
  Given el usuario está editando una cotización
  And el campo "Nombre de la Cotización" está vacío
  And todos los demás campos obligatorios son válidos
  When el usuario intenta guardar la cotización
  Then el sistema no permite el guardado
  And el sistema muestra un mensaje de error claro como "El campo 'Nombre de la Cotización' es obligatorio."
```

## 7. Data and Business Rules


| field | type | required | default | validation | catalog | example |
|---|---|---|---|---|---|---|
| rfc_cliente | string | yes | N/A | Regex RFC (persona física 13 caracteres, moral 12 caracteres) conforme al SAT. | N/A | XAXX010101000 |
| fecha_inicio_vigencia | date | yes | Fecha actual | Debe ser menor o igual a 'fecha_fin_vigencia'. No puede ser una fecha pasada (a menos que se especifique). | N/A | 2026-04-21 |

| nombre_cotizacion | string | yes | N/A | Longitud mínima 3 caracteres, máxima 100 caracteres. | N/A | Cotización de Servicios Anuales |


**BR-001:** Formato de RFC del Cliente
- Description: El RFC del cliente debe cumplir con el formato estándar del SAT para personas físicas (13 caracteres) o morales (12 caracteres).
- Trigger: Al ingresar o actualizar el campo 'rfc_cliente' y al intentar guardar la cotización.
- Logic: `IF rfc_cliente NO CUMPLE CON REGEX_RFC THEN ERROR "El formato del RFC es incorrecto."`
- Implementation: Módulo de Validación de Datos Generales (Backend) y lógica de validación en Frontend.
- Exception: N/A

**BR-002:** Coherencia de Fechas de Vigencia
- Description: La 'fecha_inicio_vigencia' no puede ser posterior a la 'fecha_fin_vigencia'.
- Trigger: Al ingresar o actualizar los campos 'fecha_inicio_vigencia' o 'fecha_fin_vigencia' y al intentar guardar la cotización.
- Logic: `IF fecha_inicio_vigencia > fecha_fin_vigencia THEN ERROR "La fecha de inicio de vigencia no puede ser posterior a la fecha de fin."`
- Implementation: Módulo de Validación de Datos Generales (Backend) y lógica de validación en Frontend.
- Exception: N/A

**BR-003:** Campos Obligatorios
- Description: Todos los campos definidos como obligatorios (ej. 'rfc_cliente', 'fecha_inicio_vigencia', 'fecha_fin_vigencia', 'nombre_cotizacion') no pueden estar vacíos o nulos.
- Trigger: Al intentar guardar la cotización.
- Logic: `IF CAMPO_OBLIGATORIO IS NULL OR EMPTY THEN ERROR "El campo '[Nombre del Campo]' es obligatorio."`
- Implementation: Módulo de Validación de Datos Generales (Backend) y lógica de validación en Frontend.
- Exception: N/A

## 10. UX and Navigation Flow
**UX Flow:** El usuario navega a la pantalla de "Edición de Datos Generales de la Cotización". A medida que ingresa datos en los campos (RFC, fechas de vigencia, nombre), el sistema realiza validaciones en tiempo real (frontend). Si se detectan errores, se muestran mensajes de error junto al campo correspondiente y el botón de "Guardar" permanece deshabilitado o con una indicación visual de que hay errores. Una vez que todos los campos obligatorios son válidos, el botón "Guardar" se habilita. Al hacer clic en "Guardar", se realiza una validación final en el backend antes de persistir la información.
**Messages/Modals:**
- Mensajes de error específicos para cada validación fallida, mostrados inline o como tooltips junto a los campos (ej., "El formato del RFC es incorrecto", "La fecha de inicio no puede ser posterior a la fecha de fin").
- Mensaje de error general si el guardado falla por múltiples validaciones en el backend (ej., "Por favor, corrige los errores en los campos resaltados.").
**Stepper/Breadcrumbs:** No aplica directamente a la validación, pero la pantalla de edición podría ser parte de un flujo de creación de cotizaciones con un stepper.

## 11. Architecture and Technical Dependencies
- **Módulo de Validación de Datos Generales (Backend):** Servicio REST que expone un endpoint para recibir y validar los datos de la cotización. Es el componente principal para la lógica de negocio de validación.
- **Módulo de Frontend (UI):** Implementará validaciones en el lado del cliente para proporcionar retroalimentación inmediata al usuario, replicando las reglas de validación del backend.
- **Servicio de Cotizaciones (Backend):** Consumirá el Módulo de Validación antes de intentar persistir o procesar la cotización.
- **Base de Datos:** Para persistir la cotización una vez que ha pasado todas las validaciones.

## 16. Technical Notes and Risks
**Risks:**
1.  **Discrepancia entre validación Frontend y Backend:**
    -   Description: Las reglas de validación implementadas en el frontend podrían diferir o estar desactualizadas respecto a las del backend, lo que llevaría a una mala experiencia de usuario (validación en frontend exitosa, pero rechazo en backend).
    -   Impact: Inconsistencia de datos, frustración del usuario, retrabajo.
    -   Probability: Media
    -   Mitigation: Asegurar la reutilización de reglas de validación (ej. a través de esquemas compartidos o librerías de validación comunes) o implementar un proceso de sincronización estricto y pruebas exhaustivas de integración entre ambos lados.
2.  **Complejidad de reglas de validación futuras:**
    -   Description: Si las reglas de validación se vuelven muy complejas o dependientes de múltiples factores (ej. reglas dinámicas por tipo de cliente), el módulo de validación actual podría no ser escalable o fácil de mantener.
    -   Impact: Dificultad para añadir nuevas reglas, errores difíciles de depurar, alto costo de mantenimiento.
    -   Probability: Baja (para esta historia, pero media a largo plazo)
    -   Mitigation: Diseñar el módulo de validación con extensibilidad en mente (ej. patrón de reglas de negocio o BRMS si la complejidad lo justifica).
**Technical Debt:** N/A (A ser definido por el equipo operativo según el alcance y el MVP).

## 17. Criticality
**Criticality Level:** Alta
**Justification:** La validación de datos es una capa fundamental para asegurar la integridad y consistencia de la información crítica de las cotizaciones. Errores o datos inconsistentes en esta etapa inicial pueden propagarse a lo largo del sistema, causando problemas significativos en procesos de negocio posteriores (ej., errores en la facturación, contratos mal generados, incumplimiento normativo).
**Feature Impact:** Sin una validación robusta, la funcionalidad completa de "Gestión de Cotizaciones" sería inestable, propensa a errores y no confiable, afectando directamente la credibilidad y usabilidad del sistema.
**Critical Dependencies:** Todas las historias de usuario que impliquen la creación, edición o procesamiento de cotizaciones dependen críticamente de que los datos generales sean válidos.
**Recommended Priority:** Sprint actual.

## 18. Identified Assumptions
1.  **Formato RFC estándar (México):**
    -   Description: Se asume que el formato de RFC a validar es el estándar mexicano (12 o 13 caracteres alfanuméricos con estructura específica definida por el SAT).
    -   Impact if false: La validación podría rechazar RFCs válidos (si el formato esperado difiere) o aceptar inválidos, lo que llevaría a problemas fiscales o de identificación del cliente.
    -   Requires validation from: Equipo de Negocio/Legal/Fiscal.
2.  **Rangos de vigencia razonables y no pasados:**
    -   Description: Se asume que las fechas de vigencia no tienen restricciones de rango extremas (ej., no se puede cotizar para más de 5 años en el futuro) y que las fechas de inicio de vigencia no pueden ser en el pasado (excepto si explícitamente se requiere para ciertas cotizaciones).
    -   Impact if false: El sistema podría permitir cotizaciones con vigencias excesivamente largas o cortas, o en el pasado, lo cual podría ser inconsistente con las políticas de negocio.
    -   Requires validation from: Equipo de Negocio.
