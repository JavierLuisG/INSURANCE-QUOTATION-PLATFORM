## 2. Enabled Capability
**CAP-001:** Gestión de Catálogos de Referencia
**Business Value:** Asegura la integridad y validez de la información de negocio (suscriptores, agentes, giros) en el sistema de cotizaciones, reduciendo errores manuales y mejorando la experiencia del usuario al seleccionar opciones.
**Requires:** N/A
**Enables:** FT-001: Creación y Edición de Datos Generales de la Cotización
**Orchestrates:** `Plataforma-core-ohs`

## 3. User Story
Como un usuario,
Quiero que el sistema consulte catálogos de suscriptores, agentes y giros desde el servicio de referencia,
Para asegurar la información de negocio.

## 4. Functional Description
**Description:** Esta historia de usuario describe la funcionalidad para que el sistema obtenga y muestre listas de selección (catálogos) para suscriptores, agentes y giros. Cuando un usuario interactúa con los campos de selección correspondientes en la interfaz de usuario, el sistema debe realizar una llamada al servicio `Plataforma-core-ohs` para obtener las opciones más recientes y válidas. Es crucial manejar los casos en que el servicio externo no esté disponible, mostrando un mensaje de error apropiado y, si se ha definido, utilizando un mecanismo de fallback para ofrecer una experiencia de usuario continua.
**Flow:** Acceso a formulario de cotización → [**HU-029: Consumir catálogos de suscriptores, agentes y giros**] → Selección de opciones de catálogo → Guardar/Editar cotización (FT-001)

**BR-001:** Mecanismo de Caché para Catálogos
- Description: Para optimizar el rendimiento y reducir la carga en el servicio `Plataforma-core-ohs`, se debe implementar un mecanismo de caché para los catálogos que se consideren estáticos o de baja frecuencia de cambio.
- Trigger: Al solicitar la carga de un catálogo.
- Logic: Antes de llamar al servicio externo, verificar si el catálogo está en caché y si no ha expirado. Si está presente y válido, devolver los datos de la caché. De lo contrario, llamar al servicio externo, almacenar la respuesta en caché y devolver los datos.
- Implementation: Componente Backend (Cliente API).
- Exception: Los catálogos que requieren estar actualizados en tiempo real o son altamente dinámicos no deben ser cacheados o deben tener un tiempo de vida (TTL) muy corto.

**BR-002:** Manejo de Fallback para Catálogos
- Description: En caso de que el servicio `Plataforma-core-ohs` no esté disponible o falle, el sistema debe tener una estrategia de fallback para evitar bloquear la interfaz de usuario.
- Trigger: Fallo en la comunicación o respuesta de `Plataforma-core-ohs`.
- Logic: Si la llamada al servicio externo falla, el sistema intentará cargar un conjunto de datos predefinido (si existe y es relevante) o mostrará un mensaje de error específico y deshabilitará el campo de selección.
- Implementation: Componente Backend (Cliente API) y Frontend (UI).
- Exception: Si no hay datos de fallback válidos o la estrategia es no tenerlos, solo se mostrará el mensaje de error.

## 11. Architecture and Technical Dependencies
- `Plataforma-core-ohs`: Servicio de referencia externo para la obtención de catálogos.
    - Propósito: Proveer listas de suscriptores, agentes y giros.
    - Timeout: 5 segundos.
    - Retries: 3 intentos con estrategia de backoff exponencial.
- Cliente API (Backend): Módulo o clase encargada de realizar las llamadas HTTP al servicio `Plataforma-core-ohs`.
- Mecanismo de Caché (Redis/Caché en memoria): Para almacenar temporalmente las respuestas de los catálogos y reducir la latencia y carga del servicio externo.
- Circuit Breaker (ej. Resilience4j/Hystrix): Implementado en el Cliente API para `Plataforma-core-ohs` para prevenir la propagación de fallos en cascada.

## 13. Edge Cases and Exceptions
### Case 1: Servicio de `Plataforma-core-ohs` no disponible y sin fallback
```gherkin
Scenario: Fallo del servicio de catálogos sin fallback
  Given que el servicio `Plataforma-core-ohs` no responde o devuelve un error irrecuperable
  And no se ha definido un mecanismo de fallback para el catálogo solicitado
  When el usuario intenta cargar un catálogo (ej. 'Suscriptores')
  Then el sistema muestra un mensaje de error claro al usuario (ej. "No se pudo cargar el catálogo de suscriptores.")
  And el campo de selección permanece deshabilitado o vacío
```

### Case 2: Catálogo vacío o sin resultados
```gherkin
Scenario: Servicio de catálogos responde con una lista vacía
  Given que el servicio `Plataforma-core-ohs` responde con una lista vacía para un catálogo específico
  When el usuario intenta cargar ese catálogo
  Then el campo de selección se muestra vacío
  And (Opcional) se muestra un mensaje informativo como "No hay opciones disponibles para este catálogo."
```

### Case 3: Catálogo extenso que requiere paginación o búsqueda
```gherkin
Scenario: Catálogo extenso con paginación/búsqueda
  Given que un catálogo (ej. 'Suscriptores') contiene un número elevado de elementos (ej. >1000)
  When el usuario interactúa con el campo de selección
  Then el frontend implementa paginación o un campo de búsqueda para filtrar las opciones
  And las llamadas al backend para obtener el catálogo incluyen parámetros de paginación/búsqueda
```

## 16. Technical Notes and Risks
**Risks:**
1.  **Disponibilidad y rendimiento de `Plataforma-core-ohs`**:
    - Descripción: La disponibilidad y el tiempo de respuesta del servicio externo pueden impactar directamente la experiencia del usuario y la capacidad de completar formularios.
    - Impacto: Imposibilidad de cargar catálogos, lentitud en la UI, frustración del usuario.
    - Probabilidad: Media.
    - Mitigación: Implementar Circuit Breaker, reintentos con backoff exponencial, monitoreo proactivo del servicio externo, y un mecanismo de fallback robusto.
2.  **Consistencia y actualización de los datos de los catálogos**:
    - Descripción: Si los datos en `Plataforma-core-ohs` no están actualizados o son inconsistentes, la información en el sistema de cotizaciones será incorrecta.
    - Impacto: Errores en la información de negocio, decisiones basadas en datos erróneos.
    - Probabilidad: Baja.
    - Mitigación: Establecer acuerdos de nivel de servicio (SLA) con el equipo de `Plataforma-core-ohs` y definir políticas de TTL para la caché que permitan una frescura de datos aceptable.
3.  **Volumen de datos en los catálogos**:
    - Descripción: Si algunos catálogos tienen un número muy elevado de elementos, su carga podría afectar el rendimiento del frontend y la red.
    - Impacto: UI lenta, consumo excesivo de memoria/red.
    - Probabilidad: Baja/Media.
    - Mitigación: Implementar paginación y/o funcionalidad de búsqueda/autocompletado en el frontend y backend para catálogos extensos.

## 18. Identified Assumptions
1.  **Estructura de datos de catálogos**:
    - Description: Se asume que la API de `Plataforma-core-ohs` para cada catálogo (suscriptores, agentes, giros) devolverá una estructura de datos consistente y predecible, incluyendo al menos un identificador único y un nombre descriptivo para cada elemento.
    - Impact if false: El frontend no podrá parsear ni mostrar correctamente las opciones, o se requerirán adaptaciones significativas en el código para cada catálogo.
    - Requires validation from: Equipo de `Plataforma-core-ohs` y Arquitectura.
2.  **Volumen de catálogos**:
    - Description: Se asume que el volumen de elementos en cada catálogo (suscriptores, agentes, giros) es manejable para una carga inicial completa en el frontend, o que el servicio `Plataforma-core-ohs` soporta parámetros de paginación/filtrado para catálogos extensos.
    - Impact if false: Problemas de rendimiento en el frontend, sobrecarga de red y posible bloqueo de la interfaz de usuario.
    - Requires validation from: Equipo de `Plataforma-core-ohs` y Producto.
3.  **Definición del mecanismo de fallback**:
    - Description: Se asume que existe una estrategia clara y un conjunto de datos de fallback predefinidos (si aplica) para cada catálogo en caso de indisponibilidad del servicio `Plataforma-core-ohs`.
    - Impact if false: La experiencia del usuario será totalmente bloqueada en caso de fallo del servicio, sin opciones alternativas.
    - Requires validation from: Producto y Arquitectura.
