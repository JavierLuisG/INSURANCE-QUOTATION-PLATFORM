## 3. User Story
Como desarrollador,
Quiero poder configurar respuestas dinámicas y escenarios de error controlados en el mock server,
Para poder facilitar pruebas de resiliencia y diferentes comportamientos del servicio externo.

## 4. Functional Description
**Description:** Esta historia de usuario permite a los desarrolladores configurar el mock server para simular comportamientos complejos de servicios externos. Esto incluye la capacidad de introducir retrasos artificiales en las respuestas, forzar respuestas de error HTTP (como 500) y generar datos con formatos incorrectos o malformados para catálogos específicos. Esta funcionalidad es crucial para validar cómo las aplicaciones consumidoras (como el cotizador) reaccionan ante condiciones de red adversas, fallos de servicio y datos inesperados, mejorando su resiliencia y manejo de errores.
**Flow:** HU-092 (Configuración básica del mock server) → HU-098 (Configuración de respuestas dinámicas y errores) → HU-XXX (Ejecución de pruebas de resiliencia y manejo de errores).

## 6. Acceptance Criteria (3-5 criteria)
### AC-001: Configurar retraso específico en la respuesta
**Description:** Valida que el desarrollador puede configurar el mock server para introducir un retraso artificial en la respuesta de un endpoint específico.

```gherkin
Scenario: El cotizador consulta un catálogo con retraso configurado
  Given el mock server está configurado y activo
  And el desarrollador ha configurado un retraso de 2 segundos para el endpoint /catalogs/productos
  When el cotizador consulta el endpoint /catalogs/productos
  Then el cotizador recibe la respuesta del catálogo después de un retraso de aproximadamente 2 segundos
```

### AC-002: Configurar respuesta de error HTTP 500
**Description:** Valida que el desarrollador puede configurar el mock server para que un endpoint devuelva un código de error HTTP específico, como 500.

```gherkin
Scenario: Simulación de error interno del servidor
  Given el mock server está configurado y activo
  And el desarrollador ha configurado el endpoint /orders/create para devolver un error HTTP 500
  When un cliente intenta crear una orden consultando /orders/create
  Then el cliente recibe una respuesta con código de estado HTTP 500
```

### AC-003: Configurar datos malformados para un catálogo
**Description:** Valida que el desarrollador puede configurar el mock server para devolver datos con un formato incorrecto o inesperado para un catálogo específico.

```gherkin
Scenario: Simulación de datos malformados para un catálogo
  Given el mock server está configurado y activo
  And el desarrollador ha configurado el endpoint /catalogs/clientes para devolver datos JSON malformados
  When el cotizador consulta el endpoint /catalogs/clientes
  Then el cotizador recibe una respuesta con datos JSON sintácticamente incorrectos
```

**BR-001:** Aplicación de Escenarios de Mock
- Description: El mock server debe aplicar la configuración de escenario más reciente o prioritaria para un endpoint dado.
- Trigger: Cada vez que el mock server recibe una solicitud para un endpoint con un escenario configurado.
- Logic:
  1. Identificar el endpoint de la solicitud.
  2. Buscar configuraciones de escenario activas para ese endpoint.
  3. Si existen múltiples, aplicar la que tenga mayor prioridad o la más reciente (TBD - definir regla de precedencia).
  4. Ejecutar el comportamiento definido (retraso, error, datos malformados).
- Implementation: Módulo de procesamiento de solicitudes del mock server.
- Exception: Si no hay configuración para el endpoint, se devuelve la respuesta por defecto.

## 16. Technical Notes and Risks
**Risks:**
1.  **Complejidad de la Interfaz de Usuario para Configuración:**
    *   Description: Diseñar una interfaz intuitiva y potente para gestionar múltiples escenarios, condiciones y prioridades puede ser complejo y tedioso para el desarrollador.
    *   Impact: Baja adopción, errores de configuración, tiempo adicional en el equipo de desarrollo.
    *   Probability: Media.
    *   Mitigation: Comenzar con una configuración simple para el MVP, iterar con feedback de desarrolladores, utilizar componentes de UI existentes, considerar una API para configuración programática avanzada.
2.  **Rendimiento del Mock Server:**
    *   Description: La aplicación de lógica condicional para escenarios dinámicos (retrasos, errores) podría introducir sobrecarga y afectar el rendimiento del mock server si no se optimiza.
    *   Impact: Pruebas más lentas, resultados inconsistentes.
    *   Probability: Baja a Media.
    *   Mitigation: Realizar pruebas de carga en el mock server, optimizar la lógica de coincidencia de rutas y aplicación de escenarios.

**Technical Debt:**
*   Inicialmente, la interfaz de configuración podría ser una interfaz de línea de comandos (CLI) o edición manual de archivos de configuración, con la intención de desarrollar una UI web completa en una historia futura.

## 17. Criticality
**Criticality Level:** Alta
**Justification:** Esta funcionalidad es fundamental para la capacidad de los equipos de desarrollo de realizar pruebas de resiliencia y validación de manejo de errores de los sistemas que consumen servicios externos. Sin ella, la calidad y robustez de las aplicaciones se verían comprometidas.
**Feature Impact:** La no implementación o el fallo de esta historia impactaría directamente la capacidad de probar escenarios críticos de fallo y latencia, lo que podría llevar a sistemas inestables en producción y una alta deuda técnica en pruebas. Es un habilitador clave para la calidad del software.
**Critical Dependencies:** Los equipos de desarrollo y QA dependen directamente de esta historia para validar sus propias historias de usuario relacionadas con la fiabilidad de los servicios.
**Recommended Priority:** Sprint actual (Dada la prioridad "Alta" indicada).

## 18. Identified Assumptions
1.  **Existencia de una interfaz para la configuración:**
    *   Description: Se asume que habrá una forma, ya sea una interfaz de usuario (UI) o una API, para que el desarrollador interactúe y configure estos escenarios en el mock server de manera eficiente.
    *   Impact if false: La configuración de los escenarios requeriría una manipulación manual de archivos o código, lo que sería ineficiente, propenso a errores y limitaría la adopción de la funcionalidad.
    *   Requires validation from: Equipo de Desarrollo del Mock Server / Arquitectura.
2.  **Identificación única de endpoints/catálogos:**
    *   Description: Se asume que los endpoints o catálogos a los que se aplicarán las configuraciones dinámicas pueden ser identificados de forma única por el mock server.
    *   Impact if false: Podría haber conflictos o ambigüedades en qué configuración aplicar, llevando a comportamientos impredecibles del mock.
    *   Requires validation from: Equipo de Desarrollo del Mock Server.
