## 3. User Story
Como desarrollador,
Quiero que al guardar los resultados del cálculo, se actualice el campo `fechaUltimaActualizacion` y el número de versión de la cotización,
Para mantener un registro de cambios y facilitar la gestión de concurrencia.

## 4. Functional Description
**Description:** Esta historia de usuario describe la necesidad de que el sistema actualice automáticamente ciertos metadatos de una cotización cada vez que se persisten los resultados de un cálculo exitoso. Específicamente, se debe actualizar el campo `fechaUltimaActualizacion` con la fecha y hora actuales y el número de versión de la cotización debe incrementarse en uno. Esta operación debe ser atómica junto con la persistencia del cálculo para asegurar la integridad de los datos y el soporte para el versionado optimista.
**Flow:** HU-060 (Cálculo de Cotización) → HU-062 (Actualización de Metadatos de Cotización al guardar cálculo) → [Siguiente historia que consuma cotización actualizada]

### AC-001: Actualización de fechaUltimaActualizacion
**Description:** Valida que el campo `fechaUltimaActualizacion` se actualiza correctamente con la fecha y hora actuales tras la persistencia de un cálculo exitoso.

```gherkin
Scenario: Actualizar fechaUltimaActualizacion al guardar cálculo

  When se guardan nuevos resultados de un cálculo exitoso para esa cotización
  Then el campo `fechaUltimaActualizacion` de la cotización se actualiza con la fecha y hora actuales
```

### AC-002: Incremento del número de versión
**Description:** Valida que el número de versión de la cotización se incrementa en uno tras la persistencia de un cálculo exitoso.

```gherkin
Scenario: Incrementar número de versión al guardar cálculo
  Given existe una cotización con versión N y resultados de cálculo persistidos previamente
  When se guardan nuevos resultados de un cálculo exitoso para esa cotización
  Then el número de versión de la cotización se incrementa a N+1
```

### AC-003: Actualización de metadatos sin cambios en resultados de cálculo
**Description:** Valida que si la cotización se guarda sin cambios en los resultados del cálculo (ej. solo una operación de guardado que activa la lógica), solo `fechaUltimaActualizacion` y la versión se actualizan.

```gherkin
Scenario: Actualizar solo metadatos si no hay cambios en resultados de cálculo

  When se invoca la operación de guardar la cotización sin cambios en los resultados de cálculo X
  Then el campo `fechaUltimaActualizacion` se actualiza con la fecha y hora actuales
  And el número de versión de la cotización se incrementa a N+1
  And los resultados de cálculo X de la cotización permanecen inalterados
```

**BR-001:** Actualización Atómica de Metadatos
- Description: La actualización de `fechaUltimaActualizacion` y `version` debe ser parte de la misma transacción atómica que la persistencia de los resultados del cálculo de la cotización.
- Trigger: Al guardar los resultados del cálculo de una cotización.
- Logic:
  ```
  FUNCTION guardarResultadosCalculo(cotizacion)
    BEGIN TRANSACTION
      PERSISTIR(cotizacion.resultadosCalculo)
      cotizacion.fechaUltimaActualizacion = FECHA_HORA_ACTUAL
      cotizacion.version = cotizacion.version + 1
      PERSISTIR(cotizacion) // o actualizar
    COMMIT TRANSACTION
    ON ERROR ROLLBACK TRANSACTION
  ```
- Implementation: Repositorio de cotizaciones, Módulo de actualización de metadatos
- Exception: Si la persistencia falla, no se deben actualizar los metadatos.

## 16. Technical Notes and Risks
**Risks:**
1.  **Riesgo: Fallo en la atomicidad de la operación.**
    -   Descripción: Si la actualización de metadatos no es atómica con la persistencia del cálculo, podría haber inconsistencias de datos (cálculo guardado pero metadatos no actualizados o viceversa).
    -   Impacto: Datos inconsistentes, fallos en la detección de concurrencia, dificultad en el seguimiento de cambios.
    -   Probabilidad: Media (si no se implementa una transacción adecuada).
    -   Mitigación: Asegurar el uso de transacciones de base de datos para encapsular ambas operaciones (persistencia y actualización de metadatos).
2.  **Riesgo: Problemas de rendimiento por actualización de metadatos.**
    -   Descripción: La actualización de `fechaUltimaActualizacion` y `version` podría añadir una sobrecarga mínima a cada operación de guardado.
    -   Impacto: Aumento ligero en la latencia de las operaciones de guardado.
    -   Probabilidad: Baja (generalmente es una operación de bajo costo).
    -   Mitigación: Monitorear el rendimiento; optimizar las consultas de actualización si es necesario.

## 17. Criticality
**Criticality Level:** Alta
**Justification:** La funcionalidad es esencial para mantener la integridad de los datos, el registro de cambios históricos y, crucialmente, para el correcto funcionamiento del mecanismo de versionado optimista (FT-014), que es clave para la gestión de concurrencia en un entorno multiusuario.
**Feature Impact:** Sin esta actualización, la gestión de cotizaciones carecería de un registro de su última modificación y el versionado optimista sería ineficaz, lo que podría llevar a la pérdida de datos o a la sobreescritura de cambios.
**Critical Dependencies:** FT-014 (Versionado Optimista). Cualquier historia que dependa de un control de concurrencia o de un registro de la última modificación de una cotización.
**Recommended Priority:** Sprint actual (dada su prioridad "Alta" y su papel fundamental en la integridad y concurrencia).
