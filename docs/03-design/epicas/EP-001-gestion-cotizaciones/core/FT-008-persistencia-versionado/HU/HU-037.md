## 3. User Story
Como desarrollador,
quiero implementar un mecanismo de versionado optimista,
para prevenir la pérdida de datos por ediciones concurrentes de la misma cotización.

## 4. Functional Description
**Description:** El sistema implementará un mecanismo de versionado optimista para prevenir conflictos de datos cuando múltiples usuarios intentan editar la misma cotización simultáneamente. Cada cotización tendrá un identificador de versión (número de versión o ETag). Al guardar una cotización, el sistema validará que el identificador de versión enviado por el usuario coincide con la versión actual en la base de datos. Si las versiones no coinciden, la operación de guardado será rechazada, y el usuario será notificado para que recargue la versión más reciente y resuelva el conflicto.
**Flow:** Edición de Cotización → HU-037 (Validación de Versionado Optimista) → Notificación de Conflicto / Guardado Exitoso

## 6. Acceptance Criteria
### AC-001: Rechazo de Edición Concurrente
**Description:** Valida que el sistema impide guardar una versión desactualizada de una cotización cuando se detecta un conflicto de concurrencia.

```gherkin
Scenario: El sistema rechaza la operación si la cotización ha sido modificada
  Given dos usuarios intentan editar y guardar la misma cotización simultáneamente
  And el primer usuario guarda sus cambios exitosamente
  When el segundo usuario intenta guardar una versión desactualizada de la cotización
  Then el sistema rechaza la operación de guardado del segundo usuario
  And el estado de la cotización en la base de datos permanece como la versión guardada por el primer usuario
```

### AC-002: Notificación al Usuario sobre Conflicto
**Description:** Asegura que el usuario es informado claramente cuando una operación es rechazada debido a un conflicto de versionado optimista.

```gherkin
Scenario: Notificación al usuario sobre el conflicto de edición
  Given una operación de guardado ha sido rechazada por versionado optimista
  When el sistema detecta el rechazo
  Then el sistema notifica al usuario que "La cotización ha sido modificada por otro usuario. Por favor, recargue para ver la versión más reciente."
```

### AC-003: Resolución de Conflicto por Recarga
**Description:** Verifica que el usuario puede resolver el conflicto recargando la versión más reciente de la cotización.

```gherkin
Scenario: El usuario puede ver la versión más reciente después de recargar
  Given se ha rechazado una operación por versionado optimista
  And el usuario ha sido notificado del conflicto
  When el usuario afectado decide recargar la cotización
  Then el sistema muestra al usuario la versión más reciente de la cotización
```

**BR-001:** Validación de Versionado Optimista
- Description: Antes de persistir cualquier cambio en una cotización, el sistema debe verificar que el número de versión (o ETag) proporcionado en la solicitud de actualización coincide con el número de versión actual almacenado para esa cotización en la base de datos.
- Trigger: Al intentar guardar o actualizar una cotización.
- Logic:
  ```
  IF cotizacion.version_en_solicitud != cotizacion.version_actual_en_db THEN
      RECHAZAR OPERACION
      LANZAR EXCEPCION DE CONFLICTO DE CONCURRENCIA (HTTP 409 Conflict)
  ELSE
      INCREMENTAR cotizacion.version_actual_en_db EN 1
      GUARDAR CAMBIOS EN LA COTIZACION
  END IF
  ```
- Implementation: Backend (capa de persistencia/servicio de Cotizaciones).
- Exception: Excepción de Conflicto de Concurrencia.

## 10. UX and Navigation Flow
**UX Flow:**
1.  Usuario A abre el formulario de edición de una Cotización (con `version_number` N).
2.  Usuario B modifica y guarda la misma Cotización, incrementando su `version_number` a N+1.
3.  Usuario A intenta guardar sus cambios (basados en la versión N).
4.  El sistema detecta el conflicto de versión.
5.  Se muestra una `Modal/Toast de Notificación` al Usuario A con el mensaje: "La cotización ha sido modificada por otro usuario. Por favor, recargue para ver la versión más reciente."
6.  Usuario A hace clic en un botón "Recargar" o cierra la notificación.
7.  El sistema carga la versión N+1 de la Cotización en el formulario de Usuario A.
**Messages/Modals:** "La cotización ha sido modificada por otro usuario. Por favor, recargue para ver la versión más reciente."
**Stepper/Breadcrumbs:** No aplica directamente a esta historia.

## 13. Edge Cases and Exceptions
### Case 1: Múltiples reintentos de guardar una versión desactualizada
```gherkin
Scenario: Usuario intenta guardar repetidamente una versión desactualizada
  Given el usuario ha sido notificado de un conflicto de versión
  And el usuario no ha recargado la cotización
  When el usuario intenta guardar sus cambios nuevamente sin recargar la versión más reciente
  Then el sistema rechaza la operación de guardado
  And el sistema muestra la misma notificación de conflicto al usuario
```
### Case 2: Errores de red durante la recarga de la cotización
**Description:** Si, después de un conflicto, el usuario intenta recargar la cotización, pero ocurre un error de red o de comunicación con el backend.
**Expected Response:** El sistema debe manejar el error de red mostrando un mensaje apropiado al usuario (e.g., "Error al cargar la cotización. Por favor, inténtelo de nuevo.") y no cargar una versión corrupta o antigua.

## 16. Technical Notes and Risks
**Risks:**
1.  **Complejidad en la resolución del conflicto por el usuario:**
    *   Description: La estrategia actual de "recargar y volver a aplicar cambios" puede ser frustrante para el usuario si ha realizado muchos cambios.
    *   Impact: Mala experiencia de usuario, posible pérdida de trabajo y abandono de la edición.
    *   Probability: Media.
    *   Mitigation: Para futuras iteraciones, considerar explorar estrategias más avanzadas de resolución de conflictos (e.g., fusión de cambios) o al menos proporcionar un mensaje más instructivo y opciones. Para esta HU, la recarga es el mecanismo definido.
2.  **Rendimiento:**
    *   Description: Aunque la verificación de versión es generalmente rápida, si no se implementa de manera eficiente, podría añadir una latencia mínima a las operaciones de guardado.
    *   Impact: Pequeño aumento en el tiempo de respuesta de las operaciones de guardado.
    *   Probability: Baja.
    *   Mitigation: Monitorear el rendimiento de las operaciones de guardado después de la implementación para asegurar que no hay degradación significativa.
