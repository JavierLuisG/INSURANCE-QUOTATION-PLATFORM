## 3. User Story
Como usuario,
Quiero configurar parámetros específicos para cada cobertura seleccionada (e.g., sumas aseguradas, deducibles),
Para ajustar con precisión el alcance y las condiciones de la protección.

## 4. Functional Description
**Description:** Esta historia permite al usuario configurar valores detallados para los parámetros asociados a las coberturas de seguro que ha seleccionado previamente. Una vez que se activa una cobertura que requiere configuración (como "Robo" que pide una "Suma Asegurada"), el sistema habilitará los campos correspondientes en la interfaz de usuario. El usuario podrá ingresar valores para estos parámetros (e.g., suma asegurada, deducible), los cuales serán validados contra rangos predefinidos. Al guardar, estos valores se persistirán y se asociarán a la cobertura específica y a la ubicación dentro de la cotización.
**Flow:** HU-122 (Seleccionar y Deseleccionar Coberturas por Ubicación) → HU-123 (Configurar Parámetros Específicos de Cobertura) → HU-XXX (Revisar Resumen de Cotización)

## 6. Acceptance Criteria (3-5 criteria)
### AC-001: Habilitación Dinámica de Campos de Parámetros
**Description:** Valida que los campos de configuración de parámetros se activen correctamente solo cuando se selecciona una cobertura que los requiere.

```gherkin
Scenario: Habilitar campos de configuración de parámetros al activar una cobertura
  Given que he seleccionado una cobertura que requiere la configuración de parámetros (e.g., "Robo de Contenido")
  When activo la cobertura "Robo de Contenido"
  Then se habilitan los campos específicos para configurar sus valores (e.g., "Suma Asegurada de Contenido", "Deducible por Robo")
```

### AC-002: Persistencia Exitosa de Parámetros de Cobertura
**Description:** Valida que los valores de los parámetros de cobertura ingresados por el usuario se guarden correctamente en el sistema, asociados a la cobertura y la ubicación.

```gherkin
Scenario: Persistir valores de parámetros de cobertura válidos
  Given que los campos de parámetros para una cobertura están habilitados
  And he ingresado valores válidos en los parámetros de cobertura (e.g., Suma Asegurada = 150000, Deducible = 500)
  When guardo la configuración de la póliza
  Then estos valores se persisten correctamente junto con la cobertura y la ubicación en el sistema
```

### AC-003: Notificación de Error por Valores Fuera de Rango
**Description:** Valida que el sistema notifique al usuario con un mensaje de error claro cuando los valores ingresados para los parámetros de cobertura estén fuera de los rangos de validación predefinidos.

```gherkin
Scenario: Notificación de error al ingresar valores de parámetros fuera de rango
  Given que estoy configurando los parámetros de una cobertura
  And la suma asegurada tiene un rango de validación entre 10,000 y 1,000,000
  When ingreso un valor para la suma asegurada de 5,000
  Then el sistema me notifica con un mensaje de error: "La Suma Asegurada debe estar entre 10,000 y 1,000,000."
  And no me permite guardar la configuración hasta corregir el valor
```

**BR-001: Rango de Suma Asegurada por Cobertura**
- Description: Para cada tipo de cobertura, existe un rango predefinido de valores mínimos y máximos para la suma asegurada que el usuario puede configurar.
- Trigger: Al ingresar o modificar la suma asegurada para una cobertura específica.
- Logic: `valorSumaAsegurada >= Rango.minSumaAsegurada(coberturaId) && valorSumaAsegurada <= Rango.maxSumaAsegurada(coberturaId)`
- Implementation: Servicio de Cotizaciones (Backend), posiblemente utilizando reglas gestionadas por HU-165.
- Exception: Mensaje de error al usuario si el valor está fuera de rango.

**BR-002: Rango de Deducible por Cobertura**
- Description: Para cada tipo de cobertura, existe un rango predefinido de valores mínimos y máximos para el deducible que el usuario puede configurar.
- Trigger: Al ingresar o modificar el deducible para una cobertura específica.
- Logic: `valorDeducible >= Rango.minDeducible(coberturaId) && valorDeducible <= Rango.maxDeducible(coberturaId)`
- Implementation: Servicio de Cotizaciones (Backend).
- Exception: Mensaje de error al usuario si el valor está fuera de rango.

## 10. UX and Navigation Flow
**UX Flow:** Pantalla de "Selección de Coberturas" (HU-122) → Activación de una cobertura con parámetros → Habilitación dinámica de campos de entrada en la misma pantalla o en un modal/panel lateral → Ingreso de valores → Validación en tiempo real o al guardar → Botón "Guardar Parámetros" → Mensaje de confirmación o error.
**Messages/Modals:**
- Mensaje de éxito: "Parámetros de la cobertura [Nombre Cobertura] guardados exitosamente."
- Mensaje de error de validación: "El valor de [Parámetro] ([Valor Ingresado]) está fuera del rango permitido ([Min]-[Max])."
- Mensaje de error general: "No se pudieron guardar los parámetros de cobertura. Intente nuevamente."
**Stepper/Breadcrumbs:** Esta funcionalidad se insertaría dentro de un paso más grande de "Configuración de Póliza", por ejemplo: "Datos del Asegurado" → "Ubicaciones" → "Coberturas y Parámetros" → "Revisión".

## 11. Architecture and Technical Dependencies
- **Frontend (Campos de Entrada de Parámetros):** Responsable de la renderización dinámica de los campos de entrada, la habilitación/deshabilitación, y posiblemente validaciones de formato básicas en el cliente.
- **Backend (API de Cotizaciones para persistencia de parámetros):** Un microservicio RESTful que expone endpoints para:
    - Recuperar los rangos de validación por cobertura.
    - Recibir y validar los parámetros de cobertura ingresados.
    - Persistir los parámetros, asociándolos a la cobertura y ubicación de la cotización.
- **HU-165 (Validar Rangos de Sumas Aseguradas):** Implica que el backend debe tener acceso a un repositorio o servicio de reglas de negocio que define los rangos de validación para sumas aseguradas y deducibles por cada tipo de cobertura.
- **Base de Datos:** Para almacenar los parámetros configurados para cada cobertura y ubicación dentro de una cotización.

## 16. Technical Notes and Risks
**Notas de Implementación:**
- La interfaz debe mostrar claramente qué parámetros son configurables para cada cobertura, posiblemente mediante un diseño adaptable que muestre/oculte campos dinámicamente.
- La lógica de validación de rangos debe ser robusta y extensible, idealmente configurable externamente para evitar cambios en el código para cada ajuste de rango.
**Risks:**
1.  **Complejidad de la UI/UX:**
    - Descripción: Si hay muchas coberturas con diferentes combinaciones de parámetros, la interfaz puede volverse abrumadora y difícil de usar.
    - Impacto: Baja adopción, errores del usuario, retrabajo de UI.
    - Probabilidad: Media.
    - Mitigación: Trabajar de cerca con UX para diseñar una interfaz intuitiva, quizás usando modales, paneles colapsables o un diseño por pasos.
2.  **Mantenimiento de Rangos de Validación:**
    - Descripción: La gestión y actualización de los rangos de validación para cada parámetro por cobertura puede ser compleja y requerir una solución robusta (como un BRMS o configuración centralizada).
    - Impacto: Datos incorrectos, necesidad de despliegues frecuentes, cálculos de prima erróneos.
    - Probabilidad: Media.
    - Mitigación: Asegurar que HU-165 proporcione una solución flexible para la gestión de reglas de negocio, y que esta historia la integre correctamente.

## 17. Criticality
**Criticality Level:** Medium
**Justification:** Esta historia es fundamental para ofrecer un producto de seguro personalizado y con valor añadido. Aunque una cotización básica podría existir sin ella, la capacidad de ajustar sumas aseguradas y deducibles es clave para satisfacer las necesidades específicas del cliente y para que la póliza sea atractiva y competitiva.
**Feature Impact:** La no implementación o el fallo de esta funcionalidad limitaría severamente la capacidad de personalización de las pólizas, reduciendo la propuesta de valor y la flexibilidad del sistema de cotizaciones.
**Critical Dependencies:** Depende de la selección de coberturas y es un prerrequisito para el cálculo preciso de la prima y la emisión de una póliza personalizada.
**Recommended Priority:** Sprint actual o próximo, dada su importancia estratégica para la personalización del producto.

## 18. Identified Assumptions
1.  **Existencia y Definición de Coberturas Configurables:**
    - Description: Se asume que el catálogo de coberturas incluye coberturas que requieren parámetros específicos (e.g., suma asegurada, deducibles) y que estos requisitos están claramente definidos.
    - Impact if false: Si no hay coberturas con parámetros o si no están bien definidos, la historia perdería su propósito o generaría errores en tiempo de ejecución.
    - Requires validation from: Equipo de Producto, Actuarial.
2.  **Disponibilidad de Rangos de Validación:**
    - Description: Se asume que los rangos mínimos y máximos para los parámetros de cada cobertura (e.g., suma asegurada, deducible) estarán definidos y accesibles para el backend (posiblemente a través de la implementación de HU-165).
    - Impact if false: El sistema no podría validar los valores ingresados, llevando a configuraciones de pólizas incorrectas y riesgos financieros.
    - Requires validation from: Equipo de Producto, Actuarial, Equipo de Desarrollo Backend (para la integración con la fuente de reglas).
3.  **Interfaz de Usuario Intuitiva:**
    - Description: Se asume que la interfaz de usuario será diseñada de manera que la habilitación de campos y la entrada de parámetros sea clara, intuitiva y no genere confusión al usuario.
    - Impact if false: Frustración del usuario, configuración de pólizas erróneas, necesidad de rediseño de UI.
    - Requires validation from: Equipo de UX/UI, Producto.
