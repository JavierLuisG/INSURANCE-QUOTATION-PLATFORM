## 3. User Story
Como sistema,
Quiero verificar que cada ubicación candidata a cálculo tenga los datos mínimos requeridos,
Para determinar su `estadoValidacion` y si puede incluirse en el proceso de cálculo.

## 4. Functional Description
**Description:** Esta historia describe el proceso automático por el cual el sistema evalúa cada ubicación de riesgo antes de que se incorpore en un cálculo. La validación se centra en asegurar la presencia y validez de tres datos mínimos: un `codigoPostal` válido, la `giro.claveIncendio` definida, y al menos una garantía marcada como tarifable. El resultado de esta evaluación actualiza el campo `estadoValidacion` de la ubicación a `COMPLETA` o `INCOMPLETA`. Si la ubicación es `INCOMPLETA`, se registra una lista de los campos faltantes en `alertasBloqueantes`. Es importante destacar que una ubicación incompleta no bloquea el cálculo de las demás ubicaciones que sí cumplan los criterios.
**Flow:** [HU-116: Editar Detalles de Ubicación de Riesgo] → [HU-167: Verificar Datos Mínimos Requeridos por Ubicación] → [HU-125: Iniciar Proceso de Cálculo de Prima]

## 6. Acceptance Criteria (3-5 criteria)
### AC-001: Ubicación con datos mínimos completos
**Description:** Valida que una ubicación que cumple con todos los requisitos de datos mínimos sea marcada como `COMPLETA` y apta para el cálculo.

```gherkin
Scenario: Ubicación con todos los datos mínimos requeridos
  Given una ubicación candidata a cálculo
  And la ubicación tiene un `codigoPostal` válido
  And la ubicación tiene una `giro.claveIncendio` definida
  And la ubicación tiene al menos una garantía tarifable (esTarifable: true)
  When el sistema valida los datos mínimos de la ubicación
  Then la ubicación se marca con `estadoValidacion: COMPLETA`
  And la ubicación puede ser incluida en el proceso de cálculo
```

### AC-002: Ubicación con datos mínimos incompletos
**Description:** Valida que una ubicación a la que le falte al menos uno de los datos mínimos sea marcada como `INCOMPLETA` y se registren los campos faltantes.

```gherkin
Scenario: Ubicación con datos mínimos faltantes
  Given una ubicación candidata a cálculo
  And falta al menos uno de los datos mínimos requeridos (ej. `codigoPostal`, `giro.claveIncendio`, garantías tarifables)
  When el sistema valida los datos mínimos de la ubicación
  Then la ubicación se marca con `estadoValidacion: INCOMPLETA`
  And el sistema registra los campos faltantes en `alertasBloqueantes`
```

### AC-003: Ubicaciones incompletas no bloquean el cálculo de las demás
**Description:** Valida que la presencia de ubicaciones `INCOMPLETA` no impida que otras ubicaciones `COMPLETA` participen en el cálculo.

```gherkin
Scenario: Ubicación incompleta no interfiere con el cálculo de otras ubicaciones
  Given un conjunto de ubicaciones candidatas a cálculo
  And al menos una ubicación ha sido marcada con `estadoValidacion: INCOMPLETA`
  And otras ubicaciones han sido marcadas con `estadoValidacion: COMPLETA`
  When se inicia el proceso de cálculo
  Then las ubicaciones con `estadoValidacion: COMPLETA` son procesadas para el cálculo
  And las ubicaciones con `estadoValidacion: INCOMPLETA` son excluidas del cálculo, pero no detienen el proceso general
```

**BR-001:** Definición de Datos Mínimos Requeridos
- Description: Establece los criterios específicos que una ubicación debe cumplir para ser considerada "COMPLETA" y apta para el cálculo.
- Trigger: Al iniciar la validación de una ubicación candidata a cálculo.
- Logic: Una ubicación es "COMPLETA" si cumple **TODAS** las siguientes condiciones:
    1.  `codigoPostal` es válido.
    2.  `giro.claveIncendio` está presente y es válida.
    3.  La lista de `garantias` contiene al menos una garantía con `esTarifable` = `true`.
- Implementation: Módulo de Reglas de Validación (Backend).
- Exception: Si alguna condición no se cumple, la ubicación se marca como "INCOMPLETA".

**BR-002:** Registro de Alertas Bloqueantes
- Description: Define cómo se registran los campos faltantes o inválidos cuando una ubicación no cumple los datos mínimos.
- Trigger: Cuando una ubicación no cumple la BR-001.
- Logic: Por cada condición no cumplida en BR-001, se añade el nombre del campo correspondiente a la lista `alertasBloqueantes`.
- Implementation: Módulo de Reglas de Validación (Backend).
- Exception: N/A

## 16. Technical Notes and Risks
**Risks:**
1.  **Riesgo: Complejidad y rendimiento de la validación de `codigoPostal`.**
    - Description: La validación de la validez de un `codigoPostal` puede ser compleja, requiriendo lógica de negocio específica o una integración con un servicio externo de geolocalización/validación de direcciones. Esto podría impactar el rendimiento.
    - Impact: Mayor tiempo de desarrollo, posibles errores de validación, cuello de botella en el proceso de cálculo.
    - Probability: Media
    - Mitigation: Definir claramente el alcance de la validación de `codigoPostal` con el Product Owner. Considerar el uso de librerías existentes o un servicio de validación de CP con SLA adecuado. Optimizar la consulta si es una validación interna.
2.  **Riesgo: Escalabilidad del Módulo de Reglas de Validación.**
    - Description: Si el volumen de ubicaciones a validar simultáneamente es muy alto, el módulo de reglas podría convertirse en un cuello de botella.
    - Impact: Retrasos en el proceso de cálculo, degradación del rendimiento general del sistema.
    - Probability: Media
    - Mitigation: Diseñar el módulo para ser escalable horizontalmente. Evaluar la posibilidad de procesamiento asíncrono o por lotes para grandes volúmenes.

**Technical Debt:** N/A (A ser llenado por el equipo operativo según el alcance y MVP)

## 17. Criticality
**Criticality Level:** High
**Justification:** Esta historia es crítica porque es el guardián de la calidad de los datos para el proceso de cálculo de riesgo. Sin una validación adecuada, el sistema podría intentar realizar cálculos con información incompleta o incorrecta, lo que llevaría a resultados erróneos y decisiones de negocio potencialmente perjudiciales.
**Feature Impact:** La no implementación o un fallo en esta historia comprometería la fiabilidad y utilidad de toda la funcionalidad de cálculo de riesgo.
**Critical Dependencies:** El proceso de cálculo de riesgo depende directamente de la ejecución exitosa de esta validación.
**Recommended Priority:** Sprint actual (dada la prioridad "Alta" y su impacto en el cálculo principal).

## 18. Identified Assumptions
1.  **Definición de "codigoPostal válido"**
    - Description: Se asume que existe una definición clara y un mecanismo (interno o externo) para determinar la validez de un `codigoPostal`.
    - Impact if false: Si no hay una definición o mecanismo, la validación será incompleta o incorrecta, comprometiendo la calidad de los datos.
    - Requires validation from: Product Owner, Equipo Técnico (para el alcance técnico).
2.  **Disponibilidad de datos de ubicación**
    - Description: Se asume que las ubicaciones candidatas a cálculo, con todos sus atributos (`codigoPostal`, `giro.claveIncendio`, `garantias`), están disponibles y correctamente persistidas en el sistema (ej. por HU-116).
    - Impact if false: La validación no podrá ejecutarse correctamente si los datos no están accesibles o con el formato esperado.
    - Requires validation from: Equipo Técnico, Product Owner (para la estructura de datos).
3.  **Uso posterior de `alertasBloqueantes`**
    - Description: Se asume que la información registrada en `alertasBloqueantes` será utilizada posteriormente (ej. para informar a un usuario, para reportes de calidad de datos, etc.).
    - Impact if false: Si esta información no tiene un uso definido, el esfuerzo de registrarla podría ser innecesario.
    - Requires validation from: Product Owner.
