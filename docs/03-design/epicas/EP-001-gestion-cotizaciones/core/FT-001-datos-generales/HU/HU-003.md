## 3. User Story
Como un **usuario**,
quiero **introducir el nombre y RFC del asegurado**,
para que **identificar correctamente al cliente en la cotización**.

## 4. Functional Description
**Description:** Esta historia de usuario permite al usuario introducir el nombre completo y el Registro Federal de Contribuyentes (RFC) del asegurado dentro de la sección de datos generales de una cotización. El sistema debe validar el formato del RFC tanto en el frontend como en el backend para asegurar su corrección, y el nombre debe ser aceptado y persistido. En caso de un RFC inválido, se notificará al usuario con un mensaje de error.
**Flow:** [Creación de Cotización (si existiera una US previa)] → **[HU-003: Capturar y validar datos generales del asegurado]** → [Introducción de Datos del Vehículo/Cobertura]

**BR-001:** Validación de formato de RFC
- Description: El RFC introducido por el usuario debe cumplir con el formato estándar del Registro Federal de Contribuyentes de México.
- Trigger: Al introducir un valor en el campo "RFC" (validación frontend) y al intentar guardar la cotización (validación backend).
- Logic: Implementar una expresión regular que valide la estructura del RFC (personas físicas y morales).
- Implementation: Frontend (JavaScript/TypeScript), Backend (API de cotizaciones en el servicio de validación de datos).
- Exception: Si el formato no es válido, se impide el guardado y se notifica al usuario.

## 16. Technical Notes and Risks
**Risks:**
1.  **Complejidad de la validación de RFC:**
    -   Descripción: La validación de RFC puede ser compleja debido a las diferentes estructuras para personas físicas y morales, y reglas para homoclaves.
    -   Impacto: Errores en la validación pueden llevar a datos incorrectos o rechazo de RFC válidos, afectando la experiencia del usuario y la integridad de los datos.
    -   Probabilidad: Media
    -   Mitigación: Utilizar una librería de validación de RFC probada o una expresión regular bien documentada y exhaustivamente testeada. Asegurar que la validación sea consistente entre frontend y backend.
2.  **Inconsistencia entre validaciones frontend y backend:**
    -   Descripción: Diferencias en la lógica de validación de RFC entre el frontend y el backend pueden generar una mala experiencia de usuario (ej. el frontend acepta algo que el backend rechaza).
    -   Impacto: Frustración del usuario, aumento de errores reportados.
    -   Probabilidad: Baja (si se implementa cuidadosamente)
    -   Mitigación: Reutilizar la misma lógica de validación o asegurar que las reglas sean idénticas y se prueben conjuntamente.

**Technical Debt:** [To be filled by operating team per scope and MVP]
- Considerar un servicio centralizado de validación de datos maestros para RFC en el futuro, si el sistema crece y requiere validaciones más complejas o integraciones con servicios externos (ej. SAT).

## 17. Criticality
**Criticality Level:** Alta
**Justification:** La identificación correcta del asegurado mediante su nombre y RFC es fundamental para cualquier proceso de cotización y emisión de pólizas de seguro. Sin estos datos validados, la cotización carece de validez legal y operativa, impidiendo el avance del proceso de negocio.
**Feature Impact:** La no implementación o el fallo de esta historia impide la creación de cotizaciones válidas y el avance en el proceso de contratación de seguros, deteniendo la funcionalidad principal del módulo de cotizaciones.
**Critical Dependencies:** Todas las historias de usuario subsiguientes que requieran la identificación del asegurado dependen críticamente de esta.
**Recommended Priority:** Sprint actual / Inmediata (dada la prioridad 'Alta' del usuario).
