## 1. Identificación General
**Feature:** Configuración de Coberturas de Cotización
**Capability:** CAP-001 - Gestión de Catálogos de Garantías
**Actor:** Sistema (Primario), Usuario (Interactúa con la UI)
**Bounded Context:** Cotizaciones / Configuración de Productos
**Story Points:** 3

## 2. Enabled Capability
**CAP-001:** Gestión de Catálogos de Garantías
**Business Value:** Ofrecer opciones de garantías actualizadas y completas en la configuración de coberturas, lo que mejora la precisión, exhaustividad y personalización de las cotizaciones de seguros.
**Requires:** HU-068 (Conectividad básica), FT-020 (Simulación de Servicio Plataforma-core-ohs)
**Enables:** CAP-002 - Configuración Detallada de Coberturas
**Orchestrates:** `Plataforma-core-ohs` (o su mock)

## 3. User Story
Como **sistema**,
Quiero **recuperar el catálogo de garantías desde el servicio `Plataforma-core-ohs` (o su mock)**,
Para que **ofrecer opciones actualizadas y completas en la configuración de coberturas de la cotización**.

## 4. Functional Description
**Description:** Al iniciar el proceso de configuración de coberturas para una cotización, el sistema debe realizar una llamada al servicio externo `Plataforma-core-ohs` (o su mock en entornos de desarrollo/pruebas) para obtener la lista de todas las garantías disponibles. Esta información será procesada y presentada al usuario en la interfaz de usuario para que pueda seleccionar y asociar una o varias garantías a las coberturas de la cotización, cumpliendo con las reglas de negocio establecidas.
**Flow:** Configuración de Coberturas (Inicio) → **HU-078: Recuperar Catálogo de Garantías** → Presentación y Selección de Opciones de Garantía al Usuario

| esOpcional | boolean | yes | true | N/A | N/A | true |
| reglasCombinacion | array of objects | no | [] | Estructura JSON que define las reglas de compatibilidad/exclusión | N/A | [{"tipo": "EXCLUDE", "garantiaId": "b2c3d4e5-f6a7-8901-2345-67890abcdef0"}] |


**BR-001: Reglas de Combinación y Exclusión de Garantías**
- Description: Las garantías pueden tener reglas de negocio complejas que definen cómo pueden combinarse o si son mutuamente excluyentes con otras garantías.
- Trigger: Al seleccionar o deseleccionar una garantía en la interfaz de usuario.
- Logic: `SI (garantiaA.esExclusivaCon(garantiaB) Y garantiaB.estaSeleccionada) ENTONCES (garantiaA.deshabilitarSeleccion())` o `SI (garantiaC.esRequeridaPor(garantiaD) Y garantiaD.estaSeleccionada) ENTONCES (garantiaC.seleccionarYBloquear())`
- Implementation: Lógica de negocio implementada en el backend de cotizaciones o en el frontend para validaciones en tiempo real.
- Exception: Se muestra un mensaje de error al usuario si intenta una combinación inválida.

## 11. Architecture and Technical Dependencies
- **`Plataforma-core-ohs` (Servicio Externo)**: API REST que expone el catálogo de garantías.
    - Propósito: Obtener la lista maestra de garantías.
    - Timeout: 5000 ms.
    - Retries: 2, con estrategia de backoff exponencial.
- **FT-020 (Mock de `Plataforma-core-ohs`)**: Implementación simulada del servicio externo para desarrollo y pruebas.
- **Cliente API REST**: Módulo o librería encargada de realizar las llamadas HTTP al servicio `Plataforma-core-ohs`.
- **Capa de mapeo de datos**: Componente encargado de transformar el DTO (Data Transfer Object) del servicio externo a un modelo de dominio interno (ej. `Garantia`).
- **Repositorio de Catálogos**: Abstracción para el acceso a catálogos, que encapsula la lógica de llamada al cliente API REST y el mapeo.
- **Circuit Breaker**: Implementar un patrón Circuit Breaker (ej. Resilience4j, Hystrix) para aislar fallos del servicio `Plataforma-core-ohs`.

## 16. Technical Notes and Risks
**Risks:**
1.  **Complejidad de Reglas de Negocio para Combinación de Garantías**:
    *   Description: Las "reglas de negocio complejas para su combinación o exclusión" mencionadas pueden ser muy difíciles de modelar e implementar, llevando a errores lógicos y una experiencia de usuario deficiente.
    *   Impact: Cotizaciones incorrectas, frustración del usuario, mayor esfuerzo de desarrollo y mantenimiento.
    *   Probability: Media.
    *   Mitigation: Realizar un spike de diseño para entender la complejidad, colaborar estrechamente con el SME para definir las reglas explícitamente, considerar el uso de un Business Rule Management System (BRMS) si la complejidad es muy alta. Implementar pruebas exhaustivas para las reglas.
2.  **Disponibilidad y Latencia del Servicio `Plataforma-core-ohs`**:
    *   Description: Una baja disponibilidad o alta latencia del servicio externo podría impactar negativamente el rendimiento y la experiencia del usuario al configurar cotizaciones.
    *   Impact: Retrasos en la UI, errores, frustración del usuario.
    *   Probability: Media.
    *   Mitigation: Implementar Circuit Breaker, reintentos con backoff exponencial, mostrar indicadores de carga y mensajes de error claros. Considerar una estrategia de caché para el catálogo si sus cambios no son frecuentes.

**Technical Debt:** Si las reglas de negocio complejas se implementan de forma ad-hoc sin un patrón claro o un motor de reglas, podría generar deuda técnica en el futuro.

## 17. Criticality
**Criticality Level:** Media
**Justification:** Es una funcionalidad esencial para ofrecer opciones de garantías en las cotizaciones. Aunque una cotización básica podría crearse sin ella, la capacidad de personalizar y completar el producto de seguro se vería severamente limitada.
**Feature Impact:** Sin esta historia, la funcionalidad de "Configuración de Coberturas" no podría ofrecer garantías adicionales, lo que la haría incompleta y menos valiosa para el usuario.
**Critical Dependencies:** La interfaz de usuario que permite la configuración de coberturas depende directamente de la capacidad de recuperar y presentar este catálogo.
**Recommended Priority:** Sprint Actual (considerando su estimación y su impacto directo en una funcionalidad clave).

## 18. Identified Assumptions
1.  **Formato Consistente del Catálogo de Garantías**:
    *   Description: Se asume que el servicio `Plataforma-core-ohs` devolverá un formato de datos de garantías estable y bien documentado que nuestro sistema puede consumir y mapear a su modelo de dominio.
    *   Impact if false: Requiere mayor esfuerzo de desarrollo para el mapeo, riesgo de errores de integración si el formato cambia sin previo aviso.
    *   Requires validation from: Equipo de `Plataforma-core-ohs` y Arquitectos de Integración.
2.  **Volumen y Frecuencia de Actualización del Catálogo**:
    *   Description: Se asume que el catálogo de garantías no es excesivamente grande (miles de elementos) y no cambia con una frecuencia muy alta (ej. varias veces por minuto), lo que permitiría estrategias de caché si fuera necesario para el rendimiento.
    *   Impact if false: Problemas de rendimiento si no se cachea y hay muchas consultas; datos desactualizados si se cachea un catálogo muy volátil.
    *   Requires validation from: Product Owner y Equipo de `Plataforma-core-ohs`.
