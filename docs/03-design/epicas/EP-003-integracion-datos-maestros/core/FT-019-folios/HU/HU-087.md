## 1. Identificación General / General Identification
**Feature:** Generación de Folios
**Capability:** CAP-001 - Gestión de Secuencias Numéricas
**Actor:** Sistema (Módulo de Generación de Folios)
**Bounded Context:** Gestión de Documentos y Folios

## 2. Enabled Capability
**CAP-001:** Gestión de Secuencias Numéricas
**Business Value:** Asegura la unicidad y continuidad de los folios generados, lo cual es crítico para la integridad legal, contable y operativa de los documentos y procesos de negocio. Evita duplicados y saltos en la numeración, garantizando la trazabilidad.
**Requires:** HU-086 (Generar Folio)
**Enables:** Cualquier funcionalidad que dependa de folios únicos y consecutivos (ej. emisión de facturas, gestión de expedientes, registro de transacciones).
**Orchestrates:** Módulo de persistencia de secuencia, Base de Datos.

## 3. User Story
Como sistema,
Quiero persistir de manera segura y consistente la última secuencia numérica utilizada para la generación de folios,
Para asegurar la unicidad y continuidad de los folios, incluso después de reinicios del sistema.

## 4. Functional Description
**Description:** Esta historia de usuario describe el mecanismo mediante el cual el sistema almacenará de forma persistente la última secuencia numérica utilizada para la generación de folios. El objetivo es garantizar que, a pesar de reinicios o fallos del sistema, la continuidad de la numeración de folios se mantenga, evitando duplicados. La operación de actualización de la secuencia debe ser atómica y transaccional para asegurar la consistencia en entornos concurrentes.
**Flow:** HU-086 (Generar Folio) → HU-087 (Persistir Secuencia de Folios) → [Uso del Folio Persistido en procesos de negocio]

## 6. Acceptance Criteria (3-5 criteria)
### AC-001: Persistencia de la secuencia actualizada
**Description:** Valida que, después de la generación de un nuevo folio y la actualización de su secuencia, el nuevo número de secuencia se guarda de forma persistente y es recuperable.

```gherkin
Scenario: Persistencia exitosa de la secuencia de folio
  Given se ha generado un nuevo folio y la secuencia interna ha avanzado a N
  When el sistema intenta persistir la nueva secuencia N
  Then la secuencia N se guarda exitosamente en la base de datos o almacenamiento persistente
  And la secuencia N es recuperable y refleja el último valor actualizado
```

### AC-002: Recuperación de secuencia tras reinicio
**Description:** Valida que el sistema es capaz de recuperar la última secuencia persistida y continuar la generación de folios desde ese punto, asegurando la continuidad.

```gherkin
Scenario: Recuperación de secuencia después de un reinicio del sistema
  Given la última secuencia persistida para un tipo de folio es M
  And el sistema ha sido reiniciado
  When el sistema solicita generar un nuevo folio de ese tipo
  Then el sistema recupera la secuencia M de la base de datos
  And el siguiente folio generado utiliza la secuencia M+1
```

### AC-003: Manejo de fallos en la persistencia
**Description:** Valida que el sistema detecta y gestiona adecuadamente los fallos durante la operación de persistencia de la secuencia, registrando el error y notificando para su resolución.

```gherkin
Scenario: Fallo en la operación de persistencia de la secuencia
  Given el sistema intenta actualizar la secuencia a un valor P
  When la operación de persistencia en la base de datos falla (ej. por un problema de conexión o permisos)
  Then el sistema registra un error crítico con los detalles del fallo
  And se emite una notificación de alerta para el equipo de operaciones
  And la secuencia de folios permanece en su último estado consistente conocido antes del intento fallido
```

**BR-001:** Actualización Atómica y Transaccional de la Secuencia
- Description: La operación de incrementar y guardar la secuencia numérica debe ser atómica y transaccional para garantizar que no haya pérdidas ni duplicidades de números de folio, incluso en escenarios de alta concurrencia.
- Trigger: Cada vez que se genera un nuevo folio y se requiere persistir su secuencia actualizada.
- Logic: Utilizar mecanismos de base de datos que garanticen la atomicidad (ej. `findAndModify` en MongoDB, transacciones SQL con `SELECT ... FOR UPDATE` o `UPDATE` con cláusula `WHERE` para verificación de versión/valor). En caso de fallo de la operación atómica, se debe reintentar o registrar un error.
- Implementation: Módulo de persistencia de secuencia.
- Exception: Si la operación atómica falla repetidamente, se debe escalar el error y activar el mecanismo de notificación.

## 11. Architecture and Technical Dependencies
-   **Módulo de persistencia de secuencia**: Componente interno del servicio de generación de folios, responsable de encapsular la lógica de acceso a la base de datos para las secuencias.
-   **Base de datos (MongoDB u otra)**: Sistema de almacenamiento persistente. Debe soportar operaciones atómicas o transaccionales para la gestión de secuencias.
-   **Framework de ORM/ODM**: (Ej. Mongoose para MongoDB, TypeORM para SQL) para interactuar con la base de datos.
-   **Circuit Breaker**: Implementado para las llamadas a la base de datos, con configuración de `timeout` (ej. 200ms) y `retries` (ej. 3 reintentos con backoff exponencial) para manejar fallos temporales de la base de datos de forma resiliente.

## 13. Edge Cases and Exceptions
### Case 1: Colisión de actualizaciones concurrentes
```gherkin
Scenario: Múltiples solicitudes intentando actualizar la misma secuencia simultáneamente
  Given la secuencia actual para 'FACTURA' es 100
  And dos procesos intentan generar un nuevo folio de 'FACTURA' al mismo tiempo
  When ambos procesos intentan actualizar la secuencia a 101 de forma atómica
  Then solo uno de los procesos logra actualizar la secuencia a 101 exitosamente
  And el otro proceso recibe una indicación de conflicto o se reintenta automáticamente
  And la base de datos refleja la secuencia 101 (o 102 si el reintento fue exitoso)
```

### Case 2: Pérdida o corrupción de datos de secuencia
```gherkin
Scenario: Recuperación tras corrupción o ausencia de datos de secuencia en la base de datos
  Given la tabla/colección de secuencias de folios está vacía o un registro específico está corrupto
  When el sistema intenta recuperar la secuencia para un tipo de folio
  Then el sistema detecta la ausencia o invalidez del dato
  And registra un error crítico en los logs
  And notifica al equipo de operaciones para intervención manual
  And el sistema puede optar por detener la generación de folios o iniciar una secuencia de emergencia (ej. desde 1)
```

## 16. Technical Notes and Risks
**Risks:**
1.  **Riesgo de Duplicación de Folios (Alto):**
    *   Description: Si la operación de actualización de la secuencia no es verdaderamente atómica y transaccional, múltiples procesos concurrentes podrían obtener el mismo número de folio, llevando a duplicados.
    *   Impact: Inconsistencias graves en los datos, problemas legales y contables, pérdida de confianza en el sistema.
    *   Probability: Media si no se utilizan mecanismos de bloqueo/atomicidad robustos de la base de datos.
    *   Mitigation: Implementación estricta de operaciones atómicas (ej. `findAndModify` en MongoDB, transacciones SQL con `SELECT ... FOR UPDATE`), pruebas de carga y concurrencia rigurosas, monitoreo de folios duplicados.
2.  **Riesgo de Pérdida de Consistencia de Secuencia (Medio):**
    *   Description: Fallos en la base de datos o corrupción de datos podrían llevar a la pérdida de la última secuencia persistida, resultando en saltos o reinicios inesperados de la numeración.
    *   Impact: Interrupción del servicio de generación de folios, necesidad de intervención manual, problemas de trazabilidad.
    *   Probability: Baja con bases de datos robustas y configuraciones de alta disponibilidad.
    *   Mitigation: Replicación de base de datos, backups regulares, monitoreo de la integridad de datos, implementación de un mecanismo de recuperación y ajuste manual por parte de administradores.

**Technical Debt:** Considerar la implementación de un servicio de secuencias distribuido (ej. basado en Zookeeper o un servicio interno de secuencias con alta disponibilidad) si la demanda de folios y la criticidad de la disponibilidad aumentan considerablemente, para desacoplar la generación de folios de una única instancia de DB. (A ser evaluado por el equipo de operaciones según el alcance y MVP).

## 17. Criticality
**Criticality Level:** Alta
**Justification:** La persistencia segura y consistente de la secuencia de folios es la base para garantizar la unicidad y continuidad de los folios, un requisito fundamental para la integridad de los datos y la validez legal/contable de muchos procesos de negocio. Un fallo aquí impactaría directamente la confiabilidad del sistema.
**Feature Impact:** Sin esta historia, la funcionalidad principal de "Generación de Folios" (HU-086) es inestable e inutilizable en un entorno productivo, ya que no puede garantizar la unicidad de los folios, invalidando cualquier documento o transacción que los utilice.
**Critical Dependencies:** HU-086 (Generar Folio).
**Recommended Priority:** Sprint Actual / Inmediato.
