**Feature:** Gestión de Cotizaciones
**Capability:** CAP-007 - Gestión de Conflictos de Versión de Cotización
**Actor:** Usuario
**Bounded Context:** Cotizaciones
**Story Points:** 2

## 2. Enabled Capability
**CAP-007:** Gestión de Conflictos de Versión de Cotización
**Business Value:** Permite a los usuarios resolver conflictos de versión de cotización de manera eficiente, reduciendo la pérdida de datos y mejorando la colaboración al asegurar que siempre trabajan con la información más actualizada. Esto mejora la experiencia del usuario y la integridad de los datos.
**Requires:** CAP-006 (Notificación de Conflictos de Versión)
**Enables:** CAP-008 (Edición Colaborativa de Cotizaciones)
**Orchestrates:** N/A

## 3. User Story
Como un **usuario**,
Quiero que el sistema me permita **recargar la cotización con la última versión desde la base de datos en caso de conflicto**,
Para poder **ver los cambios de otros usuarios y reintentar mis propias modificaciones**.

## 4. Functional Description
**Description:** Esta historia de usuario describe la funcionalidad que permite a un usuario actualizar su vista de una cotización a la última versión disponible en la base de datos. Esto ocurre específicamente cuando el usuario ha sido notificado de un conflicto de versión (por ejemplo, si otro usuario ha modificado la misma cotización). Al hacer clic en un botón de "Recargar", el sistema recuperará la versión más reciente de la cotización y actualizará la interfaz de usuario, mostrando los cambios realizados por otros usuarios. Posteriormente, el usuario podrá intentar guardar sus propias modificaciones sobre esta versión actualizada.
**Flow:** [HU-183 Notificar Usuario de Versión Más Reciente] → [HU-184 Permitir Recargar Última Versión de Cotización] → [HU-XXX Reintentar Guardar Modificaciones]

## 5. Expected Results


| element | description |
|---|---|
| Data | El objeto de cotización en la interfaz de usuario es reemplazado por la última versión obtenida directamente de la base de datos, incluyendo todos sus campos y elementos relacionados (líneas de producto, etc.). |
| States | El estado de la interfaz de usuario cambia de 'conflicto detectado' a 'mostrando la última versión'. La cotización en el frontend refleja el estado más reciente de la base de datos. La notificación de conflicto desaparece. |
| Notifications | La notificación de conflicto previamente mostrada se oculta o elimina. No se generan nuevas notificaciones, salvo un posible mensaje de éxito de recarga si se considera necesario. |
| Integrations | Se realiza una llamada a la API interna del servicio de cotizaciones para obtener los datos más recientes de la cotización. |
| Kafka | No se esperan eventos Kafka publicados o consumidos directamente por esta acción, ya que es una operación de lectura directa. |
| Logs | Se espera un log de nivel 'INFO' registrando la operación de recarga de la cotización, indicando el ID de la cotización y el usuario que realizó la acción. |
| UI | La pantalla de detalles de la cotización se refresca completamente, mostrando los datos de la última versión. El botón 'Recargar' puede deshabilitarse temporalmente o la notificación de conflicto desaparecerá después de la recarga. |


## 6. Acceptance Criteria (3-5 criteria)
### AC-001: Recarga de cotización tras conflicto
**Description:** Valida que al recibir una notificación de conflicto y hacer clic en el botón de recarga, la cotización se actualiza con la versión más reciente de la base de datos.

```gherkin
Scenario: El usuario recarga la cotización al detectar un conflicto
  Given que el usuario está editando una cotización
  And que recibe una notificación de conflicto de versión
  When el usuario hace clic en el botón "Recargar"
  Then la cotización se carga nuevamente desde la base de datos con la versión más reciente
  And la notificación de conflicto desaparece de la interfaz de usuario
```

### AC-002: Reflejo de cambios de otros usuarios
**Description:** Valida que, una vez recargada, la cotización mostrada en la interfaz de usuario refleja fielmente los cambios que otros usuarios hayan podido realizar.

```gherkin
Scenario: La cotización recargada refleja los cambios de otros usuarios
  Given que la cotización ha sido recargada con la última versión
  And que otro usuario había realizado cambios en la cotización (ej. añadió una línea de producto)
  When la cotización se muestra en la interfaz del usuario
  Then la interfaz refleja los cambios realizados por el otro usuario (ej. la nueva línea de producto está visible)
```

### AC-003: Reintento de guardado sin nuevos conflictos
**Description:** Valida que después de recargar la cotización, el usuario puede intentar guardar sus modificaciones nuevamente sin encontrar un nuevo conflicto, a menos que haya habido otra modificación concurrente.

```gherkin
Scenario: El usuario puede reintentar guardar después de recargar
  Given que el usuario ha recargado la cotización con la última versión
  And que el usuario ha realizado nuevas modificaciones sobre la versión recargada
  And que no ha habido nuevos cambios concurrentes por otros usuarios
  When el usuario intenta guardar sus modificaciones
  Then sus cambios se guardan exitosamente en la base de datos
```

**BR-001:** Determinación de la Última Versión de Cotización
- Description: Define cómo el sistema identifica la "última versión" de una cotización en la base de datos.
- Trigger: Cada vez que se solicita una cotización para recarga o visualización.
- Logic: La versión de la cotización se determina por el campo `fechaUltimaModificacion` (timestamp de la última actualización) o por un campo `numeroVersion` incremental. El sistema siempre debe recuperar la entrada con el valor más reciente de estos campos para un `idCotizacion` dado.
- Implementation: Servicio de Cotizaciones (API REST) y capa de persistencia.
- Exception: Si no se encuentra la cotización con el `idCotizacion` proporcionado, se devuelve un error de "Cotización no encontrada".

## 10. UX and Navigation Flow
**UX Flow:**
1.  El usuario está en la pantalla de edición de una cotización.
2.  Aparece una notificación o modal indicando un conflicto de versión (proveniente de HU-183).
3.  La notificación incluye un botón o enlace con el texto "Recargar".
4.  El usuario hace clic en "Recargar".
5.  Se muestra un indicador de carga (spinner) mientras se recuperan los datos.
6.  La pantalla de edición de la cotización se actualiza con los datos de la última versión.
7.  La notificación de conflicto desaparece.
**Messages/Modals:**
*   Mensaje de éxito (opcional): "Cotización recargada con éxito."
*   Mensaje de error: "Error al recargar la cotización. Por favor, inténtelo de nuevo." (en caso de fallos de red o servidor).
**Stepper/Breadcrumbs:** No aplica directamente.

## 11. Architecture and Technical Dependencies
- **Frontend (SPA):** Lógica para la gestión del botón "Recargar", visualización de notificaciones, y actualización del estado de la interfaz de usuario con los nuevos datos de la cotización.
- **Servicio de Cotizaciones (Backend API):** Un endpoint REST (ej. `GET /api/quotes/{id}`) para recuperar la cotización por su ID.
- **Base de Datos:** La fuente de verdad para la última versión de la cotización. Se espera un sistema de control de versiones o un campo de timestamp para identificar la versión más reciente.
- **Mecanismo de Control de Concurrencia:** Requiere que el backend sea capaz de identificar y servir la versión más reciente de la cotización de forma atómica.

## 13. Edge Cases and Exceptions
### Case 1: Error en la comunicación o en el servidor al recargar
```gherkin
Scenario: Error al recargar la cotización
  Given que el usuario recibe una notificación de conflicto
  When el usuario hace clic en "Recargar"
  And ocurre un error de red o el servidor responde con un error 5xx
  Then se muestra un mensaje de error informativo al usuario ("Error al recargar la cotización. Por favor, inténtelo de nuevo.")
  And la vista de la cotización no se actualiza
```

### Case 2: La cotización ya no existe en la base de datos
```gherkin
Scenario: La cotización ya no existe al intentar recargar
  Given que el usuario recibe una notificación de conflicto para una cotización X
  And que la cotización X ha sido eliminada por otro usuario o proceso
  When el usuario hace clic en "Recargar"
  Then se muestra un mensaje de error al usuario ("La cotización ya no existe o no se pudo encontrar.")
  And la interfaz de usuario puede redirigir a una página de lista de cotizaciones o limpiar el estado.
```

### Case 3: Nuevo conflicto inmediato después de la recarga
```gherkin
Scenario: Nuevo conflicto ocurre inmediatamente después de la recarga
  Given que el usuario ha recargado la cotización con éxito
  And que otro usuario realiza una modificación en la misma cotización justo después de la recarga
  When el usuario intenta guardar sus cambios sobre la cotización recargada
  Then el sistema detecta un nuevo conflicto de versión
  And se notifica al usuario del nuevo conflicto (como si fuera la primera vez)
```

## 16. Technical Notes and Risks
**Risks:**
1.  **Riesgo: Latencia en la recarga.**
    - Descripción: Si la operación de recarga de la cotización toma demasiado tiempo debido a la complejidad de los datos o problemas de red/servidor.
    - Impacto: Mala experiencia de usuario, frustración, posible abandono de la tarea.
    - Probabilidad: Media.
    - Mitigación: Implementar optimizaciones de rendimiento en el endpoint de la API, asegurar un diseño de base de datos eficiente, usar indicadores de carga visuales.
2.  **Riesgo: Inconsistencia de datos en el frontend.**
    - Descripción: Después de la recarga, la interfaz de usuario no se actualiza completamente o muestra datos incorrectos.
    - Impacto: Datos erróneos, errores de usuario, pérdida de confianza en el sistema.
    - Probabilidad: Baja (con buen testing).
    - Mitigación: Pruebas exhaustivas de integración y E2E, manejo robusto del estado en el frontend, validación de la respuesta del backend.

## 17. Criticality
**Criticality Level:** Alta
**Justification:** Esta historia es crítica porque es una parte fundamental del flujo de resolución de conflictos de versión. Sin esta funcionalidad, los usuarios no podrían ver los cambios de otros, lo que lleva a la sobrescritura de datos, inconsistencias y una experiencia de usuario muy pobre en entornos colaborativos. Es un paso esencial para la integridad de los datos y la colaboración.
**Feature Impact:** La no implementación o fallo de esta historia hace que toda la funcionalidad de "Gestión de Conflictos de Versión de Cotización" sea inútil, ya que la notificación (HU-183) no tendría una acción de seguimiento efectiva.
**Critical Dependencies:** HU-183 (Notificar Usuario de Versión Más Reciente)
**Recommended Priority:** Sprint actual (dada su alta prioridad y dependencia crítica)

## 18. Identified Assumptions
1.  **Mecanismo de Detección de Conflictos Existente**
    - Description: Se asume que existe un mecanismo (implementado en HU-183 o previo) que es capaz de detectar cuándo la versión de la cotización que el usuario está editando difiere de la versión en la base de datos y de notificar al usuario.
    - Impact if false: Si no hay un mecanismo de detección de conflictos, la funcionalidad de "Recargar" nunca sería disparada por una notificación, haciendo que la historia sea redundante o inútil en su contexto actual.
    - Requires validation from: Equipo de Backend / Producto.
2.  **Identificación Clara de la "Última Versión"**
    - Description: Se asume que la base de datos o el servicio de persistencia tiene un método claro y consistente para identificar cuál es la "última versión" de una cotización (ej. por timestamp de última modificación, número de versión).
    - Impact if false: Si no se puede determinar la última versión de manera confiable, el sistema podría cargar una versión incorrecta o inconsistente, llevando a más conflictos o pérdida de datos.
    - Requires validation from: Equipo de Backend / Arquitectura de Datos.
3.  **Permisos de Usuario para Acceder a la Cotización**
    - Description: Se asume que el usuario que intenta recargar la cotización tiene los permisos adecuados para ver y acceder a esa cotización específica.
    - Impact if false: El usuario podría ver un mensaje de error de acceso denegado en lugar de la cotización recargada, o peor aún, acceder a cotizaciones no autorizadas.
    - Requires validation from: Equipo de Seguridad / Backend.
