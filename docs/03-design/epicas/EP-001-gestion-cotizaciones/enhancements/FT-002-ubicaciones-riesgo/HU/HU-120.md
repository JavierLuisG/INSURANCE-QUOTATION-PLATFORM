**Feature:** Gestión de Ubicaciones de Riesgo

**Actor:** Usuario

## 2. Enabled Capability
**CAP-101:** Gestión de Alertas de Datos de Ubicación
**Business Value:** Asegurar la integridad de los datos de ubicación de riesgo antes del cálculo de la prima, mejorando la precisión y reduciendo errores manuales.
**Requires:** CAP-100 (Gestión de Ubicaciones de Riesgo - Implícito), HU-116 (Editar Detalles de Ubicación de Riesgo), HU-155 (Validar Datos Específicos de Ubicación de Riesgo)
**Enables:** Cálculo de Prima
**Orchestrates:** N/A

## 3. User Story
Como un usuario,
Quiero recibir alertas visuales si una ubicación de riesgo tiene datos incompletos o inválidos,
Para saber qué información necesito completar antes de calcular la prima.

## 4. Functional Description
**Description:** Esta historia de usuario permite al sistema mostrar alertas visuales en la interfaz de usuario cuando una ubicación de riesgo presenta información faltante o incorrecta en sus campos. El propósito es guiar al usuario para que complete o corrija los datos necesarios, asegurando la validez de la información antes de proceder con el cálculo de la prima.
**Flow:** `HU-116 (Editar Detalles de Ubicación de Riesgo)` → `HU-120 (Recibir Alertas por Datos Incompletos)` → `Cálculo de Prima (una vez corregido)`

## 6. Acceptance Criteria
### AC-001: Alerta por Campos Obligatorios Vacíos
**Description:** Valida que el sistema muestra una alerta visual cuando se visualiza una ubicación con campos obligatorios vacíos.

```gherkin
Scenario: Mostrar alerta por campos obligatorios vacíos
  Given una ubicación de riesgo con campos obligatorios vacíos (e.g., 'Dirección' sin valor)
  When el usuario visualiza los detalles de dicha ubicación
  Then se muestra una alerta visual (e.g., un icono de advertencia o el campo resaltado en rojo) indicando datos incompletos
  And el mensaje de la alerta sugiere qué información necesita completarse
```

### AC-002: Alerta por Datos Inválidos
**Description:** Valida que el sistema muestra una alerta visual cuando se visualiza una ubicación con datos que no cumplen con las reglas de validación.

```gherkin
Scenario: Mostrar alerta por datos inválidos
  Given una ubicación de riesgo con datos inválidos (e.g., 'Código Postal' con formato incorrecto)
  When el usuario visualiza los detalles de dicha ubicación
  Then se muestra una alerta visual (e.g., un icono de error o el campo resaltado en naranja) indicando la inconsistencia
  And el mensaje de la alerta especifica la naturaleza de la inconsistencia (e.g., "Formato de Código Postal inválido")
```

### AC-003: Desaparición de Alerta al Corregir Datos
**Description:** Valida que la alerta visual desaparece una vez que el usuario corrige los datos incompletos o inválidos y guarda los cambios.

```gherkin
Scenario: La alerta desaparece al corregir y guardar los datos
  Given una ubicación de riesgo con una alerta visual por datos incompletos o inválidos
  When el usuario completa o corrige los datos afectados
  And el usuario guarda los cambios de la ubicación
  Then la alerta visual desaparece de la interfaz de usuario
  And la ubicación se considera válida para el cálculo de la prima
```

## 7. Data and Business Rules


| field | type | required | default | validation | catalog | example |
|---|---|---|---|---|---|---|

| ciudad | String | yes | N/A | No vacío, longitud máxima 100 | N/A | Madrid |
| pais | String | yes | N/A | Código ISO 3166-1 alpha-2 (ej. ES, US) | ISO 3166-1 alpha-2 | ES |


**BR-001:** Validación de Datos de Ubicación
- **Description:** Define las reglas para determinar si los datos de una ubicación de riesgo son completos y válidos.
- **Trigger:** Al cargar la pantalla de detalles de la ubicación y al intentar guardar los cambios en la ubicación.
- **Logic:**
    - `IF (direccion IS NULL OR direccion IS EMPTY)` THEN `ubicacion.estado_validez = 'incompleta'`
    - `IF (codigo_postal IS NULL OR codigo_postal IS EMPTY)` THEN `ubicacion.estado_validez = 'incompleta'`
    - `IF (ciudad IS NULL OR ciudad IS EMPTY)` THEN `ubicacion.estado_validez = 'incompleta'`
    - `IF (pais IS NULL OR pais IS EMPTY)` THEN `ubicacion.estado_validez = 'incompleta'`
    - `IF (codigo_postal IS NOT VALID ACCORDING TO FORMAT)` THEN `ubicacion.estado_validez = 'inválida'`
    - `ELSE` `ubicacion.estado_validez = 'válida'`
- **Implementation:** Servicio de validación de datos de ubicación (HU-155).
- **Exception:** N/A

## 10. UX and Navigation Flow
**UX Flow:**
1.  **Navegación:** El usuario accede a la pantalla de detalles de una ubicación de riesgo.
2.  **Detección de Alerta:** Si la ubicación tiene datos incompletos o inválidos, el sistema muestra inmediatamente las alertas visuales.
3.  **Interacción con Alerta:** El usuario identifica los campos con problemas gracias a los iconos, resaltados o mensajes.
4.  **Corrección:** El usuario edita los campos afectados para corregir o completar la información.
5.  **Guardar:** El usuario hace clic en el botón 'Guardar'.
6.  **Validación y Desaparición:** El sistema revalida los datos; si son correctos, las alertas desaparecen y la ubicación se marca como válida.
**Messages/Modals:**
*   Mensajes de error inline para cada campo (ej. "Este campo es obligatorio", "Formato de Código Postal incorrecto").
*   Posiblemente un mensaje de resumen en la parte superior de la pantalla si hay múltiples errores, indicando "Existen datos incompletos o inválidos en esta ubicación. Por favor, corríjalos antes de continuar."
**Stepper/Breadcrumbs:** N/A

## 13. Edge Cases and Exceptions
### Case 1: Ubicación sin datos incompletos o inválidos
```gherkin
Scenario: Visualización de ubicación con datos completos y válidos
  Given una ubicación de riesgo con todos los datos completos y válidos
  When el usuario visualiza los detalles de dicha ubicación
  Then no se muestra ninguna alerta visual de datos incompletos o inválidos
```

### Case 2: Múltiples campos incompletos e inválidos
```gherkin
Scenario: Ubicación con múltiples tipos de errores
  Given una ubicación de riesgo con 'Dirección' vacía y 'Código Postal' inválido
  When el usuario visualiza los detalles de dicha ubicación
  Then se muestra una alerta visual para el campo 'Dirección' indicando que está incompleto
  And se muestra una alerta visual para el campo 'Código Postal' indicando que es inválido
  And ambas alertas persisten hasta que los respectivos campos sean corregidos
```

## 16. Technical Notes and Risks
**Notas de Implementación:**
- Las alertas deben ser claras y no obstructivas, guiando al usuario a la acción.
- Considerar el uso de un sistema de diseño de componentes para estandarizar la apariencia de las alertas.
- La lógica de validación debe ser centralizada en el servicio de HU-155 para evitar duplicidades.

**Risks:**
1.  **Nombre:** Complejidad de la Interfaz de Usuario
    - **Descripción:** Si la lógica de validación es muy compleja o hay muchos campos, la interfaz podría llenarse de alertas, volviéndose confusa para el usuario.
    - **Impacto:** Experiencia de usuario deficiente, dificultad para identificar y corregir errores.
    - **Probabilidad:** Media
    - **Mitigación:** Priorizar los mensajes más críticos, agrupar alertas por sección, utilizar patrones de diseño de UI establecidos para validaciones, y realizar pruebas de usabilidad.

**Technical Debt:** [To be filled by operating team per scope and MVP]

## 17. Criticality
**Criticality Level:** Media
**Justification:** Esta historia es importante porque mejora la calidad de los datos y la experiencia del usuario al calcular primas, pero no bloquea completamente el flujo si los datos ya son correctos o si la validación se realiza en una etapa posterior.
**Feature Impact:** Sin esta funcionalidad, los usuarios podrían proceder con ubicaciones de riesgo con datos incompletos o inválidos, lo que podría llevar a cálculos de prima erróneos o a la necesidad de correcciones manuales posteriores, afectando la eficiencia y la precisión del sistema.
**Critical Dependencies:** Depende directamente de la existencia de la interfaz de edición de ubicaciones y del servicio de validación de datos.
**Recommended Priority:** Sprint actual o siguiente, dada su prioridad "Media" y el impacto en la calidad del dato.

## 18. Identified Assumptions
1.  **Interfaz de Usuario para Ubicaciones**
    - **Description:** Se asume que ya existe una interfaz de usuario donde se pueden visualizar y editar los detalles de una ubicación de riesgo.
    - **Impact if false:** No habría dónde mostrar las alertas visuales ni dónde el usuario podría corregir los datos.
    - **Requires validation from:** Equipo de Frontend / UX.
2.  **Servicio de Validación de Datos (HU-155)**
    - **Description:** Se asume que el servicio o la lógica para validar los datos específicos de ubicación (campos obligatorios, formatos, etc.) estará disponible y accesible para el frontend.
    - **Impact if false:** No se podrían detectar los datos incompletos o inválidos, y las alertas no se mostrarían correctamente.
    - **Requires validation from:** Equipo de Backend / Arquitectura.
