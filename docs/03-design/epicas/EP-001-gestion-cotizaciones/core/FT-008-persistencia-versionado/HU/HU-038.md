## 3. User Story
Como un **desarrollador**,
quiero que el sistema **permita la actualización parcial de los campos de la cotización**,
para **optimizar las operaciones de guardado**.

## 4. Functional Description
**Description:** Esta historia de usuario describe la necesidad de implementar una funcionalidad que permita actualizar solo un subconjunto específico de campos de una cotización existente, en lugar de requerir el objeto completo. Esto es crucial para mejorar la eficiencia del sistema, especialmente en escenarios donde solo unos pocos atributos de una cotización necesitan ser modificados. La implementación debe asegurar que los campos no modificados permanezcan intactos y que los campos de control como `version` y `fechaUltimaActualizacion` se actualicen correctamente.
**Flow:** Edición de Cotización → [HU-038] Actualización Parcial de Cotización → Cotización Actualizada

## 6. Acceptance Criteria (3-5 criteria)
### AC-001: Actualización de campos modificados
**Description:** Valida que solo los campos explícitamente enviados para la actualización parcial sean modificados en la base de datos.

```gherkin
Scenario: Actualizar solo un subconjunto de campos de una cotización
  Given existe una cotización con ID "COT-001" y campos { "estado": "Pendiente", "monto": 1000, "cliente": "ABC", "version": 1 }
  When se solicita una actualización parcial para la cotización "COT-001" con { "estado": "Aprobado", "monto": 1200 }
  Then la cotización "COT-001" en la base de datos tiene los campos { "estado": "Aprobado", "monto": 1200 }
  And el campo "cliente" de la cotización "COT-001" permanece como "ABC"
```

### AC-002: Preservación de datos no modificados
**Description:** Valida que cualquier campo de la cotización que no haya sido incluido en la solicitud de actualización parcial permanezca sin cambios.

```gherkin
Scenario: Los datos no modificados de una cotización permanecen intactos
  Given existe una cotización con ID "COT-002" y campos { "nombreProducto": "Servicio X", "descripcion": "Descripción original", "precioUnitario": 500, "cantidad": 2, "version": 1 }
  When se solicita una actualización parcial para la cotización "COT-002" con { "cantidad": 3 }
  Then el campo "descripcion" de la cotización "COT-002" en la base de datos permanece como "Descripción original"
  And el campo "nombreProducto" de la cotización "COT-002" en la base de datos permanece como "Servicio X"
  And el campo "precioUnitario" de la cotización "COT-002" en la base de datos permanece como 500
```

### AC-003: Actualización de campos de control
**Description:** Valida que los campos `version` y `fechaUltimaActualizacion` se actualicen automáticamente tras una actualización parcial exitosa.

```gherkin
Scenario: Actualización de campos de control en una actualización parcial
  Given existe una cotización con ID "COT-003" con "version" 1 y "fechaUltimaActualizacion" "2026-04-20T10:00:00Z"
  When se solicita una actualización parcial para la cotización "COT-003" con { "estado": "Completado" }
  Then la cotización "COT-003" en la base de datos tiene la "version" 2
  And la "fechaUltimaActualizacion" de la cotización "COT-003" es posterior a "2026-04-20T10:00:00Z"
```

**BR-001:** Lógica de Actualización Parcial
- Description: Cuando se recibe una solicitud de actualización parcial para una cotización, el sistema debe identificar los campos presentes en la solicitud y aplicar las modificaciones solo a esos campos en la entidad persistida.
- Trigger: Solicitud de actualización (PATCH) a la API de cotizaciones.
- Logic:
    1. Recuperar la cotización existente por su ID.
    2. Iterar sobre los campos proporcionados en la solicitud de actualización.
    3. Para cada campo, actualizar su valor en la cotización recuperada.
    4. Incrementar el campo `version` de la cotización.
    5. Actualizar el campo `fechaUltimaActualizacion` a la fecha y hora actual.
    6. Persistir la cotización modificada.
- Implementation: Capa de servicio o repositorio de cotizaciones.
- Exception: Si la cotización no existe, se debe devolver un error (ej. 404 Not Found). Si hay un conflicto de versión (versioning optimista), se debe devolver un error (ej. 409 Conflict).

### Case 2: Conflicto de versión (Versionado Optimista)
```gherkin
Scenario: Conflicto al actualizar una cotización con versión obsoleta

  And la cotización "COT-004" en la base de datos no es modificada
```

### Case 3: Campos de solo lectura en la solicitud
```gherkin
Scenario: Intentar actualizar un campo de solo lectura
  Given existe una cotización con ID "COT-005"
  And el campo "id" es un campo de solo lectura
  When se solicita una actualización parcial para la cotización "COT-005" incluyendo { "id": "nuevo-id" }
  Then el sistema ignora el intento de modificar el campo "id"
  And solo los campos permitidos y modificables se actualizan
  And el sistema devuelve un código de estado 200 OK (o 204 No Content)
```

## 16. Technical Notes and Risks
**Risks:**
1.  **Manejo incorrecto de objetos parciales:**
    -   Descripción: Si la capa de datos o la API no están diseñadas cuidadosamente para manejar objetos parciales, podría haber errores de sobrescritura de datos o validaciones incorrectas.
    -   Impacto: Pérdida de datos, corrupción de información de cotizaciones.
    -   Probabilidad: Media.
    -   Mitigación: Implementar un enfoque de `PATCH` robusto (ej. usando `JsonPatch` o lógica de merge en ORM/ODM), con pruebas unitarias y de integración exhaustivas.
2.  **Validaciones de campos faltantes:**
    -   Descripción: Asegurar que las validaciones solo se apliquen a los campos presentes en la actualización parcial, sin requerir campos obligatorios que no están siendo modificados.
    -   Impacto: Errores innecesarios, frustración del desarrollador al consumir la API.
    -   Probabilidad: Media.
    -   Mitigación: Implementar un mecanismo de validación condicional que inspeccione solo los campos presentes en el payload de la solicitud.

## 17. Criticality
**Criticality Level:** Medium
**Justification:** Esta historia es importante para la optimización y eficiencia del backend, pero no bloquea la funcionalidad básica de creación o edición de cotizaciones (que podría hacerse con una actualización completa). Su implementación mejora la experiencia del desarrollador y el rendimiento del sistema a largo plazo.
**Feature Impact:** La no implementación de esta historia resultaría en operaciones de guardado menos eficientes, mayor tráfico de red y carga de base de datos para actualizaciones menores, afectando la escalabilidad y el rendimiento general de la gestión de cotizaciones.
**Critical Dependencies:** Depende críticamente de la existencia de un mecanismo de versionado optimista (FT-008) para garantizar la integridad de los datos durante las actualizaciones concurrentes.
**Recommended Priority:** Sprint actual o siguiente, después de que FT-008 esté implementado.

## 18. Identified Assumptions
1.  **Soporte de la capa de persistencia para actualizaciones parciales:**
    -   Description: Se asume que el ORM/ODM o la capa de datos subyacente puede manejar eficientemente la actualización de un subconjunto de campos sin cargar y guardar el objeto completo si no es necesario, o que se puede implementar una lógica de merge efectiva.
    -   Impact if false: Mayor complejidad en la implementación, posible menor rendimiento si se requiere cargar y guardar el objeto completo para cada actualización parcial.
    -   Requires validation from: Equipo de Arquitectura / Desarrolladores de Backend.
2.  **Validaciones de negocio existentes son compatibles con actualizaciones parciales:**
    -   Description: Se asume que las reglas de negocio y validaciones existentes para los campos de cotización pueden aplicarse de manera granular a los campos que se están actualizando, sin requerir la validación de todo el objeto.
    -   Impact if false: Necesidad de refactorizar las reglas de validación o riesgo de introducir estados inconsistentes si las validaciones no son correctas en un contexto parcial.
    -   Requires validation from: Equipo de Desarrollo / Analistas de Negocio.
