## 2. Enabled Capability
**CAP-001:** Validación de Ubicaciones de Riesgo
**Business Value:** Asegurar que las direcciones de las ubicaciones de riesgo son válidas, lo que permite obtener la zonificación de riesgo correcta. Esto es fundamental para la precisión en la evaluación de riesgos y la tarificación de pólizas.
**Requires:** CAP-002 (Gestión de Catálogo de Códigos Postales y Zonas de Riesgo)
**Enables:** CAP-003 (Cálculo de Riesgo por Ubicación), CAP-004 (Generación de Pólizas con Datos de Riesgo Validados)
**Orchestrates:** Servicio de Validación de CP (Backend)

## 3. User Story
Como un **usuario**,
Quiero **que el sistema valide el código postal de cada ubicación de riesgo**,
Para que **la dirección sea válida y obtener la zonificación de riesgo correcta**.

## 4. Functional Description
**Description:** Esta historia de usuario describe el proceso mediante el cual el sistema valida el código postal ingresado por el usuario al crear o editar una ubicación de riesgo. La validación se activa cuando el campo de código postal pierde el foco o cuando el usuario intenta guardar la ubicación. El sistema consultará el `catalogo_cp_zonas` para verificar la existencia y validez del código postal. Si el código postal es válido y se encuentra en el catálogo, se mostrarán automáticamente los datos de zona asociados (como CAT y nivel técnico) en la interfaz de usuario. En caso de que el código postal sea inválido o no se encuentre en el catálogo, el sistema presentará un mensaje de error claro al usuario y evitará que la ubicación sea guardada hasta que se proporcione un código postal válido.
**Flow:** [Ingreso/Edición de Ubicación de Riesgo] → [**HU-119: Validar Código Postal de Ubicación**] → [Guardar Ubicación Válida / Mostrar Mensaje de Error y Prevenir Guardado]

## 6. Acceptance Criteria (3-5 criteria)
### AC-001: Validación de CP al perder foco o guardar
**Description:** Este criterio valida que el sistema inicia el proceso de validación del código postal automáticamente cuando el usuario interactúa con el campo o intenta guardar la ubicación.

```gherkin
Scenario: Validación automática de Código Postal
  Given el usuario está ingresando o editando una ubicación de riesgo
  And el campo "Código Postal" está presente
  When el usuario ingresa un código postal y el campo pierde el foco
  Then el sistema inicia la validación del CP contra el `catalogo_cp_zonas`
  And si el CP es válido, muestra los datos de zona asociados
  And si el CP es inválido, muestra un mensaje de error.
```

### AC-002: Visualización de datos de zona para CP válido
**Description:** Este criterio asegura que, si el código postal es válido, el sistema recupera y muestra correctamente la información de zonificación de riesgo asociada.

```gherkin
Scenario: Mostrar datos de zona para Código Postal válido
  Given el usuario ha ingresado un código postal válido (ej. "28001")
  When el sistema valida el CP contra el `catalogo_cp_zonas`
  Then los datos de zona (CAT, nivel técnico) asociados a "28001" se muestran en la interfaz de usuario
  And el botón para guardar la ubicación está habilitado.
```

### AC-003: Manejo de CP inválido o no encontrado
**Description:** Este criterio verifica que el sistema reacciona adecuadamente ante un código postal inválido o no existente, informando al usuario y bloqueando el guardado de la ubicación.

```gherkin
Scenario: Manejo de Código Postal inválido o no encontrado
  Given el usuario ha ingresado un código postal inválido o no encontrado (ej. "99999")
  When el sistema valida el CP contra el `catalogo_cp_zonas`
  Then el sistema muestra un mensaje de error claro (ej. "Código Postal inválido o no encontrado. Por favor, verifique.")
  And el sistema no permite guardar la ubicación hasta que el CP sea corregido.
```

## 7. Data and Business Rules


| field | type | required | default | validation | catalog | example |
|---|---|---|---|---|---|---|
| codigo_postal | string | yes |  | Formato de 5 dígitos numéricos (ej. ^\d{5}$) | catalogo_cp_zonas | 28001 |
| cat | string | no |  | Valor proveniente del catálogo de CP y zonas | catalogo_cp_zonas | Zona A |
| nivel_tecnico | string | no |  | Valor proveniente del catálogo de CP y zonas | catalogo_cp_zonas | Alto |


**BR-001:** Validación de Existencia y Formato de Código Postal
- Description: Todo código postal ingresado para una ubicación de riesgo debe cumplir con el formato estándar (5 dígitos numéricos) y debe existir en el `catalogo_cp_zonas` para ser considerado válido.
- Trigger: Al perder el foco del campo "Código Postal" en la interfaz de usuario o al intentar guardar la ubicación.
- Logic:
  1. Verificar que el `codigo_postal` cumpla con el formato `^\\d{5}$`.
  2. Consultar el `catalogo_cp_zonas` para verificar si el `codigo_postal` existe.
  3. Si no cumple el formato o no existe, marcar como inválido.
- Implementation: Frontend (validación de formato), Backend (validación de existencia contra catálogo).
- Exception: Si el `catalogo_cp_zonas` no está disponible, se debe manejar como un error de servicio y notificar al usuario.

## 10. UX and Navigation Flow
**UX Flow:**
1.  El usuario navega a la pantalla de "Creación/Edición de Ubicación de Riesgo".
2.  El usuario ingresa un valor en el campo "Código Postal".
3.  Al perder el foco del campo:
    *   Si el CP es válido: Se muestran automáticamente los campos de "CAT" y "Nivel Técnico" con los datos correspondientes. El botón de guardar se mantiene habilitado.
    *   Si el CP es inválido: Aparece un mensaje de error visual (ej. texto rojo, borde de campo resaltado) debajo del campo "Código Postal". El botón de guardar se deshabilita.
4.  El usuario corrige el CP si fue inválido.
5.  Una vez el CP es válido, el usuario puede guardar la ubicación.

**Messages/Modals:**
*   Mensaje de error para CP inválido: "El código postal ingresado no es válido o no se encuentra en nuestro catálogo. Por favor, verifique e intente de nuevo."
*   Mensaje de error genérico (ej. por fallo de servicio): "No se pudo validar el código postal en este momento. Por favor, intente de nuevo más tarde o contacte a soporte."
**Stepper/Breadcrumbs:** N/A

## 11. Architecture and Technical Dependencies
- **Frontend (UI):** Componente de campo de entrada para Código Postal, componentes de visualización de datos de zona, lógica para la validación al perder foco y manejo de errores.
- **Backend (Servicio de Validación de CP):** Un microservicio o API REST que recibe el código postal y lo consulta contra el `catalogo_cp_zonas`.
- **`catalogo_cp_zonas`:** Base de datos o servicio externo que almacena la información de códigos postales y sus zonas de riesgo asociadas.
- **Timeout:** Se recomienda un timeout de 300ms para la llamada al `Servicio de Validación de CP` desde el frontend para mantener una buena experiencia de usuario.
- **Retries:** No se recomiendan reintentos automáticos desde el frontend para esta validación síncrona/asíncrona en la UI para evitar retrasos innecesarios. El usuario puede reintentar manualmente.

## 16. Technical Notes and Risks
**Technical Notes:**
- La validación del código postal debe ser asíncrona para no bloquear la UI y proporcionar una experiencia de usuario fluida.
- Se debe considerar un debounce en el campo de código postal para evitar múltiples llamadas al backend si el usuario escribe rápidamente.
**Risks:**
1.  **Disponibilidad y Actualización del Catálogo de CPs:**
    -   Description: El `Servicio de Validación de CP` depende de la disponibilidad y la actualidad del `catalogo_cp_zonas`. Si el catálogo no está disponible o contiene datos obsoletos/incorrectos, la validación fallará o proporcionará información errónea.
    -   Impact: Ubicaciones de riesgo con datos incorrectos, cálculos de riesgo erróneos, frustración del usuario.
    -   Probability: Media
    -   Mitigation: Implementar monitoreo proactivo del catálogo, establecer acuerdos de nivel de servicio (SLA) con el proveedor del catálogo, considerar estrategias de caché o fallback (ej. permitir guardar con advertencia temporal si el catálogo está caído).
2.  **Latencia del Servicio de Validación:**
    -   Description: Una alta latencia en la respuesta del `Servicio de Validación de CP` podría degradar la experiencia del usuario, especialmente si la validación es en tiempo real al perder el foco del campo.
    -   Impact: Retrasos perceptibles en la UI, frustración del usuario, percepción de lentitud del sistema.
    -   Probability: Baja-Media
    -   Mitigation: Optimización del rendimiento del servicio backend, uso de indicadores de carga (spinners) en la UI, implementación de un debounce adecuado en el campo de entrada.

## 17. Criticality
**Criticality Level:** Alta
**Justification:** La validación del código postal es un paso crítico para asegurar la integridad y precisión de los datos de las ubicaciones de riesgo. Sin esta validación, el sistema podría registrar ubicaciones con direcciones incorrectas, lo que impactaría directamente en la evaluación del riesgo, la tarificación de pólizas, la gestión de siniestros y la toma de decisiones estratégicas.
**Feature Impact:** La no implementación o el fallo de esta historia comprometería la fiabilidad de toda la funcionalidad de "Gestión de Ubicaciones de Riesgo" y de cualquier funcionalidad que dependa de la geolocalización o zonificación de riesgo.
**Critical Dependencies:** Todas las historias de usuario relacionadas con el cálculo de primas, evaluación de riesgo, reportes geográficos y análisis de exposición.
**Recommended Priority:** Próximo Sprint (confirmado por la prioridad "Alta" del contexto).

## 18. Identified Assumptions
1.  **Disponibilidad y Fiabilidad del `catalogo_cp_zonas`**
    -   Description: Se asume que el `catalogo_cp_zonas` es una fuente de datos fiable, siempre disponible y que se mantiene actualizado con la información geográfica y de zonificación de riesgo pertinente.
    -   Impact if false: La validación fallaría o proporcionaría datos incorrectos, comprometiendo la calidad de la información de riesgo.
    -   Requires validation from: Equipo de Datos y/o Propietario del Catálogo.
2.  **Formato Consistente de Código Postal**
    -   Description: Se asume que los códigos postales ingresados por los usuarios y los almacenados en el `catalogo_cp_zonas` siguen un formato consistente y estandarizado (ej. 5 dígitos numéricos sin caracteres especiales), lo que permite una validación y comparación directa.
    -   Impact if false: Inconsistencias en el formato podrían llevar a fallos de validación o a la no detección de códigos postales válidos.
    -   Requires validation from: Equipo de Desarrollo (Frontend/Backend) y Equipo de Datos.
3.  **Existencia de Datos de Zona en el Catálogo**
    -   Description: Se asume que, para cada código postal válido en el `catalogo_cp_zonas`, existe información asociada de CAT y Nivel Técnico que puede ser recuperada y mostrada.
    -   Impact if false: Incluso con un CP válido, el sistema no podría mostrar la información de zonificación esperada.
    -   Requires validation from: Equipo de Datos y/o Propietario del Catálogo.
