## 1. Identificación General / General Identification
**Feature:** Gestión de Ubicaciones para Tarificación
**Capability:** CAP-005 - Gestión de Información de Ubicación Geográfica
**Actor:** Usuario (del sistema de cotización)
**Bounded Context:** Cotizador / Tarificación
**Story Points:** 3 puntos de historia

## 2. Enabled Capability
**CAP-005:** Gestión de Información de Ubicación Geográfica
**Business Value:** Permitir que el cotizador aplique tarifas y factores de riesgo precisos basados en la ubicación geográfica (código postal), mejorando la exactitud de las cotizaciones y la evaluación de riesgos.
**Requires:** CAP-001 (Conectividad Básica del Sistema), FT-020 (Simulación de Servicio Plataforma-core-ohs)
**Enables:** CAP-006 (Cálculo Preciso de Tarifas), CAP-007 (Evaluación de Factores de Riesgo por Ubicación)
**Orchestrates:** Plataforma-core-ohs (servicio externo)

## 3. User Story
Como usuario,
Quiero consultar un código postal y obtener su información de zona (CAT, nivel técnico) desde el servicio `Plataforma-core-ohs` (o su mock),
Para que el cotizador pueda aplicar tarifas y factores de riesgo precisos basados en la ubicación.

## 4. Functional Description
**Description:** El usuario, mientras interactúa con el formulario de cotización, ingresa un código postal. El sistema valida el formato del código postal y, si es válido, procede a consultar el servicio `Plataforma-core-ohs` (o su mock) para obtener la Zona CAT y el Nivel Técnico asociados a dicho código postal. Una vez obtenida esta información, se muestra en la interfaz y se almacena junto con los demás datos de ubicación de riesgo de la cotización, permitiendo su uso en cálculos posteriores.
**Flow:** [HU-073: Ingreso de Datos de Cotización Básicos] → [HU-074: Consultar Información de Código Postal y Zona] → [HU-075: Aplicar Reglas de Tarificación por Zona]

## 6. Acceptance Criteria (3-5 criteria)
### AC-001: Consulta Exitosa de Código Postal Válido
**Description:** Validar que al ingresar un código postal válido y existente, el sistema recupera y muestra correctamente la Zona CAT y el Nivel Técnico asociados, y los guarda con los datos de ubicación de riesgo.

```gherkin
Scenario: El sistema muestra la zona CAT y el nivel técnico para un CP válido
  Given que el usuario ha ingresado un código postal válido "28001" en el formulario de cotización
  When el sistema valida el código postal y consulta la información de zona en 'Plataforma-core-ohs'
  Then el sistema muestra la "Zona CAT A" y el "Nivel Técnico 3" asociados en la interfaz
  And la información de "Zona CAT A" y "Nivel Técnico 3" se guarda con los datos de ubicación de riesgo de la cotización
```

### AC-002: Manejo de Código Postal Inválido
**Description:** Validar que el sistema detecta y notifica al usuario cuando el código postal ingresado no cumple con el formato esperado o es inválido.

```gherkin
Scenario: El sistema notifica al usuario sobre un código postal con formato inválido
  Given que el usuario ha ingresado un código postal "ABCDE" (o con un formato incorrecto)
  When el sistema intenta validar el código postal
  Then el sistema muestra un mensaje de error "El código postal ingresado no es válido. Por favor, verifique."
  And no se realiza ninguna consulta al servicio 'Plataforma-core-ohs'
```

### AC-003: Manejo de Código Postal No Encontrado
**Description:** Validar que el sistema informa al usuario cuando un código postal válido en formato no se encuentra en el catálogo del servicio `Plataforma-core-ohs`.

```gherkin
Scenario: El sistema maneja un código postal válido pero no encontrado en el catálogo
  Given que el usuario ha ingresado un código postal "00001" que no existe en el catálogo de 'Plataforma-core-ohs'
  When el sistema consulta la información de zona en 'Plataforma-core-ohs'
  Then el sistema muestra un mensaje de error "El código postal no se encontró en nuestro catálogo. Por favor, verifique."
  And la información de Zona CAT y Nivel Técnico permanece vacía o nula
```

## 7. Data and Business Rules


| field | type | required | default | validation | catalog | example |
|---|---|---|---|---|---|---|
| codigo_postal | string | yes | N/A | Formato de 5 dígitos numéricos (e.g., ^\d{5}$) | N/A | 28001 |
| zona_cat | string | no | N/A | N/A | Catálogo interno de Zonas CAT (A, B, C...) | Zona CAT A |
| nivel_tecnico | integer | no | N/A | Rango numérico (e.g., 1-5) | N/A | 3 |
| id_ubicacion_riesgo | UUID | yes | Generado automáticamente | UUID v4 | N/A | a1b2c3d4-e5f6-7890-1234-567890abcdef |


**BR-001:** Validación de Formato de Código Postal
- Description: El código postal ingresado por el usuario debe cumplir con un formato preestablecido antes de ser consultado.
- Trigger: Al ingresar o intentar procesar un código postal en el formulario.
- Logic: El `codigo_postal` debe ser una cadena de 5 caracteres numéricos.
- Implementation: Módulo de consulta de CP (validación de entrada en el frontend y backend).
- Exception: Si el formato es incorrecto, se rechaza la entrada y se notifica al usuario.

**BR-002:** Fuente de Información de Zona
- Description: La información de Zona CAT y Nivel Técnico para un código postal solo puede ser obtenida del servicio `Plataforma-core-ohs` (o su mock).
- Trigger: Cuando se requiere la información de zona para un código postal válido.
- Logic: Realizar una llamada a la API REST `/postal-codes/{codigo_postal}` del servicio externo.
- Implementation: Cliente API REST.
- Exception: Si el servicio no está disponible o falla, no se puede obtener la información de zona.

## 10. UX and Navigation Flow
**UX Flow:** El usuario ingresa un código postal en un campo de texto dentro del formulario de cotización. Tras un evento (e.g., pérdida de foco del campo, clic en un botón de validación, o envío del formulario), el sistema realiza la consulta. Los campos de Zona CAT y Nivel Técnico se rellenan automáticamente (solo lectura) o se muestran mensajes de error/éxito.
**Messages/Modals:**
*   **Mensaje de Éxito:** "Información de ubicación cargada correctamente." (Toast o mensaje inline).
*   **Mensaje de Error (CP inválido):** "El código postal ingresado no es válido. Por favor, verifique." (Mensaje inline junto al campo).

**Stepper/Breadcrumbs:** Esta funcionalidad es un paso dentro de un flujo de cotización más amplio, no requiere un stepper o breadcrumbs propio.

## 11. Architecture and Technical Dependencies
- **`Plataforma-core-ohs` (o su mock FT-020):** Servicio externo REST para la consulta de códigos postales.
    - **Propósito:** Obtener Zona CAT y Nivel Técnico.
    - **Endpoint:** `/api/v1/postal-codes/{codigo_postal}` (GET)
    - **Timeout:** 500 ms
    - **Retries:** 1 reintento con backoff exponencial
- **Cliente API REST:** Módulo interno del cotizador para encapsular la comunicación con `Plataforma-core-ohs`.
- **Módulo de Consulta de CP:** Componente de negocio en el backend del cotizador que orquesta la validación y la llamada al Cliente API REST.
- **Circuit Breaker:** Implementar un Circuit Breaker para la llamada a `Plataforma-core-ohs` para manejar la degradación del servicio de forma resiliente.

## 16. Technical Notes and Risks
**Risks:**
1.  **Dependencia Externa y Rendimiento:**
    -   Description: El rendimiento y la disponibilidad de `Plataforma-core-ohs` son críticos para la fluidez del cotizador.
    -   Impact: Retrasos en la interacción del usuario, errores en la cotización si el servicio falla.
    -   Probability: Media.
    -   Mitigation: Implementar Circuit Breaker, reintentos con backoff, monitoreo de latencia y disponibilidad del servicio externo. Considerar cacheo de datos de códigos postales si la información no cambia frecuentemente.
2.  **Volumen de Consultas:**
    -   Description: Un alto número de cotizaciones concurrentes podría generar una carga significativa en `Plataforma-core-ohs`.
    -   Impact: Degradación del rendimiento del servicio externo y del cotizador.
    -   Probability: Baja a Media (dependiendo del volumen de negocio).
    -   Mitigation: Establecer acuerdos de nivel de servicio (SLA) con el equipo de `Plataforma-core-ohs`. Evaluar la necesidad de cacheo a nivel de aplicación del cotizador.
**Technical Debt:** La dependencia inicial del FT-020 (mock) debe ser temporal. La integración real con `Plataforma-core-ohs` debe ser prioritaria para evitar que el mock se convierta en una solución permanente.

## 17. Criticality
**Criticality Level:** Alta
**Justification:** Esta historia es fundamental para la funcionalidad principal del cotizador, ya que la tarificación y la evaluación de riesgos dependen directamente de la información de ubicación. Sin ella, el cotizador no puede generar cotizaciones precisas.
**Feature Impact:** La no implementación o el fallo de esta historia hace que la funcionalidad de tarificación sea inexacta o inoperable, afectando directamente la capacidad del negocio para cotizar productos.
**Critical Dependencies:** Cálculo de Primas, Evaluación de Riesgos.
**Recommended Priority:** Sprint Actual.
