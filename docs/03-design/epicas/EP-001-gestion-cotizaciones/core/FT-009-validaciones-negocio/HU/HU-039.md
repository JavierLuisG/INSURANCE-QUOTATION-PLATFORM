## 2. Enabled Capability
**CAP-007:** Validación de Datos Generales de la Cotización
**Business Value:** Asegurar la calidad y consistencia de la información de las cotizaciones, reduciendo errores y reprocesos.
**Requires:** CAP-006 - Creación y Edición de Cotizaciones
**Enables:** CAP-008 - Procesamiento de Cotizaciones Válidas
**Orchestrates:** N/A

## 3. User Story
Como usuario,
quiero que los datos generales de la cotización se validen según reglas de negocio,
para asegurar la calidad de la información.

## 4. Functional Description
**Description:** Esta historia de usuario describe la funcionalidad de validar los datos generales introducidos por el usuario al crear o editar una cotización. El sistema debe aplicar reglas de negocio para campos como el RFC, las fechas de vigencia y campos obligatorios. Las validaciones se realizarán tanto en el frontend para una respuesta inmediata como en el backend para garantizar la integridad de los datos, mostrando mensajes de error claros al usuario cuando la información no cumpla con los requisitos.
**Flow:** [FT-001: Creación y Edición de Datos Generales de la Cotización] → [HU-039: Validar datos generales de la cotización] → [HU-035: Incrementar versión de cotización en cada edición (Guardar Cotización Válida)]

## 6. Acceptance Criteria
### AC-001: Validación de formato de RFC
**Description:** Valida que el formato del RFC introducido sea correcto antes de permitir guardar la cotización.

```gherkin
Scenario: El sistema muestra un mensaje de error al introducir un RFC con formato incorrecto
  Given he introducido un RFC con formato incorrecto (ej. "ABC12345") en el campo 'RFC del Asegurado'
  When intento guardar la cotización
  Then el sistema muestra un mensaje de error indicando "El formato del RFC es incorrecto."
  And la cotización no se guarda
```

### AC-002: Validación de fechas de vigencia
**Description:** Valida que la fecha de fin de vigencia no sea anterior a la fecha de inicio de vigencia.

```gherkin
Scenario: El sistema muestra un error si la fecha de fin de vigencia es anterior a la de inicio
  Given he introducido una 'Fecha de Inicio de Vigencia' (ej. 2026-05-01) y una 'Fecha de Fin de Vigencia' anterior (ej. 2026-04-30)
  When intento guardar la cotización
  Then el sistema muestra un mensaje de error indicando "La fecha de fin de vigencia no puede ser anterior a la fecha de inicio."
  And la cotización no se guarda
```

### AC-003: Validación de campos obligatorios
**Description:** Valida que todos los campos marcados como obligatorios estén completos antes de permitir guardar la cotización.

```gherkin
Scenario: El sistema indica campos obligatorios vacíos
  Given he dejado el campo 'Nombre del Asegurado' vacío
  And he completado todos los demás campos obligatorios correctamente
  When intento guardar la cotización
  Then el sistema muestra un mensaje de error indicando "El campo 'Nombre del Asegurado' es obligatorio."
  And la cotización no se guarda
```

## 7. Data and Business Rules


| field | type | required | default | validation | catalog | example |
|---|---|---|---|---|---|---|
| rfc_asegurado | string | yes | N/A | Formato de RFC mexicano (12 o 13 caracteres alfanuméricos, ej. ^[A-Z&Ñ]{3,4}[0-9]{2}(0[1-9]|1[0-2])(0[1-9]|[12][0-9]|3[01])[A-Z0-9]{2}[0-9A]$) | N/A | XAXX010101000 |
| fecha_inicio_vigencia | date | yes | Fecha actual (2026-04-21) | Debe ser una fecha válida. No puede ser posterior a fecha_fin_vigencia. | N/A | 2026-05-01 |
| fecha_fin_vigencia | date | yes | N/A | Debe ser una fecha válida. Debe ser igual o posterior a fecha_inicio_vigencia. | N/A | 2027-04-30 |
| nombre_asegurado | string | yes | N/A | No vacío, longitud mínima 3 caracteres. | N/A | Juan Pérez García |


**BR-001:** Formato de RFC
- Description: El RFC del asegurado debe cumplir con el formato estándar de RFC mexicano.
- Trigger: Al intentar guardar la cotización o al perder el foco del campo RFC (validación en frontend).
- Logic: Validar el campo `rfc_asegurado` contra la expresión regular definida.
- Implementation: Módulo de validación de backend y lógica de validación en frontend.
- Exception: N/A

**BR-002:** Orden de Fechas de Vigencia
- Description: La fecha de fin de vigencia no puede ser anterior a la fecha de inicio de vigencia.
- Trigger: Al intentar guardar la cotización o al cambiar cualquiera de las fechas de vigencia (validación en frontend).
- Logic: `fecha_fin_vigencia` >= `fecha_inicio_vigencia`
- Implementation: Módulo de validación de backend y lógica de validación en frontend.
- Exception: N/A

**BR-003:** Campos Obligatorios
- Description: Todos los campos definidos como obligatorios deben contener un valor.
- Trigger: Al intentar guardar la cotización.
- Logic: Verificar que los campos marcados como `required: yes` no estén vacíos.
- Implementation: Módulo de validación de backend y lógica de validación en frontend.
- Exception: N/A

## 16. Technical Notes and Risks
**Risks:**
1.  **Riesgo: Discrepancia entre validaciones Frontend y Backend**
    -   Descripción: Las reglas de validación implementadas en el frontend podrían no ser idénticas o estar desactualizadas respecto a las del backend, llevando a una experiencia de usuario inconsistente o a fallos inesperados al guardar.
    -   Impacto: Mala UX, datos inconsistentes, posibles brechas de seguridad.
    -   Probabilidad: Media
    -   Mitigación: Implementar un conjunto de reglas de validación compartidas o generadas desde una única fuente. Asegurar pruebas exhaustivas en ambos niveles.
2.  **Riesgo: Rendimiento de validación en el frontend**
    -   Descripción: Un gran número de validaciones o validaciones complejas en el frontend podrían afectar el rendimiento de la interfaz de usuario.
    -   Impacto: Experiencia de usuario lenta o frustrante.
    -   Probabilidad: Baja (para esta historia, es un número limitado de campos)
    -   Mitigación: Optimizar la lógica de validación, considerar validación diferida (on blur vs on keyup), y pruebas de rendimiento.

## 17. Criticality
**Criticality Level:** Alta
**Justification:** La validación de datos es fundamental para la integridad del negocio. Sin ella, se podrían crear cotizaciones con información errónea o incompleta, lo que impactaría negativamente en procesos subsiguientes como la emisión de pólizas o la facturación, generando retrabajos y afectando la confianza del cliente.
**Feature Impact:** La no implementación o fallo de esta historia comprometería la calidad de toda la funcionalidad de "Gestión de Cotizaciones", haciendo que los datos sean poco confiables y el proceso propenso a errores.
**Critical Dependencies:** Todas las historias que consuman o procesen datos de cotizaciones dependerán de que esta validación funcione correctamente.
**Recommended Priority:** Sprint actual.

## 18. Identified Assumptions
1.  **Formato de RFC:**
    -   Description: Se asume que el formato de RFC a validar es el estándar mexicano (personas físicas y morales) y que existe una expresión regular o lógica definida y estable para ello.
    -   Impact if false: Errores en la validación de RFC que podrían bloquear RFCs válidos o permitir inválidos.
    -   Requires validation from: Equipo de Negocio / Legal.
2.  **Mensajes de Error:**
    -   Description: Se asume que los mensajes de error deben ser claros, específicos y orientar al usuario para corregir el dato.
    -   Impact if false: Usuarios frustrados por mensajes genéricos o poco útiles, aumentando el tiempo para corregir errores.
    -   Requires validation from: Equipo de UX.
