## 3. User Story
Como usuario,
Quiero modificar los datos generales de una cotización (Nombre Asegurado, RFC, Tipo de Seguro, Moneda, Vigencia, Canal de Venta),
Para mantener la información de la cotización actualizada y precisa.

## 4. Functional Description
**Description:** Esta historia de usuario permite a un usuario modificar los campos de datos generales de una cotización existente, incluyendo el Nombre del Asegurado, RFC, Tipo de Seguro, Moneda, Vigencia y Canal de Venta. El objetivo es asegurar que la información de la cotización se mantenga siempre actualizada y precisa. Al guardar los cambios, el sistema debe persistir la nueva información, actualizar la fecha de la última modificación e incrementar el número de versión de la cotización. Se aplicarán validaciones de formato, rango y contra catálogos para los campos correspondientes.
**Flow:** [Visualizar Cotización] → [HU-112: Editar Datos Generales de la Cotización] → [Visualizar Cotización Actualizada]

## 6. Acceptance Criteria (3-5 criteria)
### AC-001: Persistencia de Cambios en Datos Generales
**Description:** Valida que, al modificar y guardar los datos generales de una cotización, los cambios se almacenan correctamente en el sistema.

```gherkin
Scenario: Usuario edita y guarda datos generales de una cotización
  Given tengo una cotización con ID "COT-123" abierta y editable
  And el Nombre Asegurado actual es "Juan Perez"
  When edito el campo "Nombre Asegurado" a "Maria Gomez"
  And guardo los cambios
  Then los cambios se persisten correctamente para la cotización "COT-123"
  And el Nombre Asegurado de la cotización "COT-123" es "Maria Gomez"
```

### AC-002: Actualización de Metadatos de Cotización
**Description:** Asegura que la `fechaUltimaActualizacion` se actualiza y el `numeroVersion` se incrementa al guardar modificaciones en la cotización.

```gherkin
Scenario: Actualización de fecha y versión al modificar cotización
  Given tengo una cotización con ID "COT-123" y numeroVersion 1
  And la fechaUltimaActualizacion es "2026-04-20T10:00:00Z"
  When modifico cualquier campo de datos generales y guardo
  Then la fechaUltimaActualizacion de la cotización "COT-123" es posterior a "2026-04-20T10:00:00Z"
  And el numeroVersion de la cotización "COT-123" es 2
```

### AC-003: Validación de Campos de Catálogo
**Description:** Verifica que los campos que dependen de catálogos (Tipo de Seguro, Moneda, Canal de Venta) solo aceptan valores válidos de sus respectivos catálogos.

```gherkin
Scenario: Selección y validación de tipo de seguro desde catálogo
  Given tengo una cotización abierta
  And el catálogo de "Tipo de Seguro" contiene "Vida", "Autos", "Hogar"
  When intento seleccionar "Salud" como Tipo de Seguro
  Then el sistema me permite seleccionarlo si "Salud" está en el catálogo
  And si "Salud" NO está en el catálogo, se muestra un mensaje de error de validación
```

### AC-004: Validación de Formato y Rango
**Description:** Confirma que el sistema valida el formato del RFC y el rango de la Vigencia según las reglas de negocio.

```gherkin
Scenario: Validación de formato de RFC y rango de Vigencia
  Given tengo una cotización abierta
  When intento guardar con un RFC "ABC123" (formato inválido)
  Then se muestra un mensaje de error de validación para el RFC
  When intento guardar con una Vigencia que excede el rango permitido (ej. más de 1 año)
  Then se muestra un mensaje de error de validación para la Vigencia
```

| numeroVersion | Integer | yes | 1 | Valor positivo, incrementa en cada actualización | N/A | 2 |


**BR-001:** Validación de Formato de RFC
- Description: El campo RFC debe cumplir con un formato específico (ej. 13 caracteres alfanuméricos para personas físicas, 12 para morales).
- Trigger: Al intentar guardar una cotización con el campo RFC modificado.
- Logic: `RFC.matches(regex_RFC_valido)`
- Implementation: Servicio de validación de cotizaciones.
- Exception: Ninguna.

**BR-002:** Validación de Rango de Vigencia
- Description: El rango de vigencia de la cotización no debe exceder un período máximo (ej. 1 año).
- Trigger: Al intentar guardar una cotización con el campo Vigencia modificado.
- Logic: `(Vigencia.fechaFin - Vigencia.fechaInicio) <= 1 año`
- Implementation: Servicio de validación de cotizaciones.
- Exception: Ninguna.

**BR-003:** Validación de Campos de Catálogo
- Description: Los campos 'Tipo de Seguro', 'Moneda' y 'Canal de Venta' deben corresponder a valores existentes en sus respectivos catálogos.
- Trigger: Al intentar guardar una cotización con cualquiera de estos campos modificados.
- Logic: `valor_campo IN catalogo_correspondiente`
- Implementation: Servicio de validación de cotizaciones, integrándose con servicios de catálogo (HU-144).
- Exception: Ninguna.

**BR-004:** Actualización de Metadatos de Cotización
- Description: Tras una modificación exitosa, la `fechaUltimaActualizacion` debe ser la fecha y hora de la operación y el `numeroVersion` debe incrementarse.
- Trigger: Después de una operación de guardado exitosa.
- Logic: `cotizacion.fechaUltimaActualizacion = now(); cotizacion.numeroVersion++`
- Implementation: Servicio de persistencia de cotizaciones.
- Exception: Ninguna.

**BR-005:** Prevención de Sobrescritura (Versionado Optimista)
- Description: Si se intenta guardar una cotización con un `numeroVersion` desactualizado, la operación debe ser rechazada para prevenir la sobrescritura de cambios concurrentes.
- Trigger: Al intentar guardar una cotización.
- Logic: `if (cotizacion.numeroVersion_enviado != cotizacion.numeroVersion_actual_DB) then throw ConcurrencyException`
- Implementation: Servicio de persistencia de cotizaciones (dependencia HU-151).
- Exception: ConcurrencyException (o similar).

### Case 2: Error de Concurrencia
```gherkin
Scenario: Guardar cambios con una versión desactualizada
  Given la cotización "COT-123" tiene numeroVersion 2 en la base de datos
  And un usuario A tiene la cotización "COT-123" con numeroVersion 1 abierta en su formulario
  And otro usuario B modifica y guarda la cotización "COT-123", incrementando su numeroVersion a 2
  When el usuario A intenta guardar sus cambios para la cotización "COT-123" (con numeroVersion 1)
  Then el sistema rechaza la operación y muestra un mensaje de error de concurrencia
```

### Case 3: Catálogo no disponible
```gherkin
Scenario: Intentar seleccionar un tipo de seguro cuando el servicio de catálogo está caído
  Given tengo una cotización abierta
  And el servicio de catálogo de "Tipos de Seguro" no está disponible

  Then el campo de selección "Tipo de Seguro" se muestra deshabilitado o con un mensaje de error indicando la indisponibilidad
  And no puedo guardar la cotización con un valor inválido o nulo para Tipo de Seguro
```

## 16. Technical Notes and Risks
**Risks:**
1.  **Concurrencia de Datos:**
    *   Descripción: Múltiples usuarios intentando editar la misma cotización simultáneamente.
    *   Impacto: Pérdida de datos o inconsistencias si no se maneja correctamente.
    *   Probabilidad: Media.
    *   Mitigación: Implementación de versionado optimista (HU-151) y manejo de errores en la UI.
2.  **Disponibilidad de Catálogos:**
    *   Descripción: Los servicios de catálogo (Tipo de Seguro, Moneda, Canal de Venta) no están disponibles.
    *   Impacto: El usuario no puede seleccionar valores válidos, impidiendo guardar la cotización.
    *   Probabilidad: Baja a Media.
    *   Mitigación: Implementar Circuit Breakers, reintentos y mensajes de error claros en la UI. Considerar cachés de catálogos si son estáticos.
3.  **Complejidad de Validaciones:**
    *   Descripción: Las validaciones de RFC y Vigencia pueden ser complejas y propensas a errores.
    *   Impacto: Datos incorrectos persistidos o rechazo de datos válidos.
    *   Probabilidad: Media.
    *   Mitigación: Uso de librerías de validación estándar, amplia cobertura de pruebas unitarias para las reglas de negocio.

## 17. Criticality
**Criticality Level:** Alta
**Justification:** La capacidad de mantener los datos de las cotizaciones actualizados y precisos es fundamental para el negocio, ya que afecta directamente la validez de las cotizaciones y la posterior emisión de pólizas. Datos incorrectos pueden llevar a errores en la contratación y problemas legales.
**Feature Impact:** Sin esta funcionalidad, la característica de "Gestión de Cotizaciones" sería incompleta y propensa a manejar información desactualizada o errónea, lo que invalidaría todo el proceso de cotización.
**Critical Dependencies:** HU-144 (Catálogos) y HU-151 (Versionado Optimista) son críticas para la correcta y segura ejecución de esta historia.
**Recommended Priority:** Sprint actual / Próximo sprint (dada la prioridad "Alta").

## 18. Identified Assumptions
1.  **Permisos de Usuario:**
    *   Description: Se asume que el "usuario" tiene los permisos necesarios (rol) para editar cotizaciones.
    *   Impact if false: El usuario no podrá realizar la acción, resultando en un error de autorización.
    *   Requires validation from: Equipo de Seguridad / Product Owner.
2.  **Estado de la Cotización:**
    *   Description: Se asume que la cotización debe estar en un estado "editable" (ej. "Abierta" o "En Edición") para poder modificar sus datos generales.
    *   Impact if false: Se podrían modificar cotizaciones en estados finales (ej. "Emitida", "Cancelada"), causando inconsistencias.
    *   Requires validation from: Product Owner / Analista de Negocio.
3.  **Disponibilidad de Catálogos:**
    *   Description: Se asume que los servicios externos que proveen los catálogos (Tipo de Seguro, Moneda, Canal de Venta) estarán disponibles y responderán de manera oportuna.
    *   Impact if false: La UI podría no cargar las opciones o las validaciones fallarían, impidiendo al usuario completar la acción.
    *   Requires validation from: Equipo de Arquitectura / Equipos dueños de los servicios de catálogo.
4.  **Mecanismo de Bloqueo Optimista:**
    *   Description: Se asume que el mecanismo de versionado optimista (HU-151) estará completamente implementado y funcionando antes o concurrentemente con esta historia.
    *   Impact if false: Riesgo de sobrescritura de datos y pérdida de información debido a ediciones concurrentes.
    *   Requires validation from: Equipo de Desarrollo / Arquitectura.
