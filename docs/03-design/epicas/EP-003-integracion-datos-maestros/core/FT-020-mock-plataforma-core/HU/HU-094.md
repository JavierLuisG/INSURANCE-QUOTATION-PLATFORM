## 3. User Story
Como desarrollador,
Quiero que el mock server simule fielmente los endpoints para códigos postales y sus zonas (CAT, nivel técnico),
Para poder probar la lógica de validación y aplicación de tarifas basadas en la ubicación en el cotizador.

## 4. Functional Description
**Description:** Esta historia de usuario detalla la creación de un mock server para emular el comportamiento de un servicio externo que proporciona información de códigos postales y sus zonas asociadas (CAT y nivel técnico). El mock server debe ser capaz de responder a consultas de códigos postales válidos con la información esperada, manejar códigos postales no existentes devolviendo una respuesta de "no encontrado", y simular fallas de servicio para probar la resiliencia y el manejo de errores del cotizador. Esto permitirá al equipo de desarrollo probar la lógica de negocio del cotizador de manera aislada y eficiente.
**Flow:** HU-092 (Desarrollo del Cotizador) → HU-094 (Simulación de Endpoints de CP) → US-XXX (Pruebas de la Lógica de Tarifas por Ubicación)

## 6. Acceptance Criteria (3-5 criteria)
### AC-001: Consulta de Código Postal Válido
**Description:** Validar que el mock server devuelve correctamente la información de zona CAT y nivel técnico asociada para un código postal existente en sus datos de prueba.

```gherkin
Scenario: El cotizador consulta un código postal válido
  Given que el cotizador consulta un código postal válido (ej. "28001")
  When el mock server lo recibe
  Then devuelve la información de zona CAT y nivel técnico asociada
  And la respuesta HTTP es 200 OK
  And la respuesta incluye "zonaCAT": "ZONA_A" y "nivelTecnico": "ALTO"
```

### AC-002: Consulta de Código Postal No Existente
**Description:** Validar que el mock server responde con una indicación clara de que el código postal no fue encontrado cuando se consulta uno que no está en sus datos simulados.

```gherkin
Scenario: El cotizador consulta un código postal no existente
  Given que el cotizador consulta un código postal no existente (ej. "99999")
  When el mock server lo recibe
  Then devuelve una respuesta indicando que no se encontró el CP
  And la respuesta HTTP es 404 Not Found
  And la respuesta incluye un mensaje de error como "Código postal no encontrado"
```

### AC-003: Simulación de Falla de Servicio
**Description:** Validar que el mock server puede simular una falla de servicio interna, permitiendo al cotizador probar su manejo de errores y resiliencia.

```gherkin
Scenario: Simulación de falla de servicio
  Given que se ha configurado el mock server para simular una falla de servicio
  When el cotizador consulta un código postal
  Then recibe un error HTTP (ej. 500 Internal Server Error)
  And la respuesta incluye un mensaje de error genérico
```

## 7. Data and Business Rules


| field | type | required | default | validation | catalog | example |
|---|---|---|---|---|---|---|
| codigoPostal | string | yes | N/A | Regex de 5 dígitos numéricos | N/A | 28001 |
| zonaCAT | string | yes | N/A | Valores predefinidos (ej. 'ZONA_A', 'ZONA_B', 'ZONA_C') | Catálogo de Zonas CAT | ZONA_A |
| nivelTecnico | string | yes | N/A | Valores predefinidos (ej. 'ALTO', 'MEDIO', 'BAJO') | Catálogo de Niveles Técnicos | ALTO |


**BR-001:** Asociación Única de Código Postal a Ubicación
- Description: Cada código postal válido en el mock debe estar asociado de forma única a una zona CAT y un nivel técnico.
- Trigger: Cuando el mock server recibe una consulta por un código postal.
- Logic: El mock buscará el `codigoPostal` solicitado en su conjunto de datos simulados. Si lo encuentra, devolverá la `zonaCAT` y el `nivelTecnico` correspondientes.
- Implementation: Configuración del archivo JSON de datos de prueba del mock server.
- Exception: Si el código postal no se encuentra, se aplica la lógica de "no encontrado" (AC-002).

## 16. Technical Notes and Risks
**Risks:**
1.  **Desfase de datos del mock:** Los datos de códigos postales y zonas en el mock server podrían desactualizarse respecto a los datos reales del servicio externo, llevando a pruebas no representativas.
    *   Impacto: Pruebas engañosas que no reflejan el comportamiento en producción.
    *   Probabilidad: Media.
    *   Mitigación: Establecer un proceso para la revisión y actualización periódica de los datos del mock. Considerar la generación de datos de prueba desde una fuente de verdad si es posible.
2.  **Complejidad excesiva del mock:** Intentar simular demasiada lógica o casos complejos del servicio real podría hacer que el mock server sea difícil de mantener.
    *   Impacto: Mayor tiempo de desarrollo y mantenimiento del mock, menor agilidad.
    *   Probabilidad: Baja.
    *   Mitigación: Limitar la simulación a los escenarios críticos necesarios para el cotizador, delegando la complejidad al servicio real cuando sea necesario para pruebas de integración.

**Technical Debt:** N/A (Este mock es una herramienta de desarrollo/prueba, no se considera deuda técnica del producto principal a menos que su mantenimiento se vuelva oneroso).

## 17. Criticality
**Criticality Level:** Crítica
**Justification:** Esta historia es fundamental para el progreso del desarrollo del cotizador. Sin un mock server fiable, la lógica de validación y aplicación de tarifas basada en la ubicación no puede ser probada de manera consistente y autónoma, lo que paralizaría el desarrollo y las pruebas de una funcionalidad central.
**Feature Impact:** La no implementación o el fallo de este mock server detendría el desarrollo y las pruebas de la funcionalidad de cálculo de tarifas por ubicación en el cotizador, impactando directamente en la capacidad de entregar la feature principal.
**Critical Dependencies:** El desarrollo y las pruebas de la lógica de negocio del cotizador que interactúa con códigos postales y zonas dependen directamente de la disponibilidad y fiabilidad de este mock.
**Recommended Priority:** Sprint actual (dada su criticidad y dependencia para otras funcionalidades).

## 18. Identified Assumptions
1.  **Formato de Comunicación Consistente:**
    *   Description: Se asume que el formato de las peticiones (request) y respuestas (response) del mock server será idéntico al del servicio externo real de códigos postales.
    *   Impact if false: El cotizador no podrá comunicarse correctamente con el mock, invalidando las pruebas y requiriendo ajustes en ambos lados.
    *   Requires validation from: Equipo de desarrollo del cotizador y/o documentación del servicio externo.
2.  **Disponibilidad del Marco de Mocking:**
    *   Description: Se asume que existe un framework de mock server adecuado y fácilmente implementable que cumple con los requisitos de simulación (ej. WireMock, MockServer).
    *   Impact if false: Se requeriría un esfuerzo adicional para desarrollar un mock server personalizado, aumentando el tiempo de implementación.
    *   Requires validation from: Equipo de arquitectura/desarrollo.
3.  **Configuración de Entorno Sencilla:**
    *   Description: Se asume que el cotizador puede ser configurado fácilmente para apuntar al mock server en entornos de desarrollo/pruebas y al servicio real en producción (ej. mediante variables de entorno).
    *   Impact if false: Dificultad para alternar entre entornos, aumentando el riesgo de errores de configuración.
    *   Requires validation from: Equipo de DevOps/Infraestructura.
