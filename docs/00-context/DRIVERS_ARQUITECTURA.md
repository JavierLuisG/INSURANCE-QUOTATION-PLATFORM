# Drivers de Arquitectura

El siguiente análisis detalla la evolución de los drivers arquitectónicos, transformando los requisitos y preocupaciones identificados en las fases previas en un conjunto refinado y cuantificado para guiar la arquitectura objetivo.

> **Nota sobre el stack tecnológico**: Las versiones específicas, frameworks, bibliotecas y herramientas de implementación están centralizados en **TECH_STACK.md**. Este documento define los *qué* y los *por qué* arquitectónicos; TECH_STACK.md define el *con qué* se implementan.

## 6. Supuestos

- **Contratos de `Plataforma-core-ohs` Estables**: Los contratos de la API REST del servicio (simulado o real) para catálogos y tarifas son estables y bien definidos, lo que permite diseñar integraciones y el mock server de forma precisa desde el inicio.
- **Fórmulas de Cálculo Simplificadas Suficientes**: Las fórmulas simplificadas y documentadas para el cálculo de los 14 componentes técnicos de prima son suficientes para el alcance del proyecto, sin requerir lógica actuarial compleja no especificada.
- **Límite de Ubicaciones Fijo en Esta Fase**: El límite de 10 ubicaciones por cotización es una restricción adecuada para las necesidades actuales del negocio y no se revisará dentro del alcance del proyecto.
- **Disponibilidad de Herramientas de Desarrollo y Pruebas**: Las herramientas necesarias (IDE, herramientas de cobertura de código, frameworks de pruebas de carga, bibliotecas de resiliencia) estarán disponibles y configuradas durante el ciclo de desarrollo conforme a lo definido en **TECH_STACK.md**.
- **Autenticación Simplificada en Esta Fase**: La autenticación y autorización se basan en un modelo interno de usuario/contraseña con roles (Agente, Asegurado), sin integración con sistemas de identidad corporativos (SSO, LDAP) en esta fase.
- **Datos de Prueba Representativos para Mock**: Los datos utilizados para poblar el mock server de `Plataforma-core-ohs` mediante migraciones de datos versionadas serán representativos de los datos reales, permitiendo desarrollo y pruebas realistas para los 14 componentes de cálculo.
- **Cotización como Unidad de Persistencia**: La cotización, junto con sus ubicaciones embebidas, puede persistirse de forma atómica a nivel de documento en la base de datos principal sin requerir transacciones multi-documento en la primera versión.

## 7. Fuera de Alcance Técnico

| id | descripcion_exclusion | justificacion | implicacion |
|---|---|---|---|
| OOS-001 | Replicación exacta de una fórmula actuarial real | El proyecto se centra en una lógica de cálculo simplificada, documentada y trazable para los 14 componentes técnicos, no en la implementación de una fórmula actuarial compleja si no fue entregada. | Los resultados de prima serán representativos y consistentes, pero no necesariamente idénticos a los de un sistema actuarial real. Se prioriza la trazabilidad y la consistencia sobre la exactitud actuarial compleja. |
| OOS-002 | Implementación de un servicio real de `Plataforma-core-ohs` | El alcance permite y fomenta el uso de un stub, mock server o fixtures versionadas para simular este servicio externo (ver TECH_STACK.md para la implementación específica del simulador). | El desarrollo no depende de la disponibilidad de un servicio externo real, pero la simulación debe replicar fielmente los contratos y comportamientos esperados, incluyendo escenarios de error y latencia. |
| OOS-003 | Pipeline de CI/CD y `docker-compose.yml` como entregables obligatorios | Son entregables opcionales del reto técnico. Pueden usarse internamente para facilitar el desarrollo pero no son mandatorios. | La ausencia de un pipeline formal puede requerir procesos de despliegue manuales. Se espera que la solución sea ejecutable localmente con instrucciones claras en el README. |
| OOS-004 | Cobertura de pruebas al 100% | El requisito mínimo es 80% en pruebas unitarias y 3 flujos críticos automatizados, no cobertura exhaustiva. | Algunas partes menos críticas del código pueden no tener cobertura automatizada. El esfuerzo de pruebas se concentra en el motor de cálculo (>90%) y los flujos de negocio principales. |
| OOS-005 | Integración con sistemas de identidad corporativos (SSO, LDAP, OAuth2) | La autenticación interna con gestión de usuarios propia está especificada en los requisitos. | El sistema tendrá su propio almacén de usuarios y credenciales. No se beneficiará de inicio de sesión unificado. Esta integración queda como mejora futura. |
| OOS-006 | Exportación de resultados a PDF/Excel | No está dentro del alcance funcional mínimo del reto técnico. | Los resultados financieros se visualizan en la interfaz web (tabla interactiva con desglose por componente y ubicación) pero no se exportan a formatos externos en esta versión. |
| OOS-007 | Invalidación de caché por eventos (webhooks, mensajería) | La estrategia de caché se basa únicamente en TTL configurable en la primera versión. | La caché puede servir datos ligeramente desactualizados dentro del TTL definido. La invalidación por eventos queda como mejora futura si se requiere mayor frescura de datos. |

## 9. Resumen de Cambios AS-IS → TO-BE

| Aspecto | AS-IS (Estado actual / sin sistema) | TO-BE (Objetivo a construir) | Mejora / Impacto KPI | Driver de Negocio |
|---|---|---|---|---|
| **Gestión de folios** | Proceso manual, sin idempotencia garantizada | Generación automática idempotente con patrón `COT-AAAA-NNNNNN`, reintentos y notificación de fallo | Eliminación de duplicados, trazabilidad desde el primer registro | RFR-001, RNF-016 |
| **Rendimiento UI** | Sin sistema — objetivo a cumplir: P95 < 500ms, carga inicial < 2s | Latencia P95 UI < 500ms, carga inicial < 2s con CDN, caché de navegador y optimización de bundles | Satisfacción del usuario y productividad de agentes desde el primer sprint | RNF-001 |
| **Rendimiento CRUD** | Sin sistema — objetivo: P95 < 1.5s | P95 CRUD < 1.5s con indexación en la base de datos por `numeroFolio` y conexiones persistentes | Eficiencia en gestión de datos, menor tiempo de espera | RNF-002 |
| **Rendimiento Cálculo** | Sin sistema — objetivo: P98 < 3s para 10 ubicaciones | P98 < 3s con caching de tarifas (TTL configurable), motor modular por componente y cálculo optimizado | Toma de decisiones rápida, experiencia de usuario ágil | RNF-003 |
| **Escalabilidad** | Sin sistema — objetivo: 500 usuarios concurrentes | >500 usuarios con servicios stateless, auto-scaling horizontal y contenedorización | Capacidad para crecer con la demanda del negocio | RNF-004 |
| **Disponibilidad** | Sin sistema — objetivo: uptime >99.5% | >99.5% con despliegue HA, balanceo de carga y tolerancia a fallos | Continuidad del negocio, acceso confiable al cotizador | RNF-008 |
| **Resiliencia ante fallo externo** | Sin mecanismo de resiliencia — dependencia total del servicio core | Circuit Breaker + Retry con backoff + caché de datos críticos. Funcionalidad degradada con mensaje amigable en <5s | Reducción del riesgo de fallo completo ante inestabilidad de `Plataforma-core-ohs` | RNF-017, RFR-004 |
| **Motor de cálculo** | Sin sistema — cálculo manual propenso a errores | Motor modular con 14 componentes técnicos, cálculo por ubicación calculable, persistencia atómica de resultados y snapshot de trazabilidad | Eliminación de errores de cálculo manual, auditabilidad completa | RFR-003, RNF-015 |
| **Ubicaciones incompletas** | Sin comportamiento definido — bloqueo total implícito | Ubicaciones incompletas generan `alertasBloqueantes` y se excluyen individualmente; el cálculo continúa con las ubicaciones válidas | Flexibilidad operativa: permite cotizaciones parciales mientras se completan datos | RFR-008 |
| **Gestión de ubicaciones** | Sin sistema — proceso manual con eliminación libre | Registro, edición y marcado como inactiva (no eliminación física). Hasta 10 ubicaciones con todos los campos del dominio | Historial preservado, integridad del documento de cotización | RFR-002 |

| **Concurrencia** | Sin sistema — riesgo de sobrescritura silenciosa | Versionado optimista con campo `version` incremental, detección de conflictos y notificación al usuario para recarga | Integridad de datos garantizada en entornos multiusuario | RFR-006, RNF-014 |
| **Datos maestros** | Carga manual de archivos o ingreso directo (proceso AS-IS del negocio) | Integración con `Plataforma-core-ohs` (simulado/real) con caché diferenciada por tipo de dato (catálogos: 12-24h; tarifas: 1-6h) | Eliminación del esfuerzo manual, datos actualizados y consistentes en toda la aplicación | EP-003 |
