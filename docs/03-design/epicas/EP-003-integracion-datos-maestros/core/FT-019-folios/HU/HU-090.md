## 2. Enabled Capability
**CAP-090:** Gestión de Idempotencia de Folios
**Business Value:** Evitar la creación de folios duplicados para la misma solicitud de cotización, asegurando la consistencia de los datos y la integridad del proceso de negocio.
**Requires:** HU-086 (Solicitud de Cotización)
**Enables:** HU-XXX - Procesos de negocio que requieren folios únicos (ej. facturación, seguimiento de ventas)
**Orchestrates:** Servicio de generación de folios, Mecanismo de detección de solicitudes duplicadas

## 3. User Story
Como Sistema,
Quiero que la generación de folios sea idempotente,
Para que se evite la creación de folios duplicados para la misma solicitud de cotización.

## 4. Functional Description
**Description:** Esta historia de usuario asegura que el proceso de generación de folios para cotizaciones sea idempotente. Esto significa que, independientemente de cuántas veces se reciba una solicitud para generar un folio para una cotización específica (identificada por un `solicitudId` único), solo se creará un único folio. El sistema utilizará este identificador de solicitud único para verificar si ya existe un folio asociado a dicha solicitud o a la cotización. Si ya existe, se devolverá el folio existente; de lo contrario, se generará uno nuevo y se asociará.
**Flow:** [HU-086 Solicitud de Cotización] → [HU-090 Generación Idempotente de Folios] → [HU-XXX Asignación de Folio a Cotización]

## 6. Acceptance Criteria (3-5 criteria)
### AC-001: Devolver folio existente si la cotización ya tiene uno asignado.
**Description:** Validar que, si se intenta generar un folio para una cotización que ya posee uno, el sistema identifique esta situación y devuelva el folio previamente asignado sin generar uno nuevo.

```gherkin
Scenario: Intento de generar folio para una cotización que ya tiene uno asignado
  Given una cotización con el ID "COT-123" ya tiene el folio "FOL-456" asignado
  When el sistema recibe una solicitud para generar un folio para "COT-123" con el ID de solicitud "REQ-001"
  Then el sistema devuelve el folio "FOL-456"
  And no se genera un nuevo folio
```

### AC-002: Generación de un único folio ante múltiples reintentos para la misma solicitud.
**Description:** Asegurar que, incluso si una solicitud de generación de folio es procesada varias veces (ej. por reintentos de red), el sistema garantice que solo se genere un único folio para ese identificador de solicitud.

```gherkin
Scenario: Múltiples reintentos de red para la misma solicitud de folio
  Given una cotización con el ID "COT-789" no tiene un folio asignado
  And el sistema recibe la solicitud de generación de folio con el ID de solicitud "REQ-002" múltiples veces
  When el sistema procesa estas solicitudes
  Then solo se genera un único folio para "COT-789" asociado a "REQ-002"
  And las solicitudes posteriores con el mismo "REQ-002" devuelven el folio ya generado
```

### AC-003: Uso de identificador de solicitud único para la verificación de idempotencia.
**Description:** Confirmar que el sistema utiliza un identificador de solicitud único (ej. ID de transacción) para verificar si una solicitud de generación de folio ya ha sido procesada previamente.

```gherkin
Scenario: Verificación de folio existente mediante ID de solicitud único
  Given una solicitud de generación de folio con el ID de solicitud "TRANS-ABC"
  When el sistema intenta generar un folio
  Then el sistema utiliza "TRANS-ABC" para verificar si ya se generó un folio previamente para esta solicitud
```

**BR-001:** Detección de Folio Existente para Cotización
- Description: Si la cotización asociada a la solicitud ya tiene un folio asignado, el sistema debe retornar ese folio sin generar uno nuevo.
- Trigger: Al recibir una solicitud de generación de folio.
- Logic: `IF cotizacion.folio IS NOT NULL THEN RETURN cotizacion.folio`.
- Implementation: Servicio de generación de folios.
- Exception: Si el `cotizacionId` no existe, se debe lanzar un error.

**BR-002:** Detección de Solicitud de Folio Duplicada por `solicitudId`
- Description: Utilizar el `solicitudId` proporcionado para verificar si ya se ha procesado previamente una solicitud de generación de folio. Si es así, se debe devolver el folio asociado a ese `solicitudId`.
- Trigger: Al recibir una solicitud de generación de folio.
- Logic: `IF existeMapeo(solicitudId) THEN RETURN folioAsociado(solicitudId) ELSE GENERAR_Y_MAPEAR_FOLIO(solicitudId)`.
- Implementation: Mecanismo de detección de solicitudes duplicadas (posiblemente una tabla de mapeo `solicitudId -> folioGenerado`).

## 16. Technical Notes and Risks
**Technical Notes:**
- La "Nota de Implementación" original ("Puede requerir un identificador de solicitud/transacción en la entrada de la API") se ha formalizado como el campo `solicitudId` en los datos y los ACs.
- Se recomienda usar una base de datos o caché distribuida para el mapeo `solicitudId -> folioGenerado` para asegurar la consistencia en entornos escalables.
- Considerar la vida útil de los registros de `solicitudId` para evitar el crecimiento ilimitado de la tabla de mapeo.

**Risks:**
1.  **Consistencia Transaccional**:
    - Descripción: Si la generación del folio y el registro del mapeo `solicitudId -> folioGenerado` no son atómicos o transaccionales, podría haber inconsistencias (folio generado pero no mapeado, o viceversa).
    - Impacto: Fallos en la idempotencia, folios duplicados o solicitudes que fallan incorrectamente.
    - Probabilidad: Media.
    - Mitigación: Implementar un patrón transaccional (ej. Two-Phase Commit si es distribuido, transacciones de DB si es local), o un mecanismo de compensación/reconciliación.
2.  **Rendimiento del Mecanismo de Detección**:
    - Descripción: Si el volumen de solicitudes es muy alto y el mecanismo de detección de `solicitudId` no es eficiente, podría convertirse en un cuello de botella.
    - Impacto: Alta latencia en la generación de folios, afectando la experiencia del usuario y la capacidad del sistema.
    - Probabilidad: Media.
    - Mitigación: Utilizar una base de datos optimizada para lecturas/escrituras rápidas (ej. NoSQL, caché), indexación adecuada, o un servicio de caché distribuido.

## 17. Criticality
**Criticality Level:** Alta
**Justification:** La generación de folios únicos es un requisito fundamental para la integridad de los procesos de negocio relacionados con las cotizaciones (ej. seguimiento, facturación, auditoría). La falta de idempotencia llevaría a inconsistencias de datos y errores operacionales significativos.
**Feature Impact:** La no implementación o una implementación fallida de esta historia resultaría en la creación de folios duplicados, lo que invalidaría la unicidad de las cotizaciones y causaría serios problemas en la gestión y el seguimiento de las mismas, afectando la confianza en el sistema.
**Critical Dependencies:** Cualquier proceso de negocio que dependa de la unicidad de los folios de cotización (ej., facturación, reportes contables, integración con CRM/ERP).
**Recommended Priority:** Sprint actual o próximo (dependiendo de la fase del proyecto).

## 18. Identified Assumptions
1.  **Disponibilidad y Unicidad del `solicitudId`**:
    - Description: Se asume que el sistema que invoca la generación de folios siempre proporcionará un `solicitudId` único y consistente para cada *intento de generación de folio lógico*.
    - Impact if false: El mecanismo de idempotencia no funcionará correctamente, pudiendo generar folios duplicados si el `solicitudId` no es único, o fallos si no se proporciona.
    - Requires validation from: Equipo de integración/consumidor del servicio de generación de folios.
2.  **Mecanismo de Almacenamiento Persistente para Mapeo**:
    - Description: Se asume la existencia y disponibilidad de un mecanismo de almacenamiento persistente y de alto rendimiento para mapear `solicitudId` a `folioGenerado`.
    - Impact if false: La idempotencia no se podrá garantizar entre reinicios del servicio o en entornos distribuidos, llevando a la generación de folios duplicados.
    - Requires validation from: Equipo técnico/arquitectura.
3.  **Vida Útil de los Mapeos**:
    - Description: Se asume que los mapeos `solicitudId -> folioGenerado` no necesitan persistir indefinidamente y pueden tener una política de caducidad (ej. 30 días) para evitar un crecimiento ilimitado del almacenamiento.
    - Impact if false: Crecimiento descontrolado de la base de datos/caché, afectando el rendimiento y los costos.
    - Requires validation from: Propietario del producto/Negocio para definir la política de retención.
