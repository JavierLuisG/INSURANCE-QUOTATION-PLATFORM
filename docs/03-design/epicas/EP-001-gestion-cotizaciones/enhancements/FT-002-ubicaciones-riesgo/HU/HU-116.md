## 1. Identificación General
**Feature:** Gestión de Cotizaciones
**Capability:** CAP-116 - Edición de Ubicación de Riesgo
**Actor:** Usuario (Agente/Suscriptor)
**Bounded Context:** Cotizaciones / Gestión de Riesgos
**Story Points:** 3

## 2. Enabled Capability
**CAP-116:** Edición de Ubicación de Riesgo
**Business Value:** Asegurar la precisión de la evaluación del riesgo y la correcta emisión de pólizas, mejorando la calidad y validez de los datos de la cotización.
**Requires:** CAP-115 (Agregar Nueva Ubicación de Riesgo), CAP-00X (Visualización de Ubicaciones en Cotización)
**Enables:** CAP-155 (Validar Datos Específicos de Ubicación de Riesgo), CAP-00Y (Cálculo de Prima de Riesgo)
**Orchestrates:** Servicio de Códigos Postales/Zonas Catastróficas (implícito), Servicio de Validación de Cotizaciones.

## 3. User Story
Como usuario,
Quiero modificar los datos específicos de una ubicación de riesgo existente con todos sus campos del dominio,
Para asegurar la precisión de la evaluación del riesgo.

## 4. Functional Description
**Description:** El usuario selecciona una cotización existente y elige una ubicación de riesgo para editar. El sistema carga los datos actuales de la ubicación en un formulario interactivo. El usuario puede modificar cualquiera de los campos del dominio de la ubicación (ej. `nombreUbicacion`, `direccion`, `codigoPostal`, `tipoConstructivo`, `giro`, `garantías[]`). Al ingresar un `codigoPostal` válido, el sistema debe actualizar automáticamente la información de `zonaCatastrofica` y nivel técnico asociada. Una vez que el usuario guarda los cambios, la información se persiste en el backend a través de una llamada `PATCH` al recurso de la ubicación. El backend recalcula automáticamente el `estadoValidacion` y las `alertasBloqueantes` de la ubicación. Si se intentan guardar datos inválidos, el sistema debe informar al usuario sobre los campos problemáticos, mostrando visualmente las `alertasBloqueantes`.
**Flow:** HU-115 (Agregar Nueva Ubicación de Riesgo) → HU-116 (Editar Detalles de Ubicación de Riesgo) → HU-155 (Validar Datos Específicos de Ubicación de Riesgo)

**BR-001: Recálculo de `estadoValidacion`**
- Description: Después de cada operación de guardado exitosa de una ubicación, el backend debe recalcular el `estadoValidacion` de esa ubicación basándose en todas las reglas de negocio aplicables a sus campos.
- Trigger: Almacenamiento exitoso de cambios de ubicación vía `PATCH`.
- Logic: El servicio de validación de cotizaciones evalúa la integridad y completitud de los datos de la ubicación.
- Implementation: Servicio de backend (quotes-service).
- Exception: Si la validación encuentra errores, el estado puede ser 'INVALIDO'.

**BR-002: Actualización Automática de `zonaCatastrofica`**
- Description: Cuando se modifica el `codigoPostal` de una ubicación y este es válido, el sistema debe consultar un servicio externo/interno para obtener y actualizar los datos de `zonaCatastrofica` y nivel técnico asociados.
- Trigger: Cambio y validación del campo `codigoPostal`.
- Logic: Invocar `postal-code-service` con el `codigoPostal` para obtener los datos catastróficos.
- Implementation: Backend (quotes-service, integrando con postal-code-service).
- Exception: Si el código postal es inválido o el servicio externo falla, `zonaCatastrofica` no se actualiza y se genera una alerta.

**BR-003: Identificación de `alertasBloqueantes`**
- Description: Si durante el proceso de guardado se detectan datos inválidos (según las reglas de negocio o de formato), el sistema debe identificar los campos específicos con problemas y agregarlos a la lista `alertasBloqueantes` de la ubicación.
- Trigger: Intento de guardar datos que no cumplen con las validaciones.
- Logic: El servicio de validación de negocio identifica los campos con errores y los retorna.
- Implementation: Backend (quotes-service).
- Exception: N/A

## 10. UX and Navigation Flow
**UX Flow:**
1.  El usuario navega a la vista de una cotización específica.
2.  En la sección de "Ubicaciones", selecciona una ubicación existente (ej. haciendo clic en un botón de "Editar" o en la fila de la tabla).
3.  Se presenta un formulario modal o una nueva pantalla con todos los campos de la ubicación precargados.
4.  El usuario modifica los campos deseados.
5.  Al modificar el `codigoPostal`, el sistema realiza una validación en tiempo real (o al perder el foco) y actualiza los campos de `zonaCatastrofica`.
6.  El usuario hace clic en el botón "Guardar".
7.  Si hay errores, el formulario resalta los campos con `alertasBloqueantes` y muestra mensajes de error.
8.  Si es exitoso, se muestra un mensaje de éxito y la pantalla regresa a la vista de la cotización con la ubicación actualizada.
**Messages/Modals:**
*   Mensaje de éxito: "Ubicación [nombreUbicacion] actualizada correctamente."
*   Mensaje de error al guardar: "No se pudo actualizar la ubicación. Por favor, revise los campos marcados."
*   Mensajes de validación en línea junto a los campos afectados por `alertasBloqueantes`.
**Stepper/Breadcrumbs:** Cotización > [Folio Cotización] > Ubicaciones > Editar Ubicación

## 11. Architecture and Technical Dependencies
- **Backend Service:** `quotes-service` (API REST: `PATCH /v1/quotes/{folio}/locations/{índice}`). Responsable de la persistencia, validación de negocio y recálculo de estados.
- **External Service:** `postal-code-service` (API REST: `GET /v1/postal-codes/{codigoPostal}`). Propósito: Obtener datos de `zonaCatastrofica` y nivel técnico. Timeout: 2000ms, Retries: 1.
- **Frontend Application:** Aplicación web (ej. React/Angular/Vue) para la interfaz de usuario del formulario de edición y manejo de la lógica de UI.
- **Database:** Base de datos de cotizaciones (ej. PostgreSQL) para almacenar los datos de las ubicaciones.

## 13. Edge Cases and Exceptions
### Case 1: Código Postal Inexistente o Inválido
```gherkin
Scenario: Ingresar un código postal que no existe
  Given Estoy editando una ubicación y el campo `codigoPostal` es requerido
  When Ingreso un `codigoPostal` que no se encuentra en el `postal-code-service` o tiene un formato inválido
  Then El sistema marca el campo `codigoPostal` como parte de `alertasBloqueantes` y `zonaCatastrofica` no se actualiza, permaneciendo con su valor anterior o nulo.
```

### Case 2: Fallo en la Integración con `postal-code-service`
```gherkin
Scenario: El servicio de códigos postales no responde
  Given Ingreso un `codigoPostal` válido en el formulario de edición
  When El sistema intenta consultar el `postal-code-service` y este falla (ej. timeout, error de servicio)
  Then El sistema muestra un mensaje de error genérico (ej. "No se pudo validar el código postal") o marca el campo `codigoPostal` con una alerta temporal, y `zonaCatastrofica` no se actualiza.
```

### Case 3: Usuario sin Permisos
```gherkin
Scenario: Un usuario sin los roles adecuados intenta editar una ubicación
  Given Un usuario con rol 'Visualizador' intenta acceder a la funcionalidad de edición de una ubicación
  When Intenta hacer clic en el botón 'Editar' o enviar el formulario de edición
  Then El botón 'Editar' está deshabilitado o el sistema retorna un error de autorización (HTTP 403 Forbidden).
```

## 16. Technical Notes and Risks
**Risks:**
1.  **Consistencia de Datos:**
    -   Description: Riesgo de que los datos de la ubicación se corrompan o se pierdan si la operación de `PATCH` falla en medio de la transacción.
    -   Impact: Datos de cotización incorrectos, impacto en la evaluación de riesgo y emisión de pólizas.
    -   Probability: Media.
    -   Mitigation: Implementar transacciones de base de datos o mecanismos de compensación en el backend. Validar la integridad de los datos antes y después del guardado.
2.  **Rendimiento de Integraciones:**
    -   Description: La dependencia del `postal-code-service` podría introducir latencia o puntos de fallo si el servicio es lento o inestable.
    -   Impact: Mala experiencia de usuario (UI lenta), datos incompletos en `zonaCatastrofica`.
    -   Probability: Baja-Media.
    -   Mitigation: Implementar caché para códigos postales frecuentes, Circuit Breaker, manejo asíncrono y mensajes de carga en la UI.
3.  **Complejidad del Formulario:**
    -   Description: Un formulario con "todos los campos del dominio" puede ser muy extenso, afectando la UX y la mantenibilidad del frontend.
    -   Impact: Mayor tiempo de desarrollo, errores de UI, frustración del usuario.
    -   Probability: Media.
    -   Mitigation: Considerar dividir el formulario en secciones lógicas o usar componentes de formulario dinámicos.

**Technical Debt:** N/A (Se determinará por el equipo operativo según el alcance y el MVP).

## 17. Criticality
**Criticality Level:** Alta
**Justification:** La precisión de los datos de la ubicación es fundamental para la correcta evaluación de riesgos, el cálculo de primas y la emisión de pólizas. Errores aquí pueden llevar a un subaseguramiento, fraude o rechazo de siniestros.
**Feature Impact:** La incapacidad de editar datos de ubicación precisos impacta directamente la validez y utilidad de todo el proceso de cotización y emisión.
**Critical Dependencies:** Todas las historias de usuario relacionadas con la validación de cotizaciones, cálculo de primas y emisión de pólizas dependen de que esta historia funcione correctamente.
**Recommended Priority:** Sprint actual (dada la prioridad "Alta" y la importancia para el negocio).

    -   Description: Se asume que el `postal-code-service` (o similar) existe, está disponible y es estable para consultar la información de `zonaCatastrofica` y nivel técnico.

    -   Description: Se asume que todos los catálogos de datos (estados, municipios, colonias, ciudades, tipos constructivos, giros, garantías) necesarios para los campos de ubicación están disponibles y actualizados.
    -   Impact if false: Errores de validación, imposibilidad de seleccionar valores correctos, datos inconsistentes.
    -   Requires validation from: Equipo de Datos / Product Owner.
