**Feature:** Gestión de Caché
**Capability:** CAP-001 - Invalidación de Caché Bajo Demanda
**Actor:** Sistema, Administrador
**Bounded Context:** Gestión de Caché
**Story Points:** 4

## 2. Enabled Capability
**CAP-001:** Invalidación de Caché Bajo Demanda
**Business Value:** Reflejar cambios urgentes en los datos maestros de forma inmediata, asegurando la consistencia de los datos y la toma de decisiones basada en información actualizada.
**Requires:** HU-105 (implica un sistema de caché funcional)
**Enables:** Consistencia de datos para funcionalidades que dependen de datos maestros actualizados.
**Orchestrates:** Servicio de Caché, Plataforma-core-ohs (para eventos)

## 3. User Story
Como un **sistema**,
Quiero **poder invalidar la caché bajo demanda (ej. por evento de actualización o acción manual)**,
Para **reflejar cambios urgentes en los datos maestros de forma inmediata**.

## 4. Functional Description
**Description:** Esta historia de usuario describe la capacidad del sistema para invalidar entradas de caché específicas para datos maestros. La invalidación puede ser activada de dos maneras: automáticamente, al detectar un evento de actualización proveniente del servicio `Plataforma-core-ohs` (ej. a través de un webhook o mensaje de cola), o manualmente, a solicitud de un administrador (ej. vía una API interna). El objetivo es asegurar que los cambios urgentes en los datos maestros se reflejen inmediatamente, forzando al sistema a consultar la fuente original en las siguientes peticiones. La implementación debe ser granular para evitar impactos innecesarios en el rendimiento de otros datos en caché.
**Flow:** `Plataforma-core-ohs` (actualización de datos) → [Detección de evento O Solicitud manual] → **HU-108: Invalidación de Caché** → [Lectura de datos maestros actualizada desde la fuente original]

## 5. Expected Results


| element | description |
|---|---|
| Data | La entrada de caché correspondiente al dato maestro afectado es eliminada o marcada como inválida en el servicio de caché. Los datos maestros en la fuente original permanecen inalterados. |
| States | El estado de la entrada de caché para el dato maestro específico cambia de 'válida' a 'inválida' o 'inexistente'. Las siguientes consultas a ese dato reflejarán el estado de la fuente original. |
| Notifications | Posibles logs de éxito o error de la operación de invalidación. Si la invalidación es manual, el administrador recibirá una confirmación en la UI o vía API. |
| Integrations | Interacción con el servicio `Plataforma-core-ohs` (para recibir eventos de actualización) y con el servicio de gestión de caché. |
| Kafka | Si se utiliza, el sistema podría consumir eventos de actualización de un topic de Kafka, o publicar un evento de auditoría de invalidación de caché. |
| Logs | Registros de auditoría para cada operación de invalidación (automática o manual), incluyendo la clave invalidada, el origen (evento/usuario) y el resultado. |
| UI | (Para invalidación manual) Una interfaz administrativa o un endpoint API interno para que los administradores puedan solicitar la invalidación de un catálogo específico. |


## 6. Acceptance Criteria
### AC-001: Invalidación por Evento de Actualización
**Description:** Validar que el sistema detecta eventos de actualización de `Plataforma-core-ohs` e invalida la entrada de caché correspondiente.

```gherkin
Scenario: El sistema invalida la caché tras un evento de actualización de Plataforma-core-ohs
  Given un evento de actualización se produce en el servicio `Plataforma-core-ohs` para el dato maestro "Producto A"
  And la entrada de caché para el dato maestro "Producto A" es válida y existe
  When el sistema detecta este evento de actualización (ej. vía webhook o mensaje de cola)
  Then la entrada de caché correspondiente al dato maestro "Producto A" es invalidada
  And las siguientes consultas al dato maestro "Producto A" irán a la fuente original
```

### AC-002: Invalidación Manual de Catálogo
**Description:** Validar que un administrador puede solicitar la invalidación de la caché de un catálogo específico.

```gherkin
Scenario: Un administrador invalida la caché de un catálogo específico bajo demanda
  Given un administrador tiene permisos para invalidar la caché
  And la caché del "Catálogo de Productos" es válida
  When el administrador solicita la invalidación de la caché para el "Catálogo de Productos" vía una API interna
  Then la caché del "Catálogo de Productos" es invalidada
  And las siguientes consultas al "Catálogo de Productos" irán a la fuente original
```

### AC-003: Comportamiento Post-Invalidación
**Description:** Validar que tras una invalidación, las subsecuentes solicitudes de datos van a la fuente original.

```gherkin
Scenario: Las consultas posteriores a la invalidación acceden a la fuente original
  Given la caché para el dato maestro "Cliente XYZ" ha sido invalidada
  When se realiza una consulta al dato maestro "Cliente XYZ"
  Then el sistema consulta la fuente original para obtener el dato maestro "Cliente XYZ"
  And el dato maestro "Cliente XYZ" se vuelve a cachear con la información actualizada
```

**BR-001:** Granularidad de Invalidación
- Description: La invalidación de la caché debe ser granular, afectando solo la entrada o el conjunto de entradas específicas relacionadas con el evento o solicitud, sin invalidar toda la caché.
- Trigger: Cada vez que se realiza una operación de invalidación de caché.
- Logic: El mecanismo de invalidación debe usar claves o patrones de clave específicos para identificar las entradas a invalidar.
- Implementation: Servicio de gestión de caché.
- Exception: N/A.

## 9. Administrative Functionality (if applicable)
**Description:** Un administrador podrá acceder a una interfaz o endpoint API interno para solicitar la invalidación de catálogos o claves de caché específicos, lo que es útil para refrescar datos que no se actualizan por eventos automáticos o en casos de emergencia.

```gherkin
Scenario: Un administrador solicita la invalidación manual de un catálogo
  Given un administrador ha iniciado sesión en la herramienta de administración de caché
  And el administrador tiene el rol "Administrador de Caché"
  When el administrador selecciona el "Catálogo de Clientes" y hace clic en "Invalidar Caché"

  And el administrador recibe una confirmación de éxito en la UI
```

## 11. Architecture and Technical Dependencies
- **API de gestión de caché**: Servicio centralizado o librería que expone la funcionalidad de invalidación (ej. Redis, Memcached, o un servicio wrapper).
- **Mecanismo de escucha de eventos**: Webhook listener, consumidor de Kafka, o un servicio de mensajería (ej. RabbitMQ, SQS) para detectar eventos de `Plataforma-core-ohs`.
- **`Plataforma-core-ohs`**: Servicio fuente de los datos maestros y generador de eventos de actualización.
- **HU-105**: Prerrequisito para la existencia y gestión de la caché.

## 13. Edge Cases and Exceptions
### Case 1: Evento de Actualización con Clave de Caché No Existente
```gherkin
Scenario: Recepción de evento para clave de caché no existente
  Given un evento de actualización para el dato maestro "Producto Z" es recibido
  And no existe una entrada de caché para el dato maestro "Producto Z" en el servicio de caché
  When el sistema intenta invalidar la caché para el dato maestro "Producto Z"
  Then la operación de invalidación se completa sin error
  And se registra un log informativo indicando que la clave no existía
```

### Case 2: Fallo en la Comunicación con el Servicio de Caché
```gherkin
Scenario: Fallo en la comunicación con el servicio de caché durante la invalidación
  Given un evento de actualización válido se produce o una solicitud manual es hecha
  And el servicio de gestión de caché no está disponible o responde con error
  When el sistema intenta invalidar la entrada de caché correspondiente
  Then la operación de invalidación falla
  And se registra un log de error crítico
  And se podría activar un mecanismo de alerta o reintento
```

## 16. Technical Notes and Risks
**Risks:**
1.  **Consistencia de Eventos**: Si el mecanismo de escucha de eventos falla o pierde eventos de `Plataforma-core-ohs`, la caché podría quedar desactualizada.
    *   Impacto: Datos inconsistentes para los usuarios, lo que puede llevar a decisiones erróneas.
    *   Probabilidad: Media.
    *   Mitigación: Implementar reintentos, colas de mensajes duraderas, monitoreo de eventos perdidos, y mecanismos de reconciliación periódicos.
2.  **Sobrecarga del Servicio de Caché**: Un alto volumen de eventos de actualización o solicitudes manuales podría sobrecargar el servicio de caché.
    *   Impacto: Degradación del rendimiento general del sistema.
    *   Probabilidad: Baja a Media (dependiendo del volumen de datos y la frecuencia de actualización).
    *   Mitigación: Asegurar que el servicio de caché sea escalable, implementar limitación de tasas (rate limiting) para la API de invalidación manual, optimizar la granularidad de la invalidación.
**Technical Debt:** Considerar la implementación de un mecanismo de "soft invalidation" (marcar como obsoleto y refrescar en segundo plano) en lugar de la eliminación directa para reducir picos de carga en la fuente original, si el rendimiento es un factor crítico y la consistencia inmediata no es absoluta.

## 17. Criticality
**Criticality Level:** Media
**Justification:** La invalidación bajo demanda es crucial para mantener la consistencia de los datos maestros y asegurar que los cambios urgentes se reflejen rápidamente. Aunque un TTL puede mitigar parcialmente la necesidad, esta funcionalidad es vital para la precisión de los datos en tiempo real.
**Feature Impact:** La no implementación o el fallo de esta funcionalidad podría resultar en que los usuarios o sistemas dependientes operen con datos desactualizados, lo que puede llevar a errores operativos o decisiones incorrectas.
**Critical Dependencies:** Cualquier otra historia de usuario o funcionalidad que requiera acceder a la versión más reciente de los datos maestros de forma inmediata.
**Recommended Priority:** Sprint Actual o Siguiente Sprint, dependiendo de la frecuencia y criticidad de las actualizaciones de datos maestros.

## 18. Identified Assumptions
1.  **Mecanismo de Detección de Eventos Confiable**:
    *   Description: Se asume que existe o se puede implementar un mecanismo fiable (ej. webhook, cola de mensajes) para que el sistema detecte los eventos de actualización provenientes de `Plataforma-core-ohs`.
    *   Impact if false: La invalidación automática no funcionaría, lo que requeriría invalidaciones manuales constantes o un TTL muy bajo en la caché, comprometiendo la eficiencia.
    *   Requires validation from: Equipo de Arquitectura, Equipo de `Plataforma-core-ohs`.
2.  **API de Gestión de Caché Granular Disponible**:
    *   Description: Se asume que la plataforma de caché subyacente (ej. Redis, Memcached) expone o permite la implementación de una API para invalidar entradas específicas o grupos de entradas de forma granular.
    *   Impact if false: La implementación sería mucho más compleja o requeriría invalidar la caché completa, afectando el rendimiento.
    *   Requires validation from: Equipo de Infraestructura, Equipo de Desarrollo de Caché.
3.  **Identificación Unívoca de Claves de Caché**:
    *   Description: Se asume que los eventos de actualización y las solicitudes manuales pueden proporcionar suficiente información para identificar de forma unívoca la clave o el conjunto de claves de caché que deben ser invalidadas.
    *   Impact if false: La invalidación podría ser demasiado amplia (afectando a más datos de los necesarios) o demasiado restrictiva (fallando en invalidar lo correcto), comprometiendo la eficiencia o la consistencia.
    *   Requires validation from: Equipo de Desarrollo, Dueño de Producto.
