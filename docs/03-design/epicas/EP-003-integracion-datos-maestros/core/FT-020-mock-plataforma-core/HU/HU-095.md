## 3. User Story
Como desarrollador,
Quiero que el mock server simule fielmente los endpoints para catálogos de clasificación de riesgo y garantías,
Para probar la configuración de coberturas y la evaluación del riesgo asociado.

## 4. Functional Description
**Description:** Esta historia de usuario describe la implementación de un mock server que expone dos endpoints específicos: uno para el catálogo de clasificación de riesgo y otro para el catálogo de garantías. El objetivo es que estos endpoints devuelvan datos predefinidos (o una lista vacía) para permitir al "cotizador" consumir esta información y validar su lógica de negocio relacionada con la configuración de coberturas y la evaluación de riesgo en un entorno controlado de pruebas. El mock server debe ser capaz de responder con diferentes conjuntos de datos según la solicitud o configuración.
**Flow:** [Configuración del Entorno de Pruebas] → [HU-095: Simular Endpoints de Clasificación de Riesgo y Garantías] → [Pruebas del Cotizador con Datos Mock]

## 6. Acceptance Criteria (3-5 criteria)
### AC-001: Simulación de Catálogo de Clasificación de Riesgo
**Description:** Valida que el mock server puede responder con una lista predefinida de clasificaciones de riesgo cuando el cotizador lo solicita.

```gherkin
Scenario: El cotizador solicita el catálogo de clasificación de riesgo
  Given que el cotizador está configurado para usar el mock server
  When el cotizador solicita el catálogo de clasificación de riesgo al mock server
  Then el mock server devuelve una lista predefinida de clasificaciones de riesgo (ej. {"id": "CR001", "nombre": "Bajo Riesgo"})
```

### AC-002: Simulación de Catálogo de Garantías


## 16. Technical Notes and Risks
**Risks:**
1.  **Inconsistencia de Contrato de Datos:**
    *   Description: Los IDs y nombres devueltos por el mock server podrían no coincidir con las expectativas del cotizador, llevando a fallos de integración o de lógica de negocio.
    *   Impact: Pruebas inválidas, retrabajo en el mock server o en el cotizador, retrasos.
    *   Probability: Media
    *   Mitigation: Validación temprana con el equipo del cotizador sobre el esquema esperado. Uso de esquemas JSON para validar los datos mockados.
2.  **Mantenibilidad del Mock Server:**
    *   Description: Si el framework de mock server no es fácil de configurar o actualizar, mantener los datos de prueba podría volverse complejo.
    *   Impact: Ralentización del proceso de pruebas, mayor esfuerzo de mantenimiento.
    *   Probability: Baja (si se elige un buen framework)
    *   Mitigation: Seleccionar un framework de mock server que permita la configuración externa de datos (ej. JSON files) y sea ampliamente soportado.

**Technical Debt:** N/A (Para ser llenado por el equipo operativo según el alcance y el MVP)
